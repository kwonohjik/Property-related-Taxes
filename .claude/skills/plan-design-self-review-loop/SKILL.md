# plan-design-self-review-loop — 계획·설계 자가 검토 루프

계획·설계 문서를 **다중 검토→정정 사이클**로 점검하는 워크플로. 1회 검토는 발견 누락이 많다.

**v4 (2026-08-13)** — 실측 기반 재설계. 세 가지가 바뀌었다:

| | v3까지 | v4 |
|---|---|---|
| 규모 판정 | 엔진 타입 변경 = "대" = design.md 2개 **강제** | **검증 깊이**(세액이 바뀌는가) 축으로 재정의 · 산출물은 조건부 |
| 검증 수단 | 검토 표 + 정정 건수 | **mutation probe**(안전망 실측) + V-n·Q-n 레지스터 추가 |
| 병렬화 | fork 기본(중·대) | **인라인 기본** — Opus 5 장문 컨텍스트에서 fork 전제가 약해짐 |

> v4 개정 근거·실측 데이터는 `REVISION-PLAN.md` 참조. 단계 번호 체계(STEP 1~13)는 **보존**한다 — 계획서 15건 이상이 "STEP 5"·"13단계"를 참조한다.

## 적용 시점

- 사용자가 "오류·누락·모순·개선 검토하세요"를 요청
- 계획서 완성 직후, Do 진입 전
- 구현 중 **계획의 전제가 흔들렸을 때**(v4 추가 — §초판 판정 정정)

## 적용 금지

- 단일 파일 1줄 변경·자명한 산식
- 이미 anchor 통과한 회귀 케이스
- 문서가 없는 즉흥 작업 (먼저 계획서부터)

## 검증 깊이 판정 (v4 — 규모 표 대체)

종전 표는 「엔진 input/result 타입이 바뀌면 대」였고 대 규모에 design.md 2개를 강제했다. **실측 결과 준수율 8%**(최근 plan.md 12건 중 design.md 1건)였고, 미준수 건들의 품질은 오히려 양호했다 — 판정축이 현실과 어긋나 있었다.

진짜 축은 **세액이 바뀌는가**다.

| 깊이 | 판정 신호 | 적용 |
|---|---|---|
| **L1** | 라벨·순서·단일 모듈 정리. 세액 불변 | STEP 1~4. mutation probe N/A |
| **L2** | 여러 파일·UI 재배치·신규 필드. **세액 불변**(표시·입력 경로만) | STEP 1~4 + 10~11 + **착수 전 mutation probe** |
| **L3** | **세액이 바뀐다** · 기존 결함을 함께 고친다 · 법령 판정이 갈린다 | 전체 + **V-n 레지스터** + **결정 게이트 Q-n** + 구현 후 mutation |

> 엔진 타입이 바뀌어도 **세액이 불변이면 L2**다. 예: result에 표시용 detail 필드 추가(계산 로직 무변경) → L2. 반대로 UI만 바꿔도 **게이트 술어가 바뀌어 세액 경로가 열리면 L3**다.

## 산출물 게이트 (v4 — 조건부)

**통합 계획서 하나가 기본 1급 산출물**이다. 케이스 매트릭스 + 설계 + 테스트 계획 + 범위 밖을 한 문서에 담는다(최근 계획서가 실제로 수렴한 형태).

`.engine.design.md`·`.ui.design.md`(STEP 5/12)는 **아래 중 하나라도** 해당할 때만 생성한다:

1. 작업이 **여러 세션·여러 PR**에 걸친다 (계획서가 500줄 초과 또는 Phase 3개 이상)
2. **UI 위젯 5개 이상** 신설 — ASCII 레이아웃이 계획서 본문을 압도한다
3. 나중에 **다른 맥락에서 이어받을** 것이 명확하다

조건 미충족이면 STEP 5/12는 **N/A이고 그것이 정상**이다. 종전 "⚠️ 생략 금지"는 이 게이트로 대체됐다 — 문서를 위한 문서를 만들지 않는다.

**재생성 금지**: 문서가 디스크에 이미 있으면 재생성하지 않고 곧바로 검토한다(편집→재검토 경로에서 생성비용 0).

## 표준 13단계 (번호 보존)

```
0.  (사전) policy-check — 관련 memory feedback_* 정책을 검토 기준에 반영
1.  계획문서 오류/누락/모순/정책/개선 검토
2.  정정 사항 반영
3.  계획문서 재검토 (1의 정정이 유발한 파급) [blast-radius]
4.  정정 사항 반영
5.  엔진/데이터 설계 문서 생성          [조건부 — § 산출물 게이트]
6.  설계문서 검토                        [5 수행 시]
7.  정정 반영                            [5 수행 시]
8.  설계문서 재검토 [blast-radius]        [5 수행 시]
9.  정정 반영                            [5 수행 시]
10. 계획 ↔ 설계 통합 비교 (정합축 표 · 14 동기화 지점 커버리지)
11. 수정 사항 각 문서 반영
12. UI 디자인 문서 생성                  [조건부]
13. UI 디자인 검토 + 반영                [12 수행 시]
→ 완료 후: pre-do-anchor-verification → single-response-do-execution
```

> 5~9·12~13이 N/A이면 1~4 → 10~11로 바로 간다. 단일 문서면 10은 **문서 내부 정합**(케이스 매트릭스 ↔ 테스트 계획 ↔ 14 동기화 지점) 점검이 된다.

## ⭐ mutation probe — 안전망 실측 (v4 핵심 신규)

검토가 답해야 할 질문은 「이 코드가 맞는가」만이 아니다. **「이 동작을 지키는 것이 무엇인가」**다. 그것을 추정하지 말고 실측한다.

### 착수 전 — 바꾸려는 동작의 안전망을 잰다

바꿀 예정인 동작(차단문·게이트·산식)을 **의도적으로 무력화**하고 관련 테스트를 돌린다.

| 결과 | 해석 | 행동 |
|---|---|---|
| 여러 건 실패 | 그 동작을 지키는 계약이 실재한다 | 변경 시 그 테스트들의 **의도**를 먼저 읽는다 |
| **전부 통과** | 🔴 **안전망 0건** — 바꿔도 아무도 안 잡는다 | 바꾼 뒤의 동작을 고정할 **신규 anchor를 필수**로 지정 |

> 실측(2026-08-13): validate 차단문을 **통째로 삭제**했는데 `__tests__/calc/`+`__tests__/components/` **330파일 3,032건이 전부 통과**했다. 「grep으로 0건」이라는 정적 판정을 실행으로 확증했고, 그래서 신규 anchor 3건을 필수로 못박았다. 이 실측이 없었다면 「바꿔도 안전하다」까지만 알고 「바꾼 뒤가 무방비」라는 절반은 몰랐다.

### 구현 후 — 새로 심은 anchor가 실제로 잡는지 잰다

anchor마다 **대응 mutation**을 넣어 **정확히 그 anchor만** 실패하는지 확인한다.

- 지워도 초록 → 그 anchor는 아무것도 지키지 않는다 (기각·재작성)
- 엉뚱한 게 무더기로 실패 → 단언이 과녁을 벗어났다 (범위 축소)

```
P-n | 무력화 대상                          | 실패해야 할 anchor
----|--------------------------------------|-------------------
P-1 | 배치 patch의 시점 반영 1줄 제거      | FD-6
P-4 | 차단문 복원(수정 롤백)               | FD-10
P-5 | API 전송 게이트에서 조건 제거        | FD-11
```

### 「없음」·「불변」 단언에는 mutation이 필수다

「이 경로는 세액에 영향 없다」·「회귀 0」 같은 **부정형 단언**은 mutation 없이는 검증되지 않는다(memory `feedback_negative_assertion_needs_mutation_probe`). 계획서에 그런 문장을 쓰면 대응 probe를 함께 설계한다.

## ⭐ 미검증 레지스터 V-n (v4 신규 — L3 필수)

검토 중 「확인 필요」로 남는 것을 **표로 관리**한다. 본문에 흩뿌리면 착수 시점에 잊힌다.

| ID | 항목 | 검증 방법 | 상태 |
|---|---|---|---|
| V-1 | (설계를 가르는 미확인 사실) | KoreanLaw MCP / grep / probe | ⏳ 또는 ✅ |

**규칙**:
- **설계를 바꿀 수 있는 미검증이 남아 있으면 착수 금지.** 무엇이 달라지는지(예: 「고정 상수면 신규 필드 1개, 아니면 2개」)를 항목에 명시한다.
- 해소되면 **판정 근거를 함께 기록**한다 — 나중에 같은 의문이 재발한다.
- 해소 후에도 **여전히 미확인인 부분**은 남긴다. 「설계에는 영향 없지만 확인 안 됨」을 구분해 적고, 그 값을 화면 문구·상수로 **쓰지 않는다**.

> 실측: V-1(「개별주택가격 최초공시를 2005로 고정할 수 있는가」)이 신규 필드 개수를 1개/2개로 가르는 항목이었다. 상가 §164⑥(국세청장 단일 고시 → 상수화 가능)과 대비하고, 같은 구조의 선례(§164⑤ PHD가 날짜 필드 사용)를 찾아 **고정 불가**로 판정 → 2개 확정. 「제도 도입 연도 = 2005」 자체는 미확인으로 남기고 **안내 문구에 넣지 않기로** 못박았다.

## ⭐ 결정 게이트 Q-n (v4 신규 — L3 필수)

해석이 갈리는 지점은 조용히 고르지 않는다. 사용자 결정을 받고 **계획서에 Q-n으로 기록**한다.

- 선택지마다 **무엇이 달라지는지**(작업량·회귀 표면·UX)를 적는다
- 결정 후 **채택 근거**를 함께 남긴다 — 구현 중 흔들릴 때 되돌아볼 기준이 된다
- 결정이 나중에 **정밀화**되면(방향 유지, 술어 변경 등) 그것도 같은 자리에 기록한다

## ⭐ 초판 판정 정정 (v4 신규)

검토·구현 중 **앞선 판정이 틀렸음**이 드러나면 계획서에 **정정을 명시**한다. 조용히 고치지 않는다.

- 그 판정에 기대어 내린 **다른 결정들이 함께 흔들리기** 때문이다
- 형식: 「초판은 X라고 했다. **불완전했다** — 근거 Y. ⇒ 결론 Z로 정정」
- 사용자 승인을 받은 사항이 정밀화되면 **무엇이 유지되고 무엇이 바뀌는지** 분리해 보고한다

> 실측: 「D-1 수정은 세액 영향 없음」이 초판 판정이었으나, `anyEstimated`가 **파트 기반**임을 뒤늦게 확인해 두 조합에서 세액이 바뀔 수 있음이 드러났다. 방향(차단→무시)은 유지하되 **술어를 파트 축으로** 정정했다.

## 검토 표 형식 (매 검토 단계 출력 — 강제)

| # | 카테고리 | 우선순위 | 위치 | 문제 | 정정 |
|---|---|---|---|---|---|

- **6 카테고리**: 오류(인용·산식·시그니처) / 누락(필드·행·소스) / 모순(dual-truth) / **정책위반**(memory feedback_* · 14 동기화 지점) / 개선 / UI누락
- **4 우선순위**: Critical(빌드 깨짐·dual-truth·정책위반) > High(정확도·정합) > Medium > Low

### findings 구조화 + 종료 게이트

- `category` · `severity` · `location`(**file:line 필수** — 불확실하면 grep/Read로 확정) · `issue` · `fix`
- `legalBasis`: **KoreanLaw MCP로 위임 체인 끝까지 검증된 것만**. 미검증은 V-n으로 이관(추정 인용 금지)

**verdict (Do 진입 게이트)**:
- 미해소 critical/high 1건 이상 **또는 미해소 V-n(설계 영향) 1건 이상** → `blocked`
- mustFix 0 · 재검토 newIssues 0 · V-n 전건 해소 → `clean`
- 그 외 → `needs-fix`

## 인용 실측 (v4 강화)

검토에서 의심되는 인용(file:line)·시그니처·필드 존재는 **grep/Read로 실측 확인** 후 정정.

⚠️ **자기 문서의 인용도 예외가 아니다.** 이번 실측에서 자가검토가 **자기 계획서의 줄번호 오차 3건**을 잡았다(`78-82`→`79-82` 등). 계획서를 쓰는 시점과 검토 시점 사이에 파일이 바뀌기도 하고, 처음부터 어긋나 있기도 하다.

## 병렬 검토 게이팅 (v4 — 인라인 기본으로 전환)

v2·v3은 fork 병렬을 중·대 규모 기본으로 뒀다. 근거는 「Workflow의 문서 재-Read 오버헤드 제거」였는데, **Opus 5의 장문 컨텍스트 + 한 응답 다중 도구 병렬 호출**로 그 전제가 약해졌다.

| 조건 | 방식 |
|---|---|
| 기본 | **인라인** — 6카테고리를 한 응답에서 grep/Read 병렬 호출로 훑는다 |
| 검토 대상 문서 **3개 이상** 또는 총 **1,500줄 이상** | fork 2~3-way |
| 문서가 서로 다른 도메인(엔진/UI/법령)에 걸침 | fork(도메인별 분담) |

> 실측: 계획서 1개(약 400줄) 검토는 fork 없이 grep 6회 병렬로 충분했고, 판정 뒤집힘 3건·누락 2건·인용 오차 3건을 잡았다.

fork를 쓸 때는 **한 메시지에 동시 호출**하고, 결과는 file:line 키로 dedup하며, **비판적으로 정독**한다(memory `feedback_subagent_completion_report_scrutiny`).

## blast-radius 재검토 (STEP 3/8/9 — 규모 무관 항상)

1. 직전 정정 diff에서 바뀐 필드명·섹션 헤딩·값을 추출
2. 그 이름들을 문서 + 관련 코드(엔진 타입·컴포넌트)까지 grep
3. 나열된 참조처만 재확인 — 컨텍스트에 있는 본문을 재사용하고 재-Read하지 않는다
4. **이스케이프**: 참조처 10곳 초과 또는 문서 30% 이상이면 즉시 전체 재검토로 fallback

## 통합 비교 정합축 (STEP 10)

| 정합 축 | 계획 | 설계/코드 | 판정 |
|---|---|---|---|
| 엔진 시그니처 | §X | input | ✓/✗ |
| 데이터 소스 단일화 | §X | 도출 | ✓/✗ |
| 인용 file:line | §X | 실측 | ✓/✗ |
| anchor 명명 | §X | 케이스표 | ✓/✗ |
