# plan-design-self-review-loop — 계획·설계 13단계 자가 검토 루프

계획·설계·UI 디자인 문서를 **다중 검토→정정 사이클**로 점검하는 워크플로. 1회 검토는 발견 누락이 많다 — 검토×2 + 통합비교 + 문서 간 동기화로 결함을 수렴시킨다. (메모리 `feedback_11step_self_review_workflow`의 11단계를 UI 디자인 생성·검토까지 확장한 13단계 실행형.)

**v2 (2026-07-03)**: 실측 결과 "중" 규모도 22분이 걸려 호출을 꺼리게 되는 문제가 확인되어 STEP 1/6/13 fork 병렬화 + STEP 3/8/9 blast-radius 재검토 + effort 분리를 도입. 단계 수·이름·번호는 불변(다른 문서의 "STEP 3" 등 참조 유지). 근거·성과 목표는 `REVISION-PLAN.md` 참조.

**v3 (2026-07-10)**: 중복이던 `plan-self-review` Workflow(`.claude/workflows/plan-self-review.js`)를 폐기(throw-stub)하고, 그 고유값(findings JSON 스키마·결정적 verdict 게이트 — 아래 § 검토 표 형식)을 이 스킬로 **이관**. plan.md forward-pointer 8곳을 이 스킬로 재배선. 이 스킬이 계획·설계 자가검토의 **단일 도구**다(Workflow 재도입 금지 — fork는 Workflow 내부 호출 불가라 컨텍스트 상속·재-Read 제거를 재현할 수 없음). 근거: memory `feedback_plan_design_self_review_over_workflow`.

## 적용 시점

- 사용자가 "오류·누락·모순·개선 검토하세요"를 **1회 이상** 요청
- 계획서(`docs/00-pm/*.plan.md`) 또는 설계 문서 완성 직후, Do 진입 전
- 신규 양식·세목·복잡 분기 기능의 문서 정합이 필요할 때

## 적용 금지

- 단일 파일 1줄 변경·자명한 산식
- 이미 anchor 통과한 회귀 케이스
- 문서가 없는 즉흥 작업 (먼저 계획서부터 작성)

## 규모별 적용 깊이 (과/소 적용 방지)

작업 규모에 맞춰 깊이를 조절한다 — 작은 정리에 STEP 5·12(디자인 문서 생성)를 강제하지 않는다. fork 병렬화(§ STEP 1/6/13 병렬 검토) 사용 여부도 같은 표로 게이팅한다 — 소규모에 fork를 쓰면 스폰 오버헤드가 순손실이다.

| 규모 | 예 | 적용 | STEP 1/6/13 fork |
|---|---|---|---|
| **소** | 단일 모듈 필드 정리·라벨/순서 변경 | 계획서 검토×2(STEP 1~4)만. 디자인 문서·STEP 5/12 **N/A** | 미적용(인라인) |
| **중** | 여러 파일·UI 재배치, 신규 엔진 필드 없음 | STEP 1~4 + 통합비교(10·11). 디자인 문서 선택(엔진 변경 시만) | 2~3-way 선택 |
| **대** | 신규 엔진 input/result·복잡 분기·신규 세목 | **전체 13단계 + STEP 5·12 디자인 문서 강제**(아래 ⚠️ 생략 금지) | 최대 6-way |

판정 기준: **엔진 input/result 타입이 바뀌면 "대"**(14 동기화 지점·디자인 문서 필수). UI·문서만 바뀌면 소/중. 아래 ⚠️ STEP 5·12 생략 금지는 **"대" 규모 전제** — 소/중은 디자인 문서 자체가 N/A다.

STEP 3/8/9의 blast-radius 재검토(아래 § 참조)는 규모 무관 항상 적용 — 소 규모라고 재검토 자체를 생략하지 않는다.

**생성 게이트 (재생성 금지 = 리뷰 전용, v3)**: STEP 5/12 설계 문서가 **디스크에 이미 존재하면 재생성하지 않고 곧바로 검토**한다 — 편집→재검토(iterate) 경로에서 생성비용 0. STEP 5/12 생성은 문서가 **없을 때만**(주로 대 규모 최초 1회) 수행하며, 이때의 설계 문서 저작은 output-bound 본질비용이라 어느 방식으로도 제거되지 않는다 → effort는 `high`로 충분하다(opus 모델은 품질 완충으로 유지, `max`는 과잉). 이 게이트는 아래 "⚠️ STEP 5·12 생략 금지"(문서가 필요한데 없으면 만들라)와 **상보적**이다 — 없으면 만들되, 있으면 재생성하지 말 것.

## 표준 13단계

```
0.  (사전) policy-check — 관련 memory feedback_* 정책 검색해 검토 기준에 반영 (자동 안분 fallback 금지·useEffect 미러링 금지·3중 패턴·dual-truth 회피 등)
1.  계획문서 오류/누락/모순/정책/개선 검토 [중·대: fork 병렬]
2.  정정 사항 계획문서 반영
3.  계획문서 재검토 (1의 정정이 유발한 파급 점검) [blast-radius]
4.  정정 사항 반영
5.  계획 기반 엔진/데이터 설계 문서(.engine.design.md) 생성
6.  설계문서 오류/모순/정책/개선/UI누락 검토 [중·대: fork 병렬]
7.  정정 사항 설계문서 반영
8.  설계문서 재검토 [blast-radius]
9.  정정 사항 반영
10. 계획 ↔ 설계 통합 비교 (정합축 표 · 14 동기화 지점 커버리지)
11. 수정 사항 각 문서 반영
12. UI 디자인 문서(.ui.design.md) 생성
13. UI 디자인 오류/누락 검토 + 반영 [대: fork 병렬]
→ 완료 후: pre-do-anchor-verification(핵심 anchor 우선 실행) → single-response-do-execution Do(커밋 전 9단계 코드 품질 게이트)
```

> STEP 0(policy-check)은 "표준 13단계" 명칭 밖의 **사전 준비** — 1~13이 검토 본체다.

### ⚠️ STEP 5·12 생략 금지 (산출물 생성 단계 — 강제)

STEP 5(`.engine.design.md`)·STEP 12(`.ui.design.md`)는 **디자인 문서를 디스크에 실제 생성**하는 단계다. "계획서에 설계가 이미 통합돼 있다"·"단일 통합 문서다"를 이유로 **건너뛰지 말 것** (위반 사례: 통합 계획서 §엔진/§UI 섹션 검토로 STEP 5/12를 대체 시도 → 디자인 문서 미생성).

- 계획서(`docs/00-pm/*.plan.md`)와 디자인 문서(`docs/02-design/features/{feature}.engine.design.md`·`.ui.design.md`)는 PDCA상 **별개 산출물** (`docs/00-pm/feature-workflow.md` Design 단계: `_template.engine.design.md` 복사 + 케이스 인벤토리 표 행≥1).
- 계획서에 엔진/UI 설계가 통합돼 있어도 그 내용을 **디자인 문서 형식으로 구체화**해 별도 파일 생성 (케이스 인벤토리·input/result 타입·알고리즘·동기화 지점·위젯 ASCII).
- 두 파일이 디스크에 존재해야 13단계 완료 — 검토만으로 대체하면 **미완료**.

## STEP 1/6/13 병렬 검토 실행 방법 (중·대 규모)

6개 카테고리(오류/누락/모순/정책위반/개선/UI누락)는 같은 문서를 서로 다른 관점으로 읽는 독립 작업이다 — 여기서만 안전하게 병렬화한다. **Workflow는 쓰지 않는다**(과거 시도 시 fresh-agent가 매번 문서를 처음부터 재-Read해야 해서 더 느렸다 — memory `feedback_plan_design_self_review_over_workflow`). 대신 `Agent(subagent_type:"fork")`를 쓴다 — fork는 현재 대화 컨텍스트를 상속해 프롬프트 캐시를 공유하므로 문서 재-Read가 없다.

1. **분담**: 중 규모 2~3-way(예: [오류+누락] / [모순+정책위반] / [개선+UI누락]), 대 규모 최대 6-way(카테고리별 1개).
2. **동시 호출**: 분담된 fork 전부를 **한 메시지에** 병렬로 호출한다(순차 호출 금지 — 병렬 이득이 사라진다). 각 fork 프롬프트에 검토 대상 카테고리·문서 경로·"검토 표 형식"(아래) 출력을 명시.
3. **병합**: 각 fork의 검토 표를 file:line 키로 합치고 중복 제거. 서로 다른 fork가 같은 결함을 다른 카테고리로 분류해 중복 보고할 수 있다 — 병합 시 하나로 합친다.
4. **비판적 정독**: fork 결과도 서브에이전트 완료보고와 동일하게 취급 — anchor·실측 근거 없이 그대로 신뢰하지 않는다(memory `feedback_subagent_completion_report_scrutiny`).
5. **effort**: fork 프롬프트는 카테고리 성격에 맞게 effort를 지정한다 — 인용 file:line·enum 값·라인 수 같은 기계적 실측은 낮은 effort로 충분하다. 정책위반 판단·Critical/High 우선순위 부여처럼 종합판단이 필요한 부분(주로 병합 후 메인 스레드 작업)은 세션 effort(사용자 설정값)를 유지한다.

## STEP 3/8/9 blast-radius 재검토 (규모 무관 항상 적용)

"2회차 검토는 1회차 정정의 파급을 노린다"(§핵심 원칙)를 절차로 강제한다 — 문서 전체를 다시 Read하지 않는다.

1. 직전 STEP(2/7)에서 실제로 바뀐 필드명·섹션 헤딩·값을 정정 diff에서 추출.
2. 그 이름들을 문서 내부 + 관련 코드(엔진 input/result 타입·컴포넌트)까지 grep해 참조처를 나열.
3. 나열된 참조처만 재확인 — 컨텍스트에 이미 있는 문서 본문을 재사용하고, 참조처가 아닌 구간은 다시 Read하지 않는다.
4. **이스케이프 조항**: 참조처가 10곳을 넘거나 문서의 30% 이상에 걸치면 범위를 좁힌 의미가 없다고 판단 — 즉시 전체 재검토로 fallback한다. 파급 범위를 과소평가해 신규 불일치를 놓치는 것이 재검토 시간을 아끼는 것보다 항상 나쁘다.

## 검토 표 형식 (매 검토 단계 출력 — 강제)

| # | 카테고리 | 우선순위 | 위치 | 문제 | 정정 |
|---|---|---|---|---|---|

- **6 카테고리**: 오류(인용·산식·시그니처) / 누락(필드·행·소스) / 모순(문서 내·문서 간 dual-truth) / **정책위반**(memory feedback_* — 자동 안분 fallback·useEffect 미러링·3중 패턴·14 동기화 지점) / 개선(단순화·일관성) / UI누락(위젯·바인딩·testid)
- **4 우선순위**: Critical(빌드 깨짐·dual-truth·정책위반) > High(정확도·정합) > Medium > Low

### findings 구조화 출력 + 종료 판정 게이트 (폐기된 workflow에서 이관 — 강제)

마크다운 검토 표에 더해, fork 병렬 검토 결과를 병합할 때 각 발견을 아래 필드로 구조화하고 **file:line 키로 dedup**한다(서로 다른 fork가 같은 결함을 다른 카테고리로 중복 보고할 수 있음). 세무 컴플라이언스 도메인의 감사성·재현성 인프라다.

- `category`: 오류 | 누락 | 모순 | 정책위반 | 개선 | UI누락
- `severity`: critical | high | medium | low
- `location`: **file:line 또는 섹션·표 위치(필수)** — 불확실하면 grep/Read 실측으로 확정
- `issue`: 결함 서술 · `fix`: 구체 수정안
- `legalBasis`: 관련 법령 조문 — **KoreanLaw MCP로 위임 체인 끝(본칙·시행령·시행규칙)까지 검증된 것만** 기재. 미검증은 "확인 필요"(추정 인용 금지)

**종료 판정 게이트 (verdict — 기계적 종료 조건, Do 진입 게이트)**:
- 미해소 **critical/high가 1건이라도** 남으면 → `blocked` (Do 진입 금지)
- mustFix 0건 · 재검토 newIssues 0건 → `clean`
- 그 외 → `needs-fix` (mustFix를 Do 진입 전 처리)

생성·정정으로 문서 파일이 실제 편집됐으면 `git diff`로 확인 후 판정한다.

## 핵심 원칙

### 1. 추정 금지 — 실측 후 단정
검토에서 의심되는 인용(file:line)·시그니처·필드 존재는 **grep/Read로 실측 확인** 후 정정. "아마"·"현행 일치 예상" 금지. (이번 세션: `computeLegalShares` 위치 "inheritance-allocation.ts L352"가 실제 `inheritance-legal-share.ts:33` — 실측으로 인용오류 정정)

### 2. 정정은 모든 관련 문서에 동기화
한 정정이 계획·엔진설계·UI설계 3곳에 걸치면 **3곳 모두** 수정. (이번 세션: 계 가산증여 4필드→3행 변경을 3개 문서 동시 반영)

### 3. 통합 비교(10단계)는 정합축 표로
| 정합 축 | 계획서 | 설계 | 판정 |
|---|---|---|---|
| 어댑터/엔진 시그니처 | §X | input | ✓/✗ |
| 데이터 소스 단일화 | §X | 도출 | ✓/✗ |
| 인용 file:line | §X | 주석 | ✓/✗ |
| 코드표 단일출처 | §X | §법령근거 | ✓/✗ |
| anchor 명명 | §5 | 케이스표 | ✓/✗ |
| **신규 필드 → 14 동기화 지점 커버리지** | §X | input/result | ✓/✗ |

> **14 동기화 지점(강제)**: 엔진 input/result에 신규 필드가 생기면 8클라이언트(①~⑧) + API/Route 6(⑨⑩⑪⑫⑬⑭)에 모두 매핑되어야 한다. **⑫Zod 입력객체·⑬body spread·⑭Route 엔진 매핑은 TypeScript가 못 잡아 침묵 strip** → Plan/Design 검토에서 신규 필드별로 14지점 도달 경로를 명시했는지 확인. (CLAUDE.md "Definition of Done — 14개 동기화 지점")

### 2회차 검토는 "1회차 정정의 파급"을 노린다
재검토(3·8단계)는 같은 문서를 다시 읽는 게 아니라 **직전 정정이 만든 새 불일치**를 찾는다. (예: 나 섹션 2원 소스화 → 케이스 인벤토리·계 집계·필드 타입에 파급)

### Do 단계 deviation도 문서에 환류
구현 중 설계와 다르게 간 결정(회귀 회피·정확도)은 **갭 분석에서 설계·계획 문서를 구현에 맞춰 갱신**. 문서-구현 드리프트 0 유지.
