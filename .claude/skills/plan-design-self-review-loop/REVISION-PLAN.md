### 시간이 어디서 새는가

1. **완전 순차 실행** — 13단계 전부를 나 혼자 메인 대화 스레드에서 하나씩 처리한다. 병렬성이 0이다.
2. **재검토가 매번 전체 재-Read** — STEP 3/8/9(재검토)는 스킬 문서상 "직전 정정이 만든 새 불일치를 찾는다"는 원칙만 있고, 실제로는 문서 전체를 다시 훑는 방식으로 수행된다. 위 사례의 STEP2~4(9분)가 가장 큰 덩어리인 이유다.
3. **effort 미분리** — 라인 수 세기·함수 시그니처 대조 같은 기계적 검증과, 정책위반 판단·Critical/High 우선순위 부여 같은 종합판단이 같은 effort로 처리된다. 세션 effort가 지금처럼 max일 때 기계적 검증까지 비싸진다.

### 왜 이전 Workflow 버전은 더 느렸나 (대조군, memory `feedback_plan_design_self_review_over_workflow`)

10단계를 매번 **새 에이전트**(컨텍스트 미보유)로 스폰했다. 매 단계 문서를 처음부터 다시 Read해야 했고, 재검토는 직전 정정 결과에 의존하는 순차 작업이라 병렬성도 못 살렸다. "멀티에이전트"라는 이름값과 달리 실질 병렬 이득 없이 fresh-agent 재-Read 오버헤드만 얹은 셈이다. → **이번 개정에서 Workflow 재도입은 하지 않는다.**

## 2. 설계 원칙

| 원칙 | 내용 |
|---|---|
| A. 의미상 순차는 그대로 | 재검토는 직전 정정 결과가 있어야 성립한다. STEP 1→2→3, 6→7→8 같은 **단계 간** 순서는 병렬화 대상이 아니다 |
| B. 병렬화 대상은 "단계 내부"뿐 | 매 검토 단계의 6개 카테고리(오류/누락/모순/정책위반/개선/UI누락)는 상호 독립적으로 같은 문서를 다른 관점으로 읽는다 — 여기가 유일하게 안전한 병렬화 지점 |
| C. Workflow 대신 fork | `Agent(subagent_type:"fork")`는 대화 컨텍스트를 상속해 프롬프트 캐시를 공유한다 — 과거 Workflow의 "매번 새로 문서 전체 재-Read" 손실을 재현하지 않는다. 병렬화 수단은 fork로 한정하고 Workflow는 쓰지 않는다 |
| D. effort 분리 | 기계적 실측(인용 file:line 확인·enum 값 grep·라인 수 카운트)은 낮은 effort로, 정책위반 판단·우선순위 부여 같은 종합판단은 세션 effort(사용자 설정값) 유지 |
| E. 재검토는 blast-radius로 좁힌다 | STEP 3/8/9는 전체 재-Read 대신, 직전 정정이 건드린 필드명·섹션 헤딩을 추출해 그 **참조처만** grep으로 확인한다. 스킬이 이미 "2회차 검토는 파급을 노린다"고 명시한 원칙을 절차로 강제한다 |
| F. 규모 게이팅을 fork에도 적용 | 기존 소/중/대 표를 fork 사용 여부까지 확장한다. 소규모에 fork를 쓰면 스폰 오버헤드가 순손실이다 |

## 3. 단계별 개정안

| STEP | 현재 | 개정 | 병렬화 |
|---|---|---|---|
| 0 | policy-check | 변경 없음(이미 빠름) | — |
| 1 | 계획서 검토 (인라인, 6카테고리 동시 서술) | 규모 "중" 이상이면 6카테고리를 최대 3개 fork로 분담(예: [오류+누락] / [모순+정책위반] / [개선+UI누락]) → 메인 스레드가 병합해 단일 검토표로 재구성 | ✓ (중·대만) |
| 2, 4, 7, 9-반영, 11 | 정정 반영 (Edit) | 변경 없음 — 파일 쓰기는 순차라 병렬 이득 없음 | — |
| 3, 8 | 재검토 (전체 재-Read) | **blast-radius 재검토**: 직전 STEP에서 바뀐 필드명/섹션명 추출 → grep으로 참조처 나열 → 그 목록만 재확인. 컨텍스트에 이미 있는 문서 재사용, 재-Read 금지 | — (범위 축소가 핵심) |
| 5 | 엔진설계 문서 생성 | 변경 없음(단일 저작물 생성은 병렬화 대상 아님) | — |
| 6 | 설계 검토 | STEP 1과 동일한 fork 분담 | ✓ (중·대만) |
| 9-검토 | 설계 재검토 | STEP 3/8과 동일한 blast-radius | — |
| 10 | 통합비교 | 변경 없음(이미 빠름) | — |
| 12 | UI설계 생성 | 변경 없음 | — |
| 13 | UI설계 검토 | STEP 1과 동일한 fork 분담(대 규모만) | ✓ (대만) |

### 규모별 적용 표 (기존 표 확장)

| 규모 | STEP1/6/13 fork | STEP3/8/9 재검토 범위 |
|---|---|---|
| 소 | 미적용(인라인) | blast-radius(범위 축소는 규모 무관 항상 적용) |
| 중 | 2~3-way 선택 | blast-radius |
| 대 | 최대 6-way | blast-radius, 단 파급 범위가 문서 30% 이상이면 전체 재검토로 fallback |

## 4. 예상 효과 (추정치 — 실측 전까지 확정 아님)

- STEP 1/6/13 fork 병렬화: 이론상 최대 3~6배지만 병합·조율 오버헤드 감안 시 실질 2.5~3.5배 절감으로 **추정**. 확인 필요.
- blast-radius 재검토: 위 사례에서 가장 큰 덩어리였던 STEP2~4(9분) 구간의 절반 이상이 재검토 대상이었다는 근거는 없음(그 9분은 재검토가 아니라 다각도 신규 검토였다) — 이 항목의 절감폭은 **다음 실행에서 실측 필요**.
- effort 분리: 세션 effort가 max일 때(이번 세션처럼) 체감 효과가 가장 크다.

목표치: "중" 규모 22분 → **12분 이하**(약 45% 단축). 이 숫자는 목표이지 보장이 아니다.

## 5. 리스크와 완화

| 리스크 | 완화 |
|---|---|
| fork 병렬 리뷰가 같은 이슈를 중복 보고 | 메인 스레드 병합 시 file:line 키로 dedup |
| blast-radius 재검토가 파급 범위를 과소평가해 신규 불일치를 놓침 | 참조처 grep을 "문서 내부"뿐 아니라 관련 코드까지 확장. 파급 범위가 넓다고 판단되면(예: 참조처 10곳 이상) 즉시 전체 재검토로 fallback — 이스케이프 조항 필수 |
| "소" 규모에도 습관적으로 fork를 써서 오히려 느려짐 | 규모 게이팅 표에 fork 사용 여부를 명시 컬럼으로 고정, 소규모는 기본 금지 |
| fork 결과를 검증 없이 그대로 병합 | 기존 정책 `feedback_subagent_completion_report_scrutiny`(서브에이전트 완료보고 비판적 정독) 그대로 적용 — fork도 예외 아님 |
