### 시간이 어디서 새는가

1. **완전 순차 실행** — 13단계 전부를 나 혼자 메인 대화 스레드에서 하나씩 처리한다. 병렬성이 0이다.
2. **재검토가 매번 전체 재-Read** — STEP 3/8/9(재검토)는 스킬 문서상 "직전 정정이 만든 새 불일치를 찾는다"는 원칙만 있고, 실제로는 문서 전체를 다시 훑는 방식으로 수행된다. 위 사례의 STEP2~4(9분)가 가장 큰 덩어리인 이유다.
3. **effort 미분리** — 라인 수 세기·함수 시그니처 대조 같은 기계적 검증과, 정책위반 판단·Critical/High 우선순위 부여 같은 종합판단이 같은 effort로 처리된다. 세션 effort가 지금처럼 max일 때 기계적 검증까지 비싸진다.

### 왜 이전 Workflow 버전은 더 느렸나 (대조군, memory `feedback_plan_design_self_review_over_workflow`)

10단계를 매번 **새 에이전트**(컨텍스트 미보유)로 스폰했다. 매 단계 문서를 처음부터 다시 Read해야 했고, 재검토는 직전 정정 결과에 의존하는 순차 작업이라 병렬성도 못 살렸다. "멀티에이전트"라는 이름값과 달리 실질 병렬 이득 없이 fresh-agent 재-Read 오버헤드만 얹은 셈이다. → **이번 개정에서 Workflow 재도입은 하지 않는다.**

## 2. 설계 원칙

| 원칙 | 내용 |
|---|---|
| A. 의미상 순차는 그대로 | 재검토는 직전 정정 결과가 있어야 성립한다. STEP 1→2→3, 6→7→8 같은 **단계 간** 순서는 병렬화 대상이 아니다 |
| B. 병렬화 대상은 "단계 내부"뿐 | 매 검토 단계의 6개 카테고리(오류/누락/모순/정책위반/개선/UI누락)는 상호 독립적으로 같은 문서를 다른 관점으로 읽는다 — 여기가 유일하게 안전한 병렬화 지점 |
| C. Workflow 대신 fork | `Agent(subagent_type:"fork")`는 대화 컨텍스트를 상속해 프롬프트 캐시를 공유한다 — 과거 Workflow의 "매번 새로 문서 전체 재-Read" 손실을 재현하지 않는다. 병렬화 수단은 fork로 한정하고 Workflow는 쓰지 않는다 |
| D. effort 분리 | 기계적 실측(인용 file:line 확인·enum 값 grep·라인 수 카운트)은 낮은 effort로, 정책위반 판단·우선순위 부여 같은 종합판단은 세션 effort(사용자 설정값) 유지 |
| E. 재검토는 blast-radius로 좁힌다 | STEP 3/8/9는 전체 재-Read 대신, 직전 정정이 건드린 필드명·섹션 헤딩을 추출해 그 **참조처만** grep으로 확인한다. 스킬이 이미 "2회차 검토는 파급을 노린다"고 명시한 원칙을 절차로 강제한다 |
| F. 규모 게이팅을 fork에도 적용 | 기존 소/중/대 표를 fork 사용 여부까지 확장한다. 소규모에 fork를 쓰면 스폰 오버헤드가 순손실이다 |

**그럼에도 미준수 건들의 품질은 양호했다** — 2026-08-13 작업은 판정 3회 뒤집힘·mutation 6건 실증·vitest 15,561건 통과로 끝났다. ⇒ 규칙이 품질을 만들고 있던 게 아니라, **규칙이 현실과 어긋나 우회되고 있었다.**

### 왜 어긋났나

판정축이 **「엔진 input/result 타입이 바뀌면 대」**였다. 이 축은 두 가지를 구분하지 못한다:

- result에 **표시용 detail 필드**를 더하는 것 (계산 로직 불변 · 세액 불변)
- 게이트 술어가 바뀌어 **세액 경로가 열리는 것** (UI만 건드려도 발생)

앞은 design.md 2개가 과잉이고, 뒤는 타입이 안 바뀌어도 깊은 검증이 필요하다. ⇒ v4는 축을 **「세액이 바뀌는가」**로 옮겼다.

## 3. mutation probe — v4 최대 신규 가치

2026-08-13 실측이 이 항목을 만들었다.

**착수 전**: 바꾸려던 validate 차단문을 **통째로 삭제**하고 관련 테스트를 돌렸다 → `__tests__/calc/`+`__tests__/components/` **330파일 3,032건 전부 통과**.

- grep으로 「그 문자열을 단언하는 테스트 0건」은 이미 알고 있었다. 실행은 그것을 **확증**했을 뿐 아니라, 정적 판정이 놓치는 절반을 드러냈다 — 「바꿔도 안전하다」와 별개로 **「바꾼 뒤가 무방비」**라는 사실.
- 그래서 신규 anchor 3건(FD-10·11·12)을 **필수**로 지정했다. 이 실측이 없었다면 심지 않았을 것이다.

**대조군**: 같은 세션에서 환산주택가격을 2배로 만드는 mutation은 **6건을 실패**시켰다 — 세액 안전망은 실재했다. 두 결과의 대비가 「어디가 비어 있는지」를 정확히 짚었다.

**구현 후**: anchor마다 대응 mutation(P-1·P-4·P-5·P-6 + 결과카드 배선 + 순환계산)을 넣어 **정확히 대응 anchor만** 실패함을 확인했다. 특히 순환계산 mutation(`rawInput`→`input`)은 5건을 실패시켰는데, 그 결함은 **값이 그럴듯해 눈으로는 잡히지 않는** 종류였다.

## 4. 미검증 레지스터 V-n

검토가 「확인 필요」를 만들어내는데, 본문에 흩어 두면 착수 시점에 잊힌다. 표로 모으고 **해소 상태를 추적**한다.

실측 사례 V-1: 「개별주택가격 최초공시를 2005 상수로 고정할 수 있는가」

- **설계를 갈랐다** — 고정 가능이면 신규 필드 1개, 불가면 2개
- 판정: 상가 §164⑥은 국세청장 **단일 고시 사건**이라 상수화 성립. 개별주택가격은 시장·군수·구청장이 **물건별** 공시이고 집행기준도 연도를 못박지 않음. 결정적으로 **같은 구조의 선례**(§164⑤ PHD)가 이미 날짜 필드를 씀 → **고정 불가·2개 확정**
- 해소 후에도 **「제도 도입 연도 = 2005」 자체는 미확인**으로 남기고, 그 값을 **안내 문구에 넣지 않기로** 못박았다 — 이 분리가 v4 규칙이 됐다

## 5. 결정 게이트 Q-n · 초판 판정 정정

해석이 갈리는 지점(5건)에서 사용자 결정을 받아 Q-1~Q-5로 기록했다. 각 선택지에 **작업량·회귀 표면·UX 차이**를 적었다.

**초판 판정 정정**이 별도 절차가 된 이유: 「D-1 수정은 세액 영향 없음」이라는 초판 판정이 **불완전**했다(`anyEstimated`가 파트 기반임을 뒤늦게 확인 → 두 조합에서 세액 변동 가능). 그 판정에 기대어 사용자 승인까지 받은 상태였으므로, **무엇이 유지되고 무엇이 바뀌는지**(방향 유지 · 술어 정정) 분리해 보고해야 했다. 조용히 고쳤다면 승인의 전제가 달라진 것을 사용자가 모른 채 진행됐을 것이다.

## 6. fork → 인라인 기본

v2가 fork를 택한 근거는 **「Workflow의 문서 재-Read 오버헤드 제거」**였다(v2 §1 대조군). 그 근거는 여전히 유효하지만, **Opus 5의 장문 컨텍스트 + 한 응답 다중 도구 병렬 호출**이 더 단순한 경로를 제공한다.

실측: 계획서 1개(약 400줄) 검토를 fork 없이 grep 6회 병렬로 수행 → 판정 뒤집힘 3건·누락 2건·인용 오차 3건 발견. fork 스폰·병합 오버헤드가 순손실이었을 규모다.

⇒ **인라인 기본**, fork는 문서 3개 이상 또는 총 1,500줄 이상 또는 도메인이 갈릴 때. v2 Phase 3(「실측 미달 시 Phase 2 롤백」)의 조건부 롤백을 이 형태로 집행한 셈이다.

## 7. 성과 기준 교체

「정정 누적 ≥10건」은 **문서가 엉성할수록 커지는** 역방향 지표였다. 잘 쓴 계획서를 검토하면 건수가 적게 나오는데, 그것을 「검토가 부실했다」로 읽게 된다.

v4는 결과로 잰다: **판정 뒤집힘 ≥1건**(검토가 방향을 바꿨는가) · **안전망 실증**(mutation) · **미검증 0**(V-n 해소) · **Critical/High 0**.
