# 양도세 개발과정 회고 & 향후 점진 확장 방식 개선안

## Context

사용자는 "기본 아웃라인 → 케이스별 문제 해결 → 점진 확장" 방식으로 양도세를 약 6개월간 개발해 왔고, 같은 방식을 취득·재산·상속·증여·종부세 5개 세목으로 확대하려 함. 이 방식 자체는 세법의 본문·단서·각호가 사례별로 펼쳐지는 도메인 특성에 맞아 유지가 합리적이지만, 양도세 진행 중 누적된 31개 feedback 메모리·8개 동기화 지점 정책·UI/엔진 시니어 분리 등이 모두 **사후 대응**으로 도입된 흔적이 있음. 이 문서는 (1) 양도세에서 반복된 문제 패턴, (2) 이미 도입된 가드레일, (3) 타 세목 확장 시 같은 학습비용을 다시 치르지 않기 위한 워크플로 보강안을 정리.

---

## A. 양도세 작업과정에서 반복된 문제 패턴

| # | 패턴 | 사례 | 근본원인 |
|---|---|---|---|
| 1 | **조문 케이스 누락 설계** | 일괄양도 §166⑥ — 사용자가 준 1개 케이스(상속+안분)만 구현 후 매매·증여·실가구분 재작업 | 사례 → 설계 직행, 조문 본문·단서·각호 전수 분기 미선언 |
| 2 | **8개 동기화 지점 누락** | API/UI fallback은 추가했는데 validation은 그대로 → 화면 통과↔검증 차단 모순 (2회 연속) | 동기화 지점이 7개일 때 ⑧ validation 누락이 정책화 안 됨 |
| 3 | **useEffect cross-field 미러링 → 무한 루프** | 3개 useEffect로 store 미러 시도 → "Maximum update depth exceeded" | "자동 동기화 = useEffect" 본능적 반응 |
| 4 | **Silent fallback으로 세무 오류** | 개별주택공시가격 미입력 시 면적비율 자동 안분 → "아주 잘못된 로직" | 빈 값을 채워주는 게 친절이라는 UX 직관 ↔ 세법은 명시적 입력 요구 |
| 5 | **UI 배치 ↔ 계산 흐름 분리** | PHD 토글·토지면적 위치를 사용자가 반복 재배치 요구 | 폼 설계가 디자이너 시각(섹션 그룹화) 우선, 엔진 변수 사용 순서 무시 |
| 6 | **테스트는 사후 추가** | PHD 41개 anchor, 겸용주택 4부분 안분 anchor 모두 구현 완료 후 사용자 검증으로 회귀 발견 → 테스트 추가 | 설계 단계에서 "이 케이스 수만큼 anchor 만든다" 약속이 없음 |
| 7 | **엔진 시니어가 UI까지 동시 담당** | 2026-04-30 이전 PHD·겸용주택 구현은 단일 에이전트 → UI 통합 누락 반복 | UI 시니어 분리 정책 자체가 사후 도입 |
| 8 | **API 라우트 Date 직렬화 silent bug** | route.ts에서 JSON string → Date 변환 누락 → `Date < string` silent false | 타입은 Date인데 JSON 경유로 string 도달, TS가 잡지 못함 |

## B. 이미 도입된 가드레일 (작동 중)

- **CLAUDE.md "Definition of Done — 8개 동기화 지점"** + 자가 점검 체크리스트
- **MEMORY.md 31개 정책 메모리** — feedback_*, project_* 분류
- **`policy-check` 스킬** — 작업 시작 시 관련 정책 사전 검색
- **`tax-field-add` 스킬** — 새 필드 추가 시 8개 지점 모두 점검
- **`mirror-pattern` 스킬** — useEffect 미러링 사전 차단
- **PDCA 5단계 + 엔진/UI 시니어 분리** — `{feature}.engine.design.md` + `{feature}.ui.design.md`
- **`ui-engine-sync-checker` 에이전트** — read-only 사후 검증
- **legal-codes 상수 + `verify:legal` 스크립트** — 조문 문자열 리터럴 금지
- **PDF 예시값 anchor 테스트 패턴** — 원단위까지 `toBe()` 회귀 자동 방어

## C. 아직 약한 지점 (타 세목 확장 시 재발 위험)

### C-1. **케이스 인벤토리가 설계 산출물이 아님**
- 현재: 사용자가 케이스를 던지면 그때 구현. 누락된 케이스는 사용자가 발견할 때까지 모름.
- 위험: 취득세 중과 13유형, 재산세 토지 3분류, 상속공제 7종 등 분기 폭이 양도세보다 크거나 같음.

### C-2. **Validation 동기화는 여전히 수동 체크리스트**
- `ui-engine-sync-checker`가 read-only로 점검하지만 호출은 사람이 결정.
- CI에 통합되지 않아 PR 단위 자동 차단 없음.

### C-3. **API 페이로드 Date·BigInt 직렬화 정책 부재**
- 양도세 1건 발견된 silent bug가 타 세목 라우트에 잠복 가능.
- 정책: 라우트 핸들러 진입 직후 "Date 필드 명시 변환 zone" 강제하는 helper 부재.

### C-4. **설계 단계 anchor 약속 부재**
- 설계 문서에 "이 기능은 N개 시나리오로 anchor N개" 선언 칸이 없음.
- 결과: 테스트는 항상 후행, 회귀는 사용자 의존.

### C-5. **엔진 시니어 ↔ UI 시니어 분리 정착도 낮음**
- 2026-04-30 신설. 양도세 PHD·겸용주택은 단일 에이전트 시절 결과물 → 8개 동기화 지점 사후 보완 잔존 가능성.

### C-6. **메모리 정책이 31개로 증가 — 사전 검토 비용 상승**
- `policy-check` 있으나 새 작업마다 31개 전수 매칭 비용. 도메인별 인덱스(예: "양도세 작업 시 먼저 보는 5개") 부재.

## D. 권장 개선안 (점진 적용, 큰 비용 없는 순)

### D-1. **설계 문서에 "케이스 인벤토리 + anchor 약속" 섹션 강제** (즉시 적용 가능)
- 모든 `{feature}.engine.design.md` 상단에 다음 표 의무:
  ```
  | # | 시나리오 | 법령 근거 | anchor 출처 | 테스트 파일 |
  ```
- 표가 비어 있으면 Do 단계 진입 금지. 사용자가 케이스를 추가로 던질 때 표에 행 추가 → 새 anchor 자동 약속.
- 도구: 새 스킬 또는 design-validator 에이전트가 표 존재·행≥1 검증.

### D-2. **`api-date-zone` helper 신설** (1회 작업, 영구 효과)
- `lib/api/date-coerce.ts` — 라우트 핸들러 첫 줄에서 사용:
  ```ts
  const body = coerceDates(rawBody, ["transferDate", "acquisitionDate", ...]);
  ```
- 누락 시 BigInt·Date 비교 silent bug 차단. 타 세목 라우트 도입 시 강제 패턴화.

### D-3. **8개 동기화 지점 자동 검증을 pre-commit hook 또는 CI에 포함**
- `ui-engine-sync-checker`를 husky pre-commit / GitHub Actions로 자동 실행.
- 누락 발견 시 커밋·머지 차단. 사람 의존 제거.

### D-4. **세목별 정책 인덱스 분리**
- `MEMORY.md`에 "양도세 작업 시 먼저 보는 5개", "취득세 작업 시 먼저 보는 5개" 그룹 추가.
- `policy-check` 스킬이 작업 세목 키워드 감지 시 해당 그룹만 우선 로드.

### D-5. **타 세목 첫 진입 시 양도세 회고 1회 적용**
- 취득세 UI 첫 작업 시작 전 다음 4개 강제 검토:
  1. 8개 동기화 지점 체크리스트 미리 채우기 (실구현 전)
  2. 케이스 인벤토리 표 작성
  3. silent fallback·자동 안분 후보 식별
  4. cross-field 동기화 필요 지점 → useEffect 사용 금지 미리 선언
- 효과: 양도세에서 6개월에 걸쳐 학습한 5개 정책이 첫 PR 전에 적용됨.

### D-6. **"엔진 + UI 시니어 동시 Plan 참여" 정책 강제**
- 새 기능 PM/Plan 단계에 두 에이전트 모두 호출 — 한쪽만 작성 금지.
- 단일 에이전트가 엔진+UI 동시 담당하는 패턴 차단.

## E. 점진 확장 방식 자체에 대한 판단

이 방식은 **유지가 옳음**. 세법은 사례를 만나면서 분기가 드러나는 구조라 워터폴 설계로 전수 분기를 사전 선언하는 것은 비현실적임. 단, **"케이스 발견 → 코드 직행"이 아니라 "케이스 발견 → 설계 문서 갱신 → 코드 + anchor 동시 추가"** 의 미니 PDCA 루프가 한 사이클 더 들어가야 함. D-1·D-3·D-5가 그 루프를 강제하는 도구.

## F. 적용 우선순위 추천

1. **D-1 케이스 인벤토리 표** — 다음 새 기능부터 즉시. 코드 없음, 문서 규칙만.
2. **D-5 취득세 첫 진입 회고 적용** — 취득세 UI 시작 시점에 1회.
3. **D-2 date-coerce helper** — 1시간 작업, 영구 효과.
4. **D-4 정책 그룹 인덱스** — MEMORY.md 편집만.
5. **D-3 CI 자동 검증** — 가장 큰 효과지만 husky/GHA 셋업 필요.
6. **D-6 동시 Plan 참여 강제** — 에이전트 트리거 정책 변경.
