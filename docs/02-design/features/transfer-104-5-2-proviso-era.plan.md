## 3. 2019년 전 계산 모델 — 결정 필요 (Q-1)

### 3.1 두 후보

단서가 없을 때 2호는 「자산별 산출세액 합계액」이다. 같은 호 자산의 합산은 예규 536으로 2019 전에도 본문이다. 문제는 **«둘 이상의 호에 해당하는 자산»(단기 × 중과, 단기 × 비사업용 토지, 단기 × 1호)이 어느 «호별 합산»에 속하느냐**다. 이 문제를 직접 다룬 2019 전 해석례는 확보하지 못했다(확인 필요).

| 후보 | 2019 전 복수 호 자산 처리 | 근거 독법 |
|---|---|---|
| **β (권고)** | **합산하지 않는다** — 자산(파트)마다 §104① 후단·⑦ 후단으로 큰 세액을 정해 그대로 더한다. 단일 호 자산의 호별 합산(본문·예규 536)은 지금과 같다 | 단서가 하는 일(«복수 세율 자산을 합산한 뒤 호별로 큰 것»)만 2019 전에서 걷어낸다. 「자산별 산출세액」의 문언 그대로 |
| α | 자산마다 **이긴 호(`rateClause`)**를 그 자산의 호로 보고, 이긴 호가 같은 단위끼리 합산한다. 합산한 뒤에는 그 호 세율만 적용한다(다시 MAX 하지 않음) | 예규 536의 «호별 합산»을 «실제 적용된 호» 기준으로 복수 호 자산까지 넓힌다 |

### 3.3 α의 1원 절벽 (P7 실측)

P1 구조에서 C를 300,000,000으로 고정하고 B를 1원씩 움직였다. B의 승자가 ①3호에서 ⑦3호로 바뀌는 지점은 **99,333,339 → 99,333,340**이다.

| 모델 | B=99,333,339 | B=99,333,340 | 1원 차이로 변한 세액 |
|---|---|---|---|
| 현행(단서) | 214,200,002 | 214,200,004 | 2 |
| **β** | 194,333,335 | 194,333,337 | **2** |
| α | 194,333,335 | 214,200,004 | **19,866,669** |

α는 B가 1원만 넘어가도 C와 합쳐져 ⑦ 누진의 높은 구간을 탄다. 같은 구조가 승자에 따라 합쳐지기도 하고 나뉘기도 하는 문제는 2026-08-02 Q3(`transfer-rate-clause-candidates.plan.md` §4)가 «승자 의존»으로 기각한 바로 그 구조다.

### 3.4 권고 — β

1. **지시와 범위가 일치한다** — «추가된 단서를 2019 전에는 적용하지 않는다»를 그대로 옮긴 것이 β다. α는 단서 제거에 더해 **현행에도 없는 새 합산**(P2의 D, P4의 장기 비사토)을 만든다.
2. **현행보다 세액이 오르는 사례가 없다**(위 표 범위). α는 P2·P4에서 2,190만~2,230만 원 오른다. 2019 전 복수 호 자산을 승자 호로 합산하라는 근거는 확보하지 못했다([[feedback_no_unfavorable_application_without_legal_basis]]).
3. **절벽이 없다**(§3.3).

⚠️ β의 한계: 예규 536의 «호별 합산»을 복수 호 자산에는 적용하지 않는 독법이다. 2019 전 복수 호 자산의 합산을 다룬 해석례가 나오면 다시 본다(확인 필요 W-1).

## 4. 설계 (β 기준)

### D-1. 시행일 상수 — `lib/tax-engine/data/sec104-5-2-proviso-era.ts` (신규)

A2 선례 `data/sec104-5-reduction-parenthesis-era.ts`와 같은 형식으로 둔다.

```ts
export const SEC104_5_2_PROVISO_FROM = "2019-01-01";
/** 양도일 기준 — 제16104호 부칙 제2조②. */
export function isSec104_5_2ProvisoInForce(transferDate: Date): boolean;
```

- 판정 기준은 **단위가 실어 온 입력의 `transferDate`**다(S-1 `ClausePart.rateInput` · S-2 `ctx.taxRateInput`).
- 다건은 한 과세기간이라 모든 단위가 같은 쪽에 놓인다. 따라서 `taxYear`를 새로 넘기지 않는다(시그니처 불변).

### D-2. 합산 식별자 — 2019 전 복수 호 단위는 **혼자**

`transfer-tax-rate-clause.ts`에 순수 함수 하나를 더한다. 키(`clauseBucketKey`)는 그대로 두고, **합산 식별자만** 단위마다 고유하게 만든다.

```ts
/** §104⑤2호 단서 시행 전(2019.1.1. 전 양도)이고 해당 호가 둘 이상이면 합산하지 않는다 — 식별자에 단위 번호를 붙인다. */
export function provisoMergeId(key: string, candidates: readonly RateClause[] | undefined, transferDate: Date, unit: string | number): string
// candidates.length >= 2 && !isSec104_5_2ProvisoInForce(transferDate) ? `${key}#${unit}` : key
```

| 지점 | 변경 |
|---|---|
| S-1 `bucketIdOf` (`:319`) | `id`를 `provisoMergeId(...)`로 만든다. 분양권 `presale:` 접두는 그 위에 그대로 붙인다. `key`(라벨·echo용)는 바꾸지 않는다 |
| S-2 `clauseGroups` (`:311`) | 그룹 키를 `provisoMergeId(clauseBucketKey(...), finals[i].candidateClauses, ctx.taxRateInput.transferDate, i)`로 |
| S-3 `partClauseBasisOf` (`:502`) | S-2와 **같은 식**으로 — 미러가 갈리면 감면 파트의 호 산정이 S-2 묶음과 어긋난다 |

- `members.length === 1`이면 버킷 세액 = 단위 세액(`calculatedTax`, 자산 단독 MAX)이다. 따라서 β 세액은 별도 계산 없이 «자산별 MAX 합»이 된다.
- S-1의 크로스 echo(`:370` `id === "104-1-8"`, `:373` `"104-1-1"`)는 복수 호 단위가 원래 해당하지 않으므로 영향이 없다.

### D-3. 감면 라벨 — `solo-*`를 쓰지 않는 이유

`transfer-tax-aggregate-reduction-step.ts:139`는 `solo-*` 키를 「호 미상」으로 표시한다. 2019 전 복수 호 단위는 호를 알고 있으므로, **`key`는 그대로 두고 식별자(`id`)에만 `#단위번호`**를 붙인다. 라벨은 `echo.key`를 읽으므로(`:137`) 「§104①2호·§104①8호」로 계속 표시된다.
