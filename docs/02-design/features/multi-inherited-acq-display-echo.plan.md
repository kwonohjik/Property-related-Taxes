# 다건·함께 양도 — 상속·증여 §163⑨ ② 채택 자산의 취득가액·필요경비 표시 정정

> **출처**: `multi-sec163-9-support.plan.md` §4 V-2·V-3(#2891 남은 확인). V-2를 재다가 표시 결함을 찾았다.
> **결정**: ⏳ 사용자 결정 대기(§2).
> **검증 깊이**: L2 — 표시 전용(세액 불변). 다건·함께 양도의 신고서 양식·계산결과 상세명세서·합산 결과 카드의 취득가액·필요경비 칸.

## 0. 결론

- **V-2 ✅ 카드** — 다건 건별 상세는 공용 `ReductionDetailCards`를 써서 §163⑨ 카드(「상속·증여 취득가액 의제 계산」)와 §164⑦ 환산 카드를 그대로 보여 준다.
- **V-3 ✅** — 다건 「이력 불러오기」는 단건 폼을 단건 세션 복원과 같은 `migratePersistedTransferForm`으로 옮긴다. ② 칸이 살아 세액·본문 키가 직접 입력과 같다.
- **새 결함(D-1)** — §163⑨ ②가 채택된 자산은 다건·함께 양도 화면의 **취득가액이 ①(또는 0)**, **필요경비가 그 차액**으로 표시된다. 세액은 맞다.
  - 원인: 표시 echo `resolveDisplayAcquisitionAndExpense`(`lib/tax-engine/transfer-tax-aggregate-display-echo.ts:188`)가 일반 실가 자산의 취득가액을 `r.singleInput.acquisitionPrice`(route 입력 = ①)에서 읽는다. 필요경비는 그 값에서 `양도가액 − 취득가액 − 양도차익`으로 거꾸로 구한다(`:198`).
  - 단건 엔진은 STEP 0.45에서 취득가액을 §163⑨ 채택값으로 바꾸고, 그 값을 `inheritedAcquisitionDetail.acquisitionPrice`에 남긴다. echo는 이 값을 읽지 않는다.
  - 항등식(양도가액 − 취득가액 − 필요경비 = 양도차익)은 역산 때문에 **그대로 성립**해서 자기검산이 결함을 가린다(같은 파일 F-14 주석의 함정과 같은 모양).
- 단건 신고서는 엔진 `expenses`에서 취득가액을 역산하므로(`FilingFormTableHelpers.ts` 일반 분기) 맞다. 결함은 echo를 쓰는 **다건과 함께 양도** 두 경로에만 있다. 함께 양도는 #2891 **전부터** 같았다.
- 시험 수정 1줄(`r.result.inheritedAcquisitionDetail?.acquisitionPrice ?? r.singleInput.acquisitionPrice`)로 다건 11행·함께 양도 6행이 전부 단건 표시와 같아졌다(§1.2 · 측정 뒤 원복).

- 함께 양도(단건 화면 · 매매 주택 + 상속 자산 · 양도가액 안분)도 같다. 상속 주택 ① + ② 열 = 취득가액 300,000,000 · 필요경비 420,000,000(정답 720,000,000 · 0).
- 화면(headless Playwright · 다건 상속 주택 ① + ②): 「신고서 양식(합산)」 취득가액 300,000,000 · 필요경비 420,000,000, 「계산결과 상세명세서」 취득가액 300,000,000 · 필요경비 420,000,000. 같은 화면의 §163⑨ 카드는 「의제 취득가액 720,000,000」이라 **한 화면 안에서 숫자가 서로 다르다**.

### 1.3 V-3 — 단건 기록 → 다건 불러오기

- 위 9행을 단건 폼으로 만들어 JSON 왕복한 기록을 `buildPropertyFromSingleRecord`로 불러와 다건 route에 보냈다. 9행 전부 직접 입력과 세액·본문 키가 같다(상속 주택 ① + ② 149,006,000 · 토지 1988 224,499,000 · 의제 전 ③ 143,701,555 등).
- 증여 행의 ⑧ 이슈 1건은 직접 입력에도 똑같이 있다(시료에 증여 필수 칸이 덜 찼다 — 기존 anchor도 증여 행은 ⑧을 건너뛴다). 불러오기 때문이 아니다.
