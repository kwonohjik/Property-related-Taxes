## §1 조문 — 세 건이 각각 무엇에 걸리는가

### 1.1 §100②③ — 구분 축은 「토지와 건물 등」

> **「소득세법」 제100조 제2항**: 「… **토지와 건물 등**을 함께 취득하거나 양도한 경우에는 이를 각각
> 구분하여 기장하되 **토지와 건물 등의 가액 구분이 불분명할 때에는** … 안분계산한다」
>
> **같은 조 제3항**: 「… 그 **토지와 건물 등**을 구분 기장한 가액이 같은 항에 따라 안분계산한 가액과
> **100분의 30 이상 차이**가 있는 경우에는 … **불분명한 때로 본다**. 다만, 다른 법령에서 정하는 바에
> 따라 가액을 구분한 경우 등 대통령령으로 정하는 사유에 해당하는 경우는 제외한다」

「토지와 건물 등」이 반복되는 것이 **Q-10의 답**이다(§4).

### 1.2 §159① — 부담부증여의 양도가액은 계약서에서 오지 않는다

> **「소득세법 시행령」 제159조 제1항 제2호**: 「양도가액 = A × B ÷ C.
> **A**: 「상속세 및 증여세법」 제60조부터 제66조까지의 규정에 따라 **평가한 가액** ·
> **B**: 채무액 · **C**: 증여가액」

⇒ 양도가액이 **평가액 × 채무비율**로 나온다. 계약서상 구분 기재가 들어갈 자리가 없다 —
S-11 차단의 근거는 타당하다. 문제는 근거가 아니라 **그 차단이 실제로 작동하지 않는다**는 것이다.

### 1.3 부가령 §64① — 1호·2호·3호의 실제 문언

> **1호**: 토지와 건물등에 대한 기준시가가 **모두 있는 경우**: 공급계약일 현재의 기준시가 비율 안분.
> **다만, 감정평가가액**[…]이 있는 경우에는 그 가액에 비례하여 안분.
> **2호**: 토지와 건물등 중 **어느 하나 또는 모두의 기준시가가 없는 경우로서** 감정평가가액이 있는
> 경우: 그 가액 비율. **다만, 감정평가가액이 없는 경우에는 장부가액**(없으면 취득가액)에 비례하여
> 안분한 후 **기준시가가 있는 자산에 대해서는 그 합계액을 다시 기준시가에 의하여 안분**.
> **3호**: 제1호와 제2호를 **적용할 수 없거나 적용하기 곤란한 경우**: 국세청장이 정하는 바.

**「소득세법 시행령」 제166조 제6항**은 「**「부가가치세법 시행령」 제64조제1항에 따라** 안분계산 하며」
로 **제1항 전체**를 준용한다. 그리고 2호 단서를 **명시적으로 언급**한다 — 「제64조제1항제2호 단서에
해당하는 **장부가액이 없는 경우**에는 「상속세 및 증여세법」 제62조제1항에 따라 평가한 가액을
기준으로 한다」.

🔴 **그러므로 Q-8을 「조문이 준용되지 않는다」로 종결하면 틀린다.** 2호·3호는 **준용된다**.
범위 밖인 이유는 다른 데 있다(§5).

> 다만 §166⑥의 상증법 §62① 부분은 「**선박 등 그 밖의 유형재산**」에 관한 것이라 토지·건물에는
> 직접 걸리지 않는다.

## §2 실측 — 방어선은 UI 하나뿐이고 뚫리지만, 엔진은 그 값을 안 읽는다

### 2.0 먼저 — 이 조합은 **UI에서 실제로 만들 수 있다**

마스터 계획서 §16.3이 「일반건물 × 부담부증여 조합 **가능 여부 미실측**」으로 남겨 둔 항목이다.
**측정했다 — 가능하다.** `TransferModeBlock.tsx:50`의 `SUPPORTED_ASSET_KINDS`에
`"general_building"`이 들어 있어 양도 형태 라디오가 일반건물에도 렌더된다.

### 2.1 무엇을 쟀나

`transferType: "burdened_gift"` + `saleSplitMode: "actual"` + 구분 양도가액(800/200)이 들어 있는
일반건물 `AssetForm`을 만들어 **폼이 실제로 쓰는 진입점**에 넣었다(throwaway probe, 확인 후 삭제).

| 계층 | 기대 | **실측** |
|---|---|---|
| `validateAssetEntry`(`transfer-tax-validate-asset.ts:669`) | 차단 메시지 | 🔴 **`null`(통과)** |
| `buildGeneralBuildingValuation`(`transfer-tax-api-gb.ts:134`) | 필드 미포함 | 🔴 **`landTransferPrice: 800000000` · `buildingTransferPrice: 200000000` 전송** |

⚠️ **진입점을 `validateGeneralBuildingAsset`으로 잡고 재면 안 된다** — 그것은 하위 함수이고,
그 앞에 `validateBurdenedGiftAsset`이 먼저 돈다(§2.2). 하위 함수만 재면 「어느 검증도 안 걸렸다」는
결론을 **우연히** 맞히게 되어, 고쳐야 할 파일을 틀리게 지목한다(이 계획서 초안이 그랬다).

### 2.2 왜 뚫리나 — 검증기가 **둘**인데 어느 쪽도 안 막는다

부담부증여 일반건물은 검증기를 **두 개** 지난다:

```
validateAssetEntry (transfer-tax-validate-asset.ts:669)
  ├─ :115  validateBurdenedGiftAsset   ← transfer-tax-validate-bg.ts (158줄)
  │          :123-132  일반건물 전용 블록 (5-b) — 취득시 기준시가 2필드 필수
  │          ⇒ S-11 차단 **없음**
  └─ :260  validateGeneralBuildingAsset ← transfer-tax-validate-gb.ts (429줄)
             :35-58  부담부증여 블록 — **모든 경로가 return**, :58 `return null`로 종료
             :409    S-11 차단 ← 🔴 **도달 불가**
```

`transfer-tax-validate-gb.ts:409`의 차단은 :35 블록이 항상 먼저 return하므로 **한 번도 실행되지
않는다**. 「부담부증여는 환산/신축 분기 미적용 — 여기서 종결」이라는 :58의 주석이 그 사실을 말하고
있는데, 나중에 :409를 추가할 때 그 전제가 검토되지 않았다.

🔑 **그리고 `transfer-tax-validate-bg.ts`에는 이미 일반건물 전용 블록이 있다**(:123-132).
S-11 차단이 있어야 할 자리는 **거기**다 — 부담부증여를 아는 검증기이고, 일반건물 분기도 이미
열려 있다. gb 쪽 :409의 죽은 차단은 옮기지 말고 **제거**한다(§3.2 A′).

### 2.3 API 게이트에는 애초에 조건이 없다

`lib/calc/transfer-tax-api-gb.ts:111-118`:

```ts
function saleSplitFields(asset: AssetForm): Record<string, unknown> {
  if (asset.saleSplitMode !== "actual") return {};   // ← 모드만 본다
  return { landTransferPrice: …, buildingTransferPrice: …, … };
}
```

부담부증여 조건이 없다. **유일한 방어는 UI다** —
`GeneralBuildingBlock.tsx:422-431`이 `blockedReason`을 넘기고,
`GeneralBuildingSaleSplitSection.tsx:55-63`이 그때 라디오·입력칸 대신 안내문만 렌더한다.

### 2.4 잔존 값이 그 UI 방어를 우회한다

양도 형태 전환은 `TransferModeBlock.tsx:62` `selectMode()` 한 곳에서 일어난다.
부담부증여 분기(`:79-88`)는 **다른 교차 상태는 정리한다**:

```ts
} else if (v === "burdened_gift") {
  onChange({
    transferType: "burdened_gift", transferCause: "general",
    nblExemptPublicExpropriation: false,                                  // ← 정리한다
    reductions: (asset.reductions ?? []).filter(r => r.type !== "public_expropriation"), // ← 정리한다
    ...(asset.bgValuationMode ? {} : { bgValuationMode: "sangjeungbeop_standard" }),
  });
```

**`saleSplitMode`·`landTransferPrice`·`buildingTransferPrice`만 빠져 있다.** 전수 grep 결과
이 세 필드를 `transferType` 변경 시 정리하는 코드는 저장소 어디에도 없다.

⇒ 사용자가 ① 일반건물을 구분양도로 입력하고 → ② 양도 형태를 부담부증여로 바꾸면,
화면에서는 칸이 사라지지만 **store에는 값이 남고 API로 전송된다**.
sessionStorage persist라 **세션을 넘어서도 남는다**(메모리 `feedback_new_asset_field_stale_sessionstorage_guard`).

🟢 **정리 패턴이 이미 그 자리에 있다는 점이 중요하다** — 새 메커니즘을 만드는 게 아니라
같은 `onChange` 객체에 세 키를 **추가**하는 것이라 수술 범위가 작다.

### 2.5 수치 영향 — 안분이 실제로 움직인다

`buildGeneralBuildingAssetCards`를 구분값 유무로 두 번 호출해 비교했다
(총 양도가액 10억 · 양도시 토지 기준시가 6억 · 건물 기준시가 2억):

| | 토지 | 건물 |
|---|---|---|
| 구분값 없음(안분) | 750,000,000 | 250,000,000 |
| 구분값 800/200(30% 내) | **800,000,000** | **200,000,000** |

**파트별 양도가액이 5천만원 이동한다.**

> 참고로 900/100을 넣으면 건물 편차 6,000bp(60%)로 §100③이 발동해 안분값으로 되돌아간다
> (`deemedUnclear: true`). **30% 안쪽 값일 때만 움직이는 것**이라 눈에 잘 띄지 않는다.

🔴 **그런데 이 측정은 「부담부증여의 세액이 바뀐다」를 뜻하지 않는다.** `buildGeneralBuildingAssetCards`
는 **환산 경로**의 함수이고, 부담부증여는 그 경로로 가지 않는다 — §2.6.

### 2.6 🔑 부담부증여는 **실가 경로**로 가고, 그 경로는 구분값을 **읽지 않는다**

payload 형태를 실측했다(부담부증여 일반건물, 기본 상태):

```
actualPriceMode = true · landAcqMode = actual · buildingAcqMode = actual
landTransferPrice = 800000000        ← 실려는 간다
```

`actualPriceMode === true`면 라우터가 **실가 경로**로 보낸다
(`general-building-route-helper.ts:160`) → `calculateGeneralBuildingActualTransfer`
(`general-building-route-actual.ts:104`).

**그 함수는 `landTransferPrice`·`buildingTransferPrice`를 destructure하지 않는다**
(:111-128 구조분해 목록 · 파일 전체 grep 0건). 자체 §166⑥ 비율(`landRatioNum`, :138)을 쓰고,
부담부증여면 `if (burdenedGiftInfo)` 분기(:159~)에서 채무비율로 파트 가액을 다시 만든다.

⇒ **잔존 구분값은 엔진까지 도달하지만 소비되지 않는다.** 세액 델타는 **0일 가능성이 크다.**

⚠️ **「크다」이지 「0이다」가 아니다.** 실가 경로 전체를 읽어 확인한 것이 아니라 구조분해 목록과
grep으로 좁힌 것이다. **Phase A가 그것을 끝까지 잰다**(§3.1). 메모리
`feedback_numeric_impact_verify_before_bug_claim`에 따라, **측정 전에는 「세액 결함」이라고 부르지 않는다.**

⇒ 그래도 **고칠 값어치는 있다**: ① 「막는다」고 적힌 코드가 안 막히는 상태를 방치하면 다음 사람이
그것을 방어선으로 신뢰한다 ② 경로가 하나만 바뀌어도(예: 환산 파트가 섞이면) 즉시 소비된다.

## §4 Q-10 다필지 — **§100③ 축이 아니다**

### 4.1 조문이 구분하라는 축

§100②③은 「**토지와 건물 등**」의 구분만 규율한다(§1.1 원문). **필지 간 구분을 요구하는 문언이 없다.**
증축(본체·증축)이 Q-10에 함께 묶여 있던 것은 그것이 「건물 내부 구분」이라 같은 성질로 보였기
때문인데, 그건 §22에서 **「건물 합계」 2-way 판정**으로 정리됐다 — 즉 **§100③의 축은 끝까지 2-way다.**

⇒ **다필지에는 §100③ 판정 단위 문제가 존재하지 않는다.** 필지가 몇 개든 「토지」 한 덩어리로
건물과 비교한다.

### 4.2 그럼 다필지는 무엇이 문제인가 — **별개 축이다**

일반건물 엔진의 토지는 **단일 필지 모델**이다:

- `lib/tax-engine/types/general-building.types.ts:76` — `landArea: number` (배열 아님)
- 양도시 토지 기준시가 = `transferLandPricePerSqm × landArea`(같은 파일 `:511` 주석)

필지마다 개별공시지가가 다르면 사용자가 **가중평균을 손으로 계산해 한 칸에 넣어야 한다.**
이것은 **기준시가 산정 정확도** 문제이지 §100③ 문제가 아니다.

### 4.3 판정 — **이 계획서 범위 밖으로 확정**

- §100③ 축으로서의 Q-10: **존재하지 않는 문제**로 종결한다.
- 다필지 입력 축(필지별 면적·공시지가): **별건**으로 분리한다. 자산 모델 변경이라 비용이 크고,
  구분양도 축과 **의존이 없다**(어느 쪽을 먼저 해도 무방).

⚠️ **되살아나는 조건**: 필지별로 **양도가액을 따로 기재**해야 할 법령 근거가 생기면 그때는
§100③ 축으로 돌아온다. 현행 문언에는 없다.

## §5 Q-8 §64① 2호·3호 — 결론은 맞고, **근거를 바꾼다**

### 5.1 종전 근거는 부정확했다

계획서는 「일반건물은 기준시가 2필드가 필수라 1호 경로가 전제된다」로 적었는데, 이 문장만 보면
「2호·3호는 준용되지 않는다」로 읽힌다. **아니다** — §166⑥은 §64조 제1항 **전체**를 준용하고,
2호 단서를 **직접 언급**한다(§1.3).

### 5.2 정확한 근거 — **폼이 1호 요건을 강제한다**

`lib/calc/transfer-tax-validate-gb.ts`가 양도시 토지·건물 기준시가를 **양쪽 다 필수**로 잡는다:

- 부담부증여 경로 `:50` `:54`
- 일반 경로 `:72` `:74`

넷 다 `parseAmount(...)`의 falsy 검사라 **0도 차단**한다. ⇒ 1호의 요건 「기준시가가 **모두 있는
경우**」가 **항상 충족**되므로 2호(「기준시가가 없는 경우」)에 도달할 수 없고, 1호가 늘 적용
가능하므로 3호(「제1호와 제2호를 적용할 수 없거나 곤란한 경우」)에도 도달하지 않는다.

### 5.3 판정 — **범위 밖 유지 확정**. 되살아나는 조건을 명시한다

⚠️ **이 필수 규칙이 완화되면 Q-8이 즉시 되살아난다.** 특히:

- 양도시 건물 기준시가 **0 입력을 허용**하면(예: 철거 예정 건물) 2호 경로가 열린다.
  엔진 `sale-split-apportion-basis.ts:90-92` `usableStdPrice`는 **합계 > 0**만 보므로
  **엔진은 이미 0을 받아들인다** — 막고 있는 것은 validate뿐이다.
- 일반건물 외 자산종류로 이 안분을 확장하면 기준시가가 없는 자산이 들어올 수 있다.

⇒ **validate의 4개 필수 검사에 「이걸 풀면 부가령 §64①2호가 열린다」는 주석을 남긴다.**
코드에 근거를 붙여야 다음 사람이 무심코 완화하지 않는다.

**B·C는 서로 독립**이라 병렬 가능하다. Phase A가 B의 범위를 A·A′로 확정했다.

🔴 **P-1(§3.5)·U-4(§7.1)는 이 Phase에 없다.** 별건이고, **P-1은 이 계획서의 세 건 모두보다
우선순위가 높다** — 세액이 실제로 틀리고 기본 경로에서 나기 때문이다.

파일 크기(800줄 정책 · 2026-08-07 실측): `transfer-tax-validate-bg.ts` **158줄** ·
`transfer-tax-validate-gb.ts` **429줄** · `transfer-tax-api-gb.ts` **352줄**.
Phase B는 **주 수정처가 158줄 파일**이고 증분이 +20줄 수준이라 트리거(800)까지 여유가 크다.

### 7.1 🔴 U-4 — 조사 중 나온 별건

`buildGeneralBuildingValuation`은 **한 파트라도 환산이거나 증축이 있으면** 환산 경로 payload를 낸다
(`transfer-tax-api-gb.ts:217` — `if (anyEstimated || asset.gbHasExtension)`).
그런데 **환산 경로는 `burdenedGiftInfo`를 받지 않는다**:

- `general-building-route-helper.ts`에서 `burdenedGiftInfo`가 등장하는 곳은 **:65(파라미터)와
  :186(실가 경로에 전달)뿐**이다. `:252` 환산 경로 호출에는 없다.
- `general-building-valuation.ts`·`general-building-extension.ts`에 **부담부증여 참조 0건**(grep).

⇒ 부담부증여 자산이 환산 경로로 가면 **§159 채무비율 산정이 통째로 빠질** 수 있다.

**도달 가능성**: UI는 부담부증여에서 취득가액 산정 방식·증축 토글을 숨긴다
(`CompanionAcqPurchaseBlock.tsx:262` 게이트). 그러나 같은 파일 :220-222가 **폼 상태를 의도적으로
보존**한다고 명시한다 — 「양도 형태를 '일반 양도'로 되돌리면 입력값 복원 가능」.
⇒ **먼저 환산·증축을 켜고 나중에 부담부증여로 바꾸면 플래그가 살아 있다**(S-11과 같은 잔존 경로).

⚠️ **아직 「그래서 세액이 틀린다」를 측정하지 않았다.** route.ts의 if-체인이 앞단에서 잡아낼
가능성도 있다(메모리 `feedback_route_if_chain_order_swallows_branches`).
**이 계획서의 작업 범위에 넣지 않는다** — 사실이면 S-11보다 크고 성격도 달라서, 별도 조사·계획이 맞다.

⚠️ **U-2는 S-11 수정의 전제가 아니다** — 지금 고치는 것은 「막는다고 해 놓고 안 막힌 것」이라
