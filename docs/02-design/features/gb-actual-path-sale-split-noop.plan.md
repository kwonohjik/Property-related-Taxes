## §0 결론 먼저 — 결함이 **셋**이고, 전부 **같은 모양**이다

일반건물 payload는 취득 방식에 따라 **두 경로**로 갈린다. 세 결함 모두
**「환산 경로엔 구현돼 있고 실가 경로엔 없다」**이다.

| | 결함 | 적용 범위 | 크기(실측) |
|---|---|---|---|
| 🔴 **P-3** | **자본적지출·양도비가 실가 경로에 도달하지 않는다** | **비용을 입력한 모든 실가 경로 자산** | **결정세액 12,800,000원 과대** (+지방소득세 1,280,000) |
| 🟠 **P-2** | 일괄 **취득가액**을 **양도시** 기준시가 비율로 안분 | 일괄 취득가액이 있는 모든 실가 경로 자산 | 토지 취득가액 **152,930,559원** 이동 |
| 🟠 **P-1** | 구분양도·감정평가·§166⑧ **미구현** | 구분양도를 쓴 자산 | 토지 양도가액 **316,625,253원** 이동 |

🔴 **P-3이 가장 나쁘다** — 구분양도든 아니든, **필요경비를 입력한 모든 자산이 과대과세**된다.
P-2·P-1은 파트 간 배분이 틀리는 것이고(합계는 보존), **P-3은 차감 자체가 사라진다.**

⚠️ **기본 취득모드가 실가**라 환산을 쓰지 않는 평범한 일반건물이 곧 이 경로다.

### 0.1 순서가 강제된다 — P-3 → P-2 → P-1

**P-2의 「비용을 자본적지출·양도비로 나눠 각각 다른 비율로 안분한다」(§5)는 P-3을 고치기 전에는
구현할 수 없다** — 나눌 두 값이 애초에 도달하지 않아 **효과 없는 코드**가 된다.

⇒ **P-3(도달) → P-2(시점·분리) → P-1(구분양도)**. 반대 순서는 불가능하다.

## §1 조문

### 1.1 §100② — **「취득 또는 양도 당시」** 두 시점을 나란히 둔다

> **「소득세법」 제100조 제2항**: 「… 토지와 건물 등을 함께 **취득하거나** 양도한 경우에는 이를 각각
> 구분하여 기장하되 토지와 건물 등의 가액 구분이 불분명할 때에는 **취득 또는 양도 당시의**
> 기준시가 등을 고려하여 대통령령으로 정하는 바에 따라 안분계산(按分計算)한다.
> **이 경우 공통되는 취득가액과 양도비용은 해당 자산의 가액에 비례하여 안분계산한다.**」

⇒ 함께 **취득**한 것의 구분이 불분명하면 **취득 당시** 기준시가, 함께 **양도**한 것이면 **양도 당시**다.

### 1.2 부가령 §64①의 「공급계약일 현재」는 **시점 준용이 아니다**

「소득세법 시행령」 §166⑥이 「부가가치세법 시행령」 §64①을 준용하고 그 1호는 「**공급계약일 현재**의
기준시가」라 한다. 그대로 읽어 「전부 양도시」로 가면 안 된다 — **§166⑥이 준용하는 것은 §64①의
「안분계산」 방법**이고, **어느 시점의 기준시가인지는 §100② 본문**이 이미 「취득 **또는** 양도 당시」로
정하고 있기 때문이다.

## §2 P-3 — 자본적지출·양도비가 **엔진에 도달하지 않는다**

### 2.1 실측 — fetch body 전수

`callTransferTaxAPI`를 `fetch` stub으로 가로채 실제 body를 봤다
(일반건물 실가 · 자본적지출 30,000,000 · 양도비 10,000,000 입력):

```
body.expenses            = 0
body.capitalExpenditure  = 30,000,000     ← 최상위에는 실린다
body.transferExpense     = 10,000,000     ← 최상위에는 실린다
gbv.capitalExpenditure   = undefined      🔴 GB payload엔 없다
gbv.transferExpense      = undefined
gbv.bundledExpenses      = undefined

⇒ route.ts:374   bundledExp = gbv.bundledExpenses ?? body.expenses ?? 0  =  0
⇒ actualExpenses = 0 으로 엔진 진입
```

### 2.2 세액 영향 (총액 10억 · 취득 5억 · 비용 4,000만)

| | 결정세액 | 지방소득세 |
|---|---|---|
| 현행(비용 0원 도달) | 133,060,000 | 13,306,000 |
| 정상(비용 40,000,000 반영) | 120,260,000 | 12,026,000 |
| **과대** | **12,800,000** | **1,280,000** |

### 2.3 왜 — 세 지점이 어긋나 있다

| # | 지점 | 상태 |
|---|---|---|
| ① | `AssetSectionExpense.tsx:58·80` | 현행 입력 칸은 **자본적지출·양도비** 두 개다. `directExpenses`는 **legacy**로, 둘이 0일 때만 렌더된다(`:109-115`) |
| ② | `transfer-tax-api.ts:285-290` | `expenses`는 **legacy `directExpenses`에서만** 온다 ⇒ 현행 필드를 쓰면 **0** |
| ③ | `transfer-tax-api-gb.ts` | `capitalExpenditure`·`transferExpense`를 **환산 payload(:279-289)에만** 넣는다. 실가 payload(:317-352)에는 **없다** |
| ④ | `general-building-route-actual.ts:319` | `buildProperties(cards, nonBusinessRatio)` — **swap 인자 없이** 호출한다. 환산 경로는 `resolveGeneralBuildingSwap(…, gbv.capitalExpenditure, gbv.transferExpense, …)`로 소비한다(`route-helper:255-260`) |

| ⑤ | `GeneralBuildingAcquisitionCards.tsx:348·459` | 파트별 자본적지출 칸은 **`isSeparate`(분리 ON) 블록 안**에만 렌더된다 ⇒ 기본 상태(분리 OFF)에서는 **대체 입력 경로도 없다** |

⇒ **분리 OFF 상태의 실가 경로에는 비용이 들어올 문(門)이 하나도 없다.**

### 2.4 ✅ W-0 해소 — **의도가 아니라 미반영이다** (2026-08-07 조사)

**근거 1 — 같은 결함이 환산 경로에서 이미 「버그」로 고쳐졌다.** 커밋 `ce846daa`(2026-07-21):

> 일반건물(general_building) **환산취득가 경로에** 자본적지출·양도비를 전달할 필드가 없어
> §97②2호 단서 swap 미발동 → capex>개산공제 시 **과다과세**(Phase 1 상가 PR#721 후속)

「전달할 필드가 없어 → 과다과세」 — 이번에 실가 경로에서 잰 것과 **같은 문장**이다.
그 커밋은 스스로 「**환산**취득가 경로에」로 범위를 한정했고, 실가 경로를 다루지 않는다는 언급도
다룰 필요가 없다는 언급도 **없다**.

**근거 2 — 설계 의도가 「실가 파트도 가산한다」고 명시돼 있다.**
O-1 커밋(`4c946050`)이 남긴 주석 `GeneralBuildingAcquisitionCards.tsx:194`:

> §97②2호는 파트별로 규칙이 갈린다 — **실가 파트는 같은 항 1호(가산)**, 환산 파트는 2호 단서(택일).

`general-building-route-cards.ts` `buildProperties`에도 같은 서술이 있다
(「실가 파트 자본적지출 **가산** — §97②**1호**는 택일이 아니라 …」).

**근거 3 (결정적) — 같은 함수가 분리 ON이면 쓰고 분리 OFF면 못 쓴다.**

```ts
// general-building-route-actual.ts:237
landExp = landDirectExpenses ?? landExpApportioned;   // 분리 ON일 때만 오는 파트별 자본적지출
```

이 동작을 고정한 anchor도 이미 있다
(`general-building-part-acq-modes.anchor.test.ts:154` — 「파트 입력 → 그 파트는 전액 직접 귀속」).

| 상태 | 입력 칸 | 도달 |
|---|---|---|
| **분리 ON** | 파트별 자본적지출(`landDirectExpenses`) | ✅ `:237` |
| **분리 OFF**(기본) | 자산 단위 자본적지출(`capitalExpenditure`) | 🔴 **경로 없음** |

**반대 근거는 0건이다** — 실가 경로에서 비용이 0이어야 한다는 주석·테스트가 없고,
UI가 자본적지출 칸을 가리지도(`AssetSectionExpense.tsx:58` 무조건 렌더) validate가 막지도 않는다.
**사용자는 칸을 보고 값을 넣는데 세액에 반영되지 않는다.**

### 2.5 🔑 실가 경로는 **swap 대상이 아니다** — 수정이 더 단순하다

환산 경로의 해법(`resolveGeneralBuildingSwap`)을 그대로 옮기면 **틀린다**.
실가 경로는 환산취득가도 개산공제도 쓰지 않으므로(`route-actual.ts:101-102`)
§97②2호 **단서**(환산가 ↔ 자본적지출+양도비 **택일**)의 요건 자체를 충족하지 않는다.

⇒ 적용 조문은 §97②**1호**(「해당 실지거래가액 + 제1항제2호·제3호의 금액」) — **단순 가산**이다.
**swap 판정을 배선하는 것이 아니라, 값을 필요경비로 실어 보내면 된다.**

## §9 회귀

### 9.1 P-3 — **세액이 줄어드는 방향**이다

비용이 새로 차감되므로 **기존 anchor 중 실가 경로 + 비용 입력 조합은 값이 바뀐다**.
⚠️ 다만 현재 그런 조합의 테스트가 있는지 **미조사** — 착수 시 먼저 센다.

🔑 **줄어드는 방향이라도 「고쳐서 세금이 줄었다」로 서술하지 않는다** — 납세자 유·불리 표현 금지.
사실은 「§97①2호·3호 필요경비가 차감되지 않던 것을 차감하게 됐다」이다.

### 9.2 P-2 — 반전 대상은 **딱 1건**이고 Excel 정답표가 **아니다**

**실측**(`:223`만 취득시 비율로 바꾸고 `npm run test:transfer` 전건):

### 9.3 🔑 Excel 유래 단언과 개발자 회귀 가드는 **성격이 정반대**다

이 계획서 초안은 위 단언을 「Excel 정답표 anchor」로 보고 「확인 없이 반전 금지」라고 적었다.
