## 2. 🔴 산식과 값이 어긋난다 (더 나쁜 쪽)

명세서 `transferPrice` 항목의 **산식 문자열이 값과 다른 것을 가리킨다**:

```
양도가액 formula: "재개발 §166 — 인가전(권리가액 의제) + 인가후(분양가 안분) + 청산금(분양가 안분)"
양도가액 value  : 525,000,000        ← 그 3파트 합은 744,218,499 이다
취득가액 formula: "재개발 §166 — 인가전(§166③ 환산 또는 실가) + 인가후(권리가액 의제) + 청산금(청산금 의제)"
취득가액 value  : 512,000,000        ← 이쪽은 산식대로 파트 합
```

원인은 `DetailedStatementRedevelopmentBuilders.ts`의 **두 지점이 서로 다른 기준을 쓰는 것**이다:

| 위치 | 코드 | 기준 |
|---|---|---|
| `:609` | 주석 「양도가액 — 합계는 totalTransferPrice 유지」(값 미변경) | 계약총액 |
| `:632` | `acqItem.value = sumAcq` | 파트 합 |
| `:467` | `applyLandContribOverrides` 내 동일 패턴 | 파트 합 |

## 3. 「합계 ≠ 파트 합」 자체는 결함이 아니다 (오독 차단)

§166은 파트가 **단계별 의제**다 — 인가전 양도가액 = 권리가액 의제, 인가후 = 분양가 안분.
같은 경제적 가치가 인가전의 「양도가액」이자 인가후의 「취득가액」으로 재등장하므로
**파트 합 ≠ 실제 양도가액이 설계상 정상**이다. 신고서가 역산을 쓰는 이유가 이것이다
(memory `feedback_redev_filing_form_acquisition_inverse`).

⇒ 본 계획은 **파트 합을 합계로 만들지 않는다.** 명세서의 취득가액만 신고서와 같은 역산으로 맞춘다.

> receiveOnly(C46)가 유일한 예외였던 이유: 그 모드는 **파트가 곧 신고단위 전부**라 둘이 일치한다.
> PR #1265에서 해소됐다.

## 6. 설계

### 6-1. 🔴 정정 — 「명세서 자체 값으로 역산」은 성립하지 않는다 (V-1 실측)

신고서 역산(`FilingFormTableHelpers.ts:565-578`)은 **분기별 `expenses`·`gain` 합**을 뺀다.
명세서는 `expenses`·`transferGain` 항목을 **자기 나름의 소스**로 세팅한다
(`expenses` = `estimatedLumpDeduction` · `transferGain` = 「합계 그대로(회귀 보존)」).

**실측 결과 두 값이 실제로 다르다**(V-1 — 7건 중 3건). 그리고 명세서 값으로 역산하면
**신고서와 어긋난다**(정정 2). 사용자가 정한 방향은 「신고서를 정본으로 맞춘다」이므로:

⇒ **역산의 피감수는 신고서와 동일한 「분기 합」을 쓴다.** 그리고 자기일관이 성립하도록
**명세서 필요경비 표시도 같은 분기 합으로 정정**한다. 둘은 분리할 수 없다 —
취득가액만 고치면 `양도 − 취득 − 경비 ≠ 차익`이 그대로 남는다.

> memory `feedback_shared_predicate_argument_parity` — **술어 공유 ≠ 단일 소스**. 인자 동일성까지 봐야 한다.
> 이번엔 그 인자(필요경비)가 실제로 달랐고, 그것이 계획을 뒤집었다.

### 6-2. 공용 leaf

`components/calc/results/transfer/`에 순수 함수 1개(무의존 leaf):

```ts
/** 재개발 합계 취득가액 역산 — 양도가 − 필요경비 − 양도차익. 자기일관성 보장. */
export function inverseRedevAcquisition(args: {
  totalTransferPrice: number;
  totalExpenses: number;
  totalGain: number;
}): number
```

- **산식만 담는다.** 어떤 값을 넣을지는 호출부가 정한다(§6-1).
- 신고서(`FilingFormTableHelpers.ts:565-578`)도 이 leaf로 **교체**한다 — 산식이 두 곳에 복제된 채
  한쪽만 바뀌는 드리프트를 원천 차단(이번 결함이 정확히 그 형태였다).
- 승계조합원 분기(`successorMemberApplied`)의 「인가후 분만」 규칙은 **호출부에서 인자를 고르는 방식**으로
  유지한다 — leaf에 분기를 넣지 않는다.

신고서·명세서가 **같은 함수의 같은 인자**를 쓰게 해 재드리프트를 막는다.

### 6-4. 산식 문자열도 함께 고친다 (필수)

값을 역산으로 바꾸면 현재 취득가액 산식(「인가전 + 인가후 + 청산금」)이 **또 값과 어긋난다** —
지금 양도가액이 겪고 있는 바로 그 병이다. 산식을 역산 서술로 교체한다:

```
취득가액 = 양도가액 − 필요경비 − 양도차익 (§166 단계별 의제 구조상 파트 합과 다름)
```

**파트별 내역(`perAsset`)은 그대로 둔다** — 단계별 의제 값 자체는 정보로서 유효하고,
합계와 다른 이유는 위 서술이 설명한다.

### 6-5. 🟡 양도가액 산식 문구 (범위 포함 여부 = Q-1)

`:610-624`의 양도가액 산식은 **값이 계약총액인데 「3파트 합」이라고 적혀 있다.** 취득가액을 고쳐도
이 오기는 남는다. 문구만 바로잡는 저비용 수정이나 **사용자가 지시한 방향(취득가액)의 밖**이다.

### 🔴 M-3 — 승계조합원 분기는 **no-op이었다** (구별력 0)

`redevBranchTotals`의 승계 분기를 제거하는 뮤테이션에 **anchor가 울리지 않았다.**

원인 실측: 엔진이 승계 시 인가전·청산금을 **이미 0으로 강제**한다
(사례 48: `preApproval {exp 0, gain 0}` · `settlement {exp 0, gain 0}`).
⇒ 「인가후 분만」과 「전체 합」이 같은 값이 되어 분기가 방어적 중복이 된다.

**분기를 지우지 않았다** — 엔진 계약이 바뀌면 그것이 방어선이기 때문이다. 대신
**그 계약 자체를 anchor A-9로 고정**했다. 계약이 깨지면 A-9가 잡는다.
leaf 주석에도 「실측상 no-op이나 계약에 기대지 않고 남긴다」를 명시했다.

> 교훈: 구별력 0인 anchor를 방치하지 않되, **원인이 「테스트가 약해서」가 아니라 「대상이 no-op이라서」**인
> 경우가 있다. 그때는 anchor를 억지로 만들지 말고 **그 no-op을 성립시키는 전제**를 고정한다.
