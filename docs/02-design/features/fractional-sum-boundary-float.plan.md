## 2. 결정 요청 (Q 레지스터)

**Q-1 경계를 어떻게 할까** — a) 그대로 둔다(세액 오류 없음·경계에 닿기 어려움). **b) 오차 여유 `1e-9`를 더해 경계를 통과로 고정(권장)**. c) 정수 연산(몫을 100분의 1 단위 정수로 반올림해 합산)으로 전환.
- b 근거: 변경이 한 줄이고, 시험 적용·3자리 스윕 불일치 0. 통과로 늘어나는 입력은 «십진으로 정확히 허용 폭 끝»뿐이라 이미 허용한 폭 안이다(세액 영향 ≈ 66,528원, 직전 계획서 Q-2의 선형 외삽 — 직접 측정 아님).
- c는 입력이 `parseFloat`한 소수 문자열이라 소수 자리 수를 가정해야 하고(2자리·3자리·분수 분모 100 외 값), ⑧이 분모를 입력받는 구조(`ownershipDenominator`)와 맞지 않아 과하다.

**Q-2 판정을 한 함수로 묶을까** — **a) `lib/calc/fractional-ratio-sum-tolerance.ts`에 `isFractionalRatioSumOutOfTolerance(sum)`을 추가해 ⑧과 일반건물 ⑫가 쓴다(권장)**. b) 두 곳에 `+ 1e-9`를 각각 쓴다.
- a 근거: 직전 PR에서 «세 곳이 같은 상수를 쓴다»로 통일했는데 판정식은 두 곳에 복제돼 있다. 같은 부동소수 합을 쓰는 두 곳이 어긋나지 않게 판정까지 하나로 둔다. ⑫ 축 B 가드는 정수 가액 비교라 이 함수를 쓰지 않는다.

**Q-3 ⑧ 차단 문구에 허용 폭을 병기할까** — **a) 안 한다(권장)**. b) 한다.
- 경계는 통과로 고정되므로 `현재 99.94%`가 차단 문구에 나오는 경우가 없어진다(차단되는 최소 합은 99.939…%로 `toFixed(2)`가 99.94로 보일 수 있음 — 입력이 3자리 이상일 때만). 이 경우는 매우 드물어 문구 변경은 하지 않는다.

## 3. 구현 계획 (Q-1 b · Q-2 a · Q-3 a 선택 시)
