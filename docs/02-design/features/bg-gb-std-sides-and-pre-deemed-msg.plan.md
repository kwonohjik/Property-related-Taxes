## 0. 이미 정해진 것 (재제안 금지)

- 직전 계획서 Q-1 (a): 기준시가 평가 양도시 기준시가 0은 ⑧ + 엔진 fail-fast(`burdened-gift-apportionment.ts` — 보충적 평가액 합 0이면 400)로 막는다. 이 계획은 그 엔진 차단이 **합계가 0일 때만** 걸려 남은 한쪽 0을 다룬다.
- Q-25(2026-10-23): 1985 전 상속·증여 부담부증여의 기준시가 평가 = 의제취득일 기준시가 × 채무비율. ③(환산취득가액)이 없다.
- 「자동 안분 fallback 금지」: 빠진 값을 다른 값으로 메우지 않고 입력을 요구한다.
- ⑧은 일반건물 부담부증여에 기준시가 4칸을 **평가 방식과 무관하게** 이미 요구한다 — 양도시 토지 ㎡당 공시지가·건물 총액(`transfer-tax-validate-gb.ts:88`·`:93`), 취득시 토지 ㎡당·건물 총액(`transfer-tax-validate-bg.ts:453`·`:456` · 같은 파일 `transfer-tax-validate-gb.ts:91`·`:95`).

## 1. 법령 확인

직전 계획서 §1(KoreanLaw MCP · 소득세법 시행령 MST 290841, 2026-10-01 시행본 · 2026-10-25 조회)을 그대로 쓴다.

- §159①2호 — 양도가액 = A × B / C(A: 상증법 §60~§66 평가액). 기준시가 평가면 A·C가 양도시 기준시가(토지 + 건물)와 담보·임대 평가 중 큰 값이다.
- §159①1호 괄호 — 양도가액을 기준시가로 산정하면 취득가액도 기준시가(취득시 기준시가 × B/C).

시가 평가에서 양도시 기준시가를 쓰는 곳은 법령 문언이 아니라 **엔진 동작**으로 적는다: 엔진은 시가 평가 양도가액을 토지·건물 양도시 기준시가 비율로 나눈다(`burdened-gift-apportionment.ts:200-203`). 이 비율의 법령 근거는 이 계획에서 새로 인용하지 않는다.

## 3. 설계

### 3.1 ⑫ — 일반건물 부담부증여 기준시가 칸 필수 (`lib/api/transfer-tax-schema-gb-bg-refines.ts`)

`refineGbBurdenedGiftActualPath`(이미 주 자산·지분·함께 양도 세 곳을 같은 표지로 훑는다 — `:34-61`)에 같은 세 곳의 `burdenedGiftInfo` 기준시가 검사를 더한다.

```
const STD_KEYS = Q-1 결정에 따라 양도시 2칸 (+ 취득시 2칸);
const requireStd = (info, path) => info && STD_KEYS.forEach((k) => !(info[k] > 0) && addIssue([...path, "burdenedGiftInfo", k], 문구));
주 자산: propertyType === "general_building" && transferType === "burdened_gift" → requireStd(data.burdenedGiftInfo, [])
지분:   같은 조건 → generalBuildingShares[i].burdenedGiftInfo
함께 양도: companionAssets[i].assetKind === "general_building" → requireStd(c.burdenedGiftInfo, ["companionAssets", i])
```

- **평가 방식과 무관**하다 — ⑧과 같은 범위(§0)이고, 시가 평가도 모양 B에서 세액이 바뀐다(§2.2).
- 문구(안): 「일반건물 부담부증여 — 양도시 토지·건물 기준시가가 모두 필요합니다. 기준시가 평가면 증여가액과 양도가액이, 시가 평가면 토지·건물 양도가액 안분이 이 값으로 정해집니다 (소득세법 시행령 제159조 제1항).」 · 취득시(Q-1 (b)): 「일반건물 부담부증여 — 취득시 토지·건물 기준시가가 모두 필요합니다 (소득세법 시행령 제159조 제1항 제1호).」
- **왜 엔진이 아니라 ⑫인가**: 모양 A와 B가 route에서 갈라져 서로 다른 엔진 경로로 간다(§2.1). 일반건물 경로에 같은 검사를 넣고 재본 결과 모양 B는 막혔지만 **모양 A(양식 비움)는 200 · 세액 0 그대로**였다(Pre-Do probe). 일반 자산 경로는 정상 입력(바닥면적 비움)도 지나가므로 그쪽에 「일반건물이면 막기」를 넣으려면 `propertyType` 분기가 엔진 두 곳에 생긴다. ⑫는 두 모양이 모두 거치는 한 곳이다. 직전 계획서 Q-1이 ⑫를 뺀 근거(엔진 한 곳이 다 막는다)는 여기 성립하지 않는다.
- ⑧을 통과한 입력은 4칸이 모두 0보다 크다: ④ `buildBurdenedGiftInfo` 일반건물 분기(`transfer-tax-api-burdened-gift.ts:425-446`)가 ⑧이 검사한 같은 칸(토지는 ㎡당 × 면적, 취득시 토지는 ⑧과 같은 leaf `effectiveGbLandPriceAtAcq`)으로 만든다. 지분 `info`는 물건 단위 값이라 둘째 지분 칸을 비워도 0이 아니다(§2.2).

### 3.2 ⑫ — 기준시가 평가 부담부증여는 ③ 이유 문구에서 뺀다 (`transfer-tax-schema-required-refines-2a.ts:676`)

```
if (
  !positive(ia.standardPriceAtTransfer) &&
  !positive(d.standardPriceAtTransfer) &&
  !(d.transferType === "burdened_gift" && d.burdenedGiftInfo?.valuationMode === "sangjeungbeop_standard")
)
```

- 술어는 `:656`과 같은 글자 그대로다(새 판정을 만들지 않는다).
- 빠진 요청은 엔진 fail-fast(`burdened-gift-apportionment.ts` — 보충적 평가액 합 0)가 맞는 문구로 400을 낸다. Pre-Do probe로 확인: 주택(의제취득일 기준시가 있음/없음)·토지 세 시료 모두 「[burdened_gift] 기준시가로 평가했는데 양도시 기준시가가 없습니다 … (「소득세법 시행령」 제159조 제1항 제2호)」. 시가 평가 시료는 종전 문구 그대로, 채운 시료 세액 9,936,000 그대로.

## 8. 범위 밖 · 확인 필요

- **이중 출처**: 모양 B에서 `generalBuildingValuation`과 `info`가 둘 다 0보다 크지만 서로 다르면 엔진은 `info`를 쓴다(실측: `info` 토지 1억 · `generalBuildingValuation` 토지 2억 → 기준시가 평가 세액 5,437,000). API 직접 호출에서만 생긴다. 한쪽을 다른 쪽에서 만들면 면적 소수에서 절사 차이가 날 수 있어(④는 `Math.floor`, 일반건물 경로는 절사 없음) 별건으로 둔다.
- **⑫ `:664` 문구**: 같은 1983 상속 기준시가 평가 시료에서 의제취득일 기준시가까지 빼고 보내면 「취득가액 원천이 필요합니다 — 상증법 평가액, §164④~⑦ 기준시가, 또는 환산(의제취득일 기준시가) 중 하나」가 뜬다. 기준시가 평가는 의제취득일 기준시가만 쓰므로(Q-25) 앞의 둘을 권하는 것이 부정확하다. API 직접 경로 문구라 이번에 고치지 않는다.
- **바닥면적 비움 → 일반 자산 경로**: 정상 입력이 일반건물 경로를 타지 않는다. 이번 시료는 세액이 같았지만, 일반건물 경로만 하는 일(부수토지 배율 판정 등)이 빠지는지는 확인 필요.
- 직전 계획서 §9 격자의 남은 「⑧ 막는데 200」 중 일반건물 시가 평가·1983 상속 시가 평가 행은 격자 probe가 지워져 다시 분류하지 못했다. 3.1 구현 후 격자를 다시 돌려 분류한다.
