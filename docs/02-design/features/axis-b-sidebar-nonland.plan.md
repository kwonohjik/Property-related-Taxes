## 1. 측정 (V 레지스터)

**V-1 계산 전 양도가액 — 폼 → 사이드바 → route** — 시료 5종(50/30/20·1/3×3·50/50·60/40·14.29×7 — 총액은 잔여가 생기게 골랐다). 사이드바 = `computeTransferPerAssetSummary(form, null)`, 서버 = route 200의 `apportionment.apportioned`(일반건물은 `#i` 접미사별 합).

| 종류 | 경로 | 잔여 있는 시료 | 계산 전 = 서버 |
|---|---|---|---|
| 일반건물 실가(§163⑨ 시료 `INH`)·환산(`S100-est`) | `generalBuildingShares` | 1/3×3 → 333,333,333·333,333,333·333,333,334 · 14.29×7 → 마지막 142,600,000 | 같다 |
| 재개발APT·입주권 | 컴패니언 | 위와 같은 값 | 같다 |
| 겸용(2지분) | 컴패니언 | 60/40 · 2,000,000,001 → 1,200,000,000·800,000,001 | 같다 |
| 건물·상가·분양권·주택 | 컴패니언 | 위와 같은 값 | 같다 |

- 부담부증여(일반건물·입주권)는 계산 전 전 자산 「계산 후 표시」다(설계대로). 계산 후는 엔진 값과 같다(일반건물 1/3×3: 66,666,666 ×3 · 입주권 동일).
- 겸용 × 부담부증여 축 B는 ⑧·⑫가 400으로 막는다.

**V-2 계산 후 일반건물 지분 × 일반 양도 (D-1)** — `computeTransferPerAssetSummary(form, route data)`:

| 시료 | 칸 | 사이드바(계산 후) | 엔진 |
|---|---|---|---|
| 실가 1/3×3 · 10억 | 양도가액 | 333,333,333 ×3 → **999,999,999** | …·…·333,333,334 → 10억 |
| 실가 14.29×7 · 10억 | 양도가액 | 142,900,000 ×7 → **1,000,300,000** | …(6개)·142,600,000 → 10억 |
| 실가 60/40 · 2,000,000,001 | 양도가액 | 1,200,000,000·**800,000,000** | …·800,000,001 |
| 실가 1/3×3 · 10억 | 취득가액 | **0** ×3 | 150,000,000 ×3 |
| 환산 60/40 · 2,000,000,001 | 취득가액 | **0**·**0** | 339,333,422·226,222,280 |
| 환산 60/40 · 2,000,000,001 | 필요경비 | **0**·**0** | 4,790,604·3,193,736 |
| `SWAP` 시료 60/40 · 2,000,000,001 | 필요경비 | **306,000,000·204,000,000** | 4,790,604·3,193,736(이 총액에서는 단서 미발동) |
| `SWAP` 시료 1/3×3 · 10억 | 필요경비 | 170,000,000 ×3 | 169,999,999 ×3(단서 발동) |

- 원인(코드): 엔진 행 id가 `land#0`·`building#0`이라 `bundledMatch`(폼 id)가 실패한다(`transfer-per-asset-summary.ts:200`). `bundledCards`는 단건 전용(`:215-216`), `gbShareBgCards`는 부담부증여 전용(`:232-233`), `apportionedMap`은 계산 전 전용(`:130`)이라 **`:297-299`의 floor 폴백**과 입력값 분기로 떨어진다. `:230-231` 주석이 «비부담부증여 지분 행은 종전 그대로»라고 남긴 그 구간이다.
- 해법 근거: 지분별 카드 합(`apportioned`의 취득·경비)이 집계 값(`aggregated.properties`)과 측정한 시료에서 전부 같다(실가·환산·`SWAP`). 부담부증여 조건만 걷으면 같은 합을 읽는다.
- 도달 경로: 결과 화면의 「이전」은 `setStep`만 부르고 결과를 지우지 않으므로(`TransferTaxCalculator.tsx`) 입력 단계로 돌아오면 사이드바가 `result`를 그대로 받는다 — **코드로 읽은 것이고 브라우저로는 확인하지 않았다(확인 필요)**.

**V-3 일반건물 지분 경로의 흡수 규칙**

| 시료 | 사이드바(계산 전) | 일반건물 서버(마지막 위치) | 컴패니언 서버(공유 함수) |
|---|---|---|---|
| 1/3×3 · assetId `Z`·`M`·`A` | 333,333,333·**333,333,334**·333,333,333 | 333,333,333·333,333,333·**333,333,334** | 사이드바와 같다 |
| 99/1 · 총액 50 | **50**·**0** | 49·1 | 400(`fixedSalePrice` > 0 위반) |

- 화면 폼의 id는 `asset-${Date.now()}-${index}`(`calc-wizard-asset-factory.ts:89`)이고 자산은 하나씩 뒤에 붙으며(`CompanionAssetsSection.tsx:97-98`) 순서를 바꾸는 UI를 찾지 못했다 — 사전순 최대 = 마지막 위치. **코드로 읽은 것이다.** 이력 복원·구 세션 id는 재지 않았다.
- 세액: 흡수 자산이 바뀌면 1원이 다른 지분으로 옮겨 가지만, 서버는 사이드바 값을 쓰지 않으므로 서버 세액은 그대로다. id 역순 시료의 서버 세액은 정순과 같다(실가 139,766,000 · 환산 187,645,782).

**V-4 🔴 동순위 묶음 전체 순열 — 메모리 고갈 (D-2, 이 항목과 별건)** — `pickFavorableTieRank`(`transfer-tax-aggregate-helpers.ts:580`)가 `TIE_CANDIDATE_LIMIT`(24) 검사 **전에** `permutations(g)`를 만든다. 순열은 묶음 크기의 계승이다. route POST 1회 실측(묶음 크기는 이 함수를 감싸 기록):

| 입력 | 묶음 크기 | 결과 |
|---|---|---|

| 토지 축 B 9건 | 9 | 200 · 166ms |
| 토지 축 B 10건 | 10 | 200 · 2,185ms |
| 토지 축 B 11건(9.09×11 — ⑧ 통과, 서버 상한 11건) | 11 | **프로세스 사망**(heap 2GB: `JavaScript heap out of memory`) |

- 겸용 3건 시료는 ⑧에 부수토지 배율 안내가 남아 있어 **⑧까지 통과한 폼으로는 재지 않았다**(확인 필요). 토지 11건은 ⑧ 통과. 토지 11건을 기본 heap으로, 운영 환경(서버리스 메모리·타임아웃)에서는 재지 않았다.
- 겸용 3건은 이 고갈 때문에 V-1·V-2 수치를 얻지 못했다.

## 2. 결정 요청 (Q 레지스터)

**Q-1 일반건물 지분 × 일반 양도의 계산 후 값 (D-1)** — a) 그대로 둔다. **b) `gbShareBgCards`의 부담부증여 조건을 걷어 전 일반건물 지분이 카드 합을 읽게 한다(권장).** c) 집계 `properties`를 새로 합산하는 분기를 추가한다.
- b 근거: 같은 합을 읽는 기존 분기(`:279`·`:377`·`:529`)가 이미 있고 V-2에서 값이 집계와 같다. 양도가액 분기만 부담부증여 안쪽(`:279`)에 있으므로 일반 경로에도 한 줄 필요하다.

**Q-2 (②와 공통) `FractionalAutoSalePriceCard`와 사이드바가 같은 흡수 헬퍼를 쓰는가** — **a) 같은 헬퍼 `absorbFractionalResidual`을 쓴다(권장).** b) 카드는 라벨대로 floor를 유지한다. c) 카드에 별도 규칙을 둔다.
- a 근거: 두 화면이 다른 숫자를 보이면 #2802가 없앤 불일치가 되살아난다. 세 번째 복사(c)는 다음 변경에서 다시 어긋난다.

**Q-3 일반건물 지분 경로의 위치 기반 흡수** — **a) 유지하고 기록만 남긴다(권장).** b) 서버도 `absorbFractionalResidual`을 쓴다(`shareId` = assetId라 가능). c) 일반건물만 사이드바를 위치 기반으로 바꾼다.
- a 근거: 현실 입력에서 갈리지 않고(V-3 — 코드로 읽음) 1원 차이의 귀속에 법적 정답이 없다(엔진 규약). b는 서버 세액 경로를 건드린다.

**Q-4 🔴 순열 메모리 고갈 (D-2)** — **a) 이 계획서와 분리한 별건 PR로, ①·②보다 먼저 고친다(권장).** b) 이 PR에 묶는다. c) ⑧·⑫로 건수를 더 제한한다.
- a 근거: 사이드바와 무관한 엔진 결함이고 계산이 아예 끝나지 않는다. c는 지금 가능한 입력을 막는다.

**Q-5 청산금 수령 단독 × 축 B (V-5)** — **a) 이번 범위에서 제외하고 별건으로 측정한다(권장).** b) 이번에 함께 조사한다.
