### 0-2. "정산"의 본질 — 개념 정정
교재 챕터 4·5에 따르면 §41의3의 "정산"은 **사후 재평가·경정청구가 아니다**. 구조는:

> 당초 증여 시점(비상장)에는 상장이익을 알 수 없으므로 **당초 증여일을 증여시기로 보되**(증여세 신고는 일단 보류), 상장 후 **정산기준일(상장일+3개월)** 의 평가가액으로 이익을 확정하여 증여세 과세표준·세액을 **정산**(당초 증여세 과세가액에 상장이익을 가산)한다. 정산기준일 가액이 당초보다 하락(평가손실)하고 차액이 기준 이상이면 당초 납부세액을 **환급**한다.

즉 보완의 본질은 ① **평가손실(환급) 방향** ② **합산배제증여재산 본세 특례**(§47①·§55①) ③ **정산세액 표현**이다. 현행 엔진은 이미 "정산기준일 기준 증여이익"을 계산하므로, **정산기준일 가액을 다시 추정하는 사후 재평가 루프는 불필요**(에이전트 1차 보고의 "정산기준일 재평가 인터페이스"는 과설계 — 폐기). 단 ⓐ 평가손실 환급 ⓑ 전환사채 미전환 시 환급(§41의3⑧)은 정산기준일 기준 계산의 **결과 분기**로서 별도 처리한다(재평가 루프와 무관).

> **§41의5 합병상장이익 동시 적용**: 본 보완(환급·합산배제·자동화)은 `eventType="merger"`(§41의5)에도 **동일 적용**한다. 엔진은 단일 함수(`calcListingGainGift`)이므로 분기 비용 없음. §41의5가 §47① 합산배제증여재산에 포함되는지는 §6 KoreanLaw TODO로 검증(교재 챕터 8은 "주식 상장 등에 따른 증여이익"으로 §41의3·§41의5 묶어 합산배제 기술).

## 2. 구현 항목 (우선순위별)

### P0 — 정산의 본질 (필수)

#### A. 환급(평가손실) 방향 — 엔진 `listing-gain.ts`
- 현행: `gain = max(perShareGain × shares, 0)` → 음수면 0.
- 보완: `loss = (B+C) − A`(=−perShareGain×shares)가 양수이고 `loss ≥ threshold`이면 **환급 대상**.
- 결과 타입 확장: `DeemedGiftResult`에 `direction?: "taxation" | "refund" | "none"`, `refundBase?: number`(평가손실 환급 대상액) echo.
  - `direction="refund"` 시 `deemedGiftValue = 0`(증여 아님), `refundBase = loss`.
- threshold는 과세·환급 동일: `Min((B+C)×30%, 3억)`(현행 식 유지).
- 입력 변경 없음(같은 4필드로 부호 판정).

#### B+C+D(통합). 합산배제증여재산 본세 특례 — `gift-tax.ts` + `EstateItem`
세 갭(챕터 1·7·10)은 본세 파이프라인 **단일 분기**로 해결한다. `EstateItem`(또는 `GiftTaxInput`)에 `isAggregationExcludedGift?: boolean`(§41의3 등 합산배제재산 표식) 도입:

- **STEP 3(§47② 합산)**: 합산배제재산 가액은 `priorAggregation` 합산 대상에서 제외 + 10년 합산(`priorGiftsWithin10Years`)과 **격리**된 별도 과세표준 산정.
- **STEP 4(§53 증여재산공제)**: 합산배제재산에는 §53·§53의2·§54 공제 **미적용** — 근거 **§55①3호**(검증✅): 합산배제증여재산 과세표준은 「증여재산가액 − 3천만원」(− 감정평가수수료). §53·§53의2·§54 공제는 **§55①4호(그 외)** 전용. 명문 호 분리이므로 납세자 불리 적용 아님.
- **STEP 5(§55①3호 과세표준)**: 합산배제재산 과세표준 = `증여이익 − 감정평가수수료 − 30,000,000`(3천만원 상수). 음수 가드.

- **구현 방식 (실측 정정 2026-06-25)**: 기존 2-stream(`gift-tax.ts:431` `partitionGiftItems` + `calcSpecialTreatmentStream`)은 **조특법 특례(§30의5·6 창업/가업) 전용** — 저율(10/20%)·한도 분리과세이므로 §41의3에 **직접 재사용 불가**. 합산배제증여재산은 **일반세율(§56)** + §55① 3천만원 + §53 배제 + 10년합산 격리. → **partition 패턴(`isSpecialTreatmentAsset` 같은 플래그로 분류)만 차용**하고, 합산배제재산 전용 처리(일반세율 적용·3천만원 공제·§53 배제)를 신규 추가. 기존 조특법 스트림과는 **제3의 분기**로 공존.
- 🔴 **회귀 위험(High)**: `isAggregationExcludedGift` 분기는 §41의2 초과배당·§42의3 등 **다른 합산배제 deemed 재산의 본세 연계에도 영향**. 플래그 **OFF 시 현행 100% 동일** 가드 필수 + 기존 deemed 본세 경로(prefill→calcGiftTax) 전수 회귀. 플래그 도입 전 현행 증여세 전체 테스트 baseline 캡처.

- **환급 방향 본세 연계(갭 #5)**: `direction="refund"`는 증여세 산출이 아니라 **당초 납부 증여세액 환급**이므로, 일반 prefill→calcGiftTax(증여이익 과세) 경로와 **별개**. 환급 케이스는 본세 마법사로 넘기지 않고 결과뷰에서 "환급 대상액(평가손실 × 세율 상당) — 당초 신고분 경정청구 안내"로 분리 표시. (정산세액 = 정산 증여세 − 당초 증여세, 음수=환급)

## 5. 설계 결정 필요 (사용자/Plan 확인)

1. **합산배제 본세 구현 방식 (실측 후 좁혀짐)**: 기존 2-stream은 조특법 특례 전용이라 재사용 불가 확정. → partition 패턴 차용 + 합산배제재산 전용 분기 신규. 남은 결정: 신규 분기를 `gift-tax.ts` 인라인 vs 별도 헬퍼(`calcAggregationExcludedStream`) 분리(800줄 정책·테스트 격리상 후자 권장).
2. **평가 자동화 범위(F)**: 정산기준일 §63 종가평균을 키움 API로 자동 조회할지, 직접입력 유지할지. 1차는 직접입력 + 할증 토글 권장.
3. **챕터 9·10·11 구현 깊이**: 계산 영향(전환사채 간주) vs 순수 안내. P2는 안내 카드로 최소 구현 권장.
