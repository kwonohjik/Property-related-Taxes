### 2.2 원인

- 전체 누진이 이기면 감면 단계에 `perClause`를 넘기지 않는다(`lib/tax-engine/transfer-tax-aggregate-reduction-step.ts:576`). 그러면 C는 `basicOnReducibleOf`(`:307-308`)의 자산 단위 식이다:

- 차손 300,000,000이 건물 파트(같은 세율군)에 닿아 통산 후 소득(870,000,000)이 B(건물 감면소득, 통산 전 1,120,000,000)보다 작아진다. 그러면 「감면 외 소득」이 0으로 계산돼 C = 2,500,000이 된다.
  실제로는 파트 안 배분이 감면 제외 토지 파트에 공제를 줬다.
- 호별 경로는 같은 문제를 리뷰 #3에서 `reductionAttributionOf`(`:118-134`, 감면 파트가 세액 계산에서 받은 기본공제)로 고쳤다. 전체 누진 경로에는 그 수정이 닿지 않았다.

> ⚠️ **③과의 관계** — B가 받은 차손만큼 줄지 않는 것(§77 세액감면형, 별건 ③)이 이 불일치를 드러나게 한다. F-A는 ③의 결론과 무관하게 맞다. 파트 귀속 C는 공제가 실제로 붙은 파트를 읽기 때문이다. ③이 「B를 줄인다」로 결정돼도 F-A·F-B의 값은 바뀌지 않는다(**확인 필요** — ③ 시험 시 함께 잴 것).

## 4. ① 수정안

### 4.1 F-A — 전체 누진 경로의 C를 파트 귀속으로

`basicOnReducibleOf`가 split 자산이고 §77 `partWise`(감면 파트 확정)이면, 그 자산의 C를 **감면 파트가 세액 계산에서 받은 기본공제**(`assetPartBasic`의 감면 파트 종류 합)로 읽는다. 호별 경로 `reductionAttributionOf().basic`과 **같은 leaf**를 쓴다(신설 `reducedPartBasicOf`).
`assetPartBasic`는 이미 `computeGroupsAndComparison`이 돌려준다(`transfer-tax-aggregate.ts:308`). 감면 단계 `base`(`:311`)에 실어 보내면 된다.

### 4.2 F-B — split 파트를 M-4 배분 단위로

1. **파트 소득 leaf** — `evaluateSplitPartTax`(`transfer-tax-split-rate.ts:217`)의 앞부분(시드 → 소득 안분 `:234-245` → 1차 세율 `:248` → 게이트 7 `:263`)을 `splitPartBasicUnits(ctx)`로 뽑는다. 세액 계산도 이 함수를 거친다(단일 소스). 게이트에 걸리면 `null` → 자산 한 행 유지.
2. **외부 배분 주입** — `SplitPartRateContext`에 `partBasicDeduction?: number[]`. 주면 `:269-277`의 파트 안 배분 대신 그 값을 쓴다. 불변식(`:281` Σ과세표준 = 자산 과세표준)은 그대로 지킨다.
3. **M-4 펼침** — `EARLIEST_TRANSFER` 축에서만:
   - 대상: `splitDetail`이 있고 §155⑳ 특례 미적용이며, (감면 없음) 또는 (§77 `partWise`).
   - 행: 파트마다 `{income: 파트 소득, rate: 파트 1차 세율, reducibleIncome: 감면 파트만 자산 B, reducibleBuckets: 감면 파트만 자산 버킷}`.
   - 같은 날 동순위·감면율 묶음(`sameDayTieGroups`·`sameDayReducibleRateGroups`)과 후보 평가(`pickFavorableTieRank`)는 행 단위로 그대로 돈다.

### 6.2 시험 패치 세 가지

- **LO** — 부동산 어댑터 `offsetLosses`(`transfer-tax-aggregate-helpers.ts:221`)에서 코어 입력 행을 propertyId → 파트 순으로 정렬해 넘기고, 결과를 원래 인덱스로 되돌렸다. 코어 무변경.
- **LR** — 코어의 두 이익 측 배분(같은 세율군 `:108-114` · 타군 `:151-156`)을 최대잉여법으로 바꿨다. 몫을 floor한 뒤 남은 원을 소수부가 큰 자산부터 1원씩 준다(동률은 인덱스 순). 차손 측 귀속(통산 표의 「어느 차손에서」)은 그대로다.
- **LR+LO** — 둘 다.

| 변형 | 3건 3,584 순서 갈림 (split / 분리) | 감면 3건 2,688 순서 갈림 | 바뀐 행(3건) | 교재 사례 33 | 엔진 테스트 실패 |
|---|---|---:|---:|---|---|
| 현행 | 391 / 395 | 232 | — | 통과 | 0 |
| LO | 0 / 0 | 0 | 510 (≤3원) | **실패 3** (T-19 2,336,343 · T-20 48,791,666 · T-21 4,712,302 — 예제에서 멀어짐) | 4 (C-13-2 + 사례 33) |
| LR | 0 / **4** | **4** | 622 (≤3원) | 통과 | 7 (C-5·C-10·C-12 · anchor A-3·A-5) |
| **LR+LO** | **0 / 0** | **0** | 622 (≤3원) | 통과 | 8 (위 7 + C-13-2) |

- **사례 33이 가르는 이유**: 건물2의 몫 7,048,645 × 26,527,095 / 80,031,063 = 2,336,343.77이다.
  - 현행은 건물2가 입력상 마지막이라 잔액 1원을 받아 예제값 2,336,344와 우연히 맞는다.
  - LO는 건물2를 앞으로 보내 floor 값 2,336,343이 된다.
  - LR은 소수부(0.77 > 토지 0.23)로 건물2에 준다. 입력 순서와 무관하게 예제값이 나온다.
- **LR만으로 남는 4행**: 소수부가 같은 동률이 인덱스 순으로 갈린다. LO가 동률 순서를 propertyId로 고정해 없앤다.
- 실패 8건은 모두 「잔액은 마지막 자산」을 고정한 characterization(`transfer-tax-loss-offset-characterization.test.ts` C-5-2·C-5-3·C-10-1·C-10-2·C-12-2·C-13-2)과 1원 단위 anchor(`loss-offset-same-rate-axis.predo.anchor.test.ts` A-3·A-5)다. 세율 축·통산 순서 규칙을 바꾼 것이 아니라 잔액 1원의 위치가 바뀐 것이다. Do-3에서 건마다 새 값의 손계산을 주석에 남기고 갱신한다.
- **주식**: LR은 공유 코어를 고치므로 주식 다종목 통산도 바뀐다. 시험 패치 상태에서 `__tests__/tax-engine/` 주식 테스트는 실패 0이었다. 주식 격자 실측은 하지 않았다(Do-3에서 잴 것).
- **부수 효과**: split과 분리 신고의 ≤3원 차이가 4행 → 8행이 된다(>3원은 ①-a 4행 그대로). 두 신고의 propertyId 집합(P vs L·B)이 달라 동률 순서가 다르기 때문이다. 입력 순서 무관을 얻는 대신 「split = 분리 신고」 1원 단위 일치는 보장하지 않는다.
