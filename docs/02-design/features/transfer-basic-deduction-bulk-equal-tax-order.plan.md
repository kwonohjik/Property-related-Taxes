# 일괄양도 기본공제 — 세액이 같을 때의 배분 순서(한계세율 → 자산 번호) — v1.0

작성 2026-10-16 · 선행 PR #2220(같은 날 양도 동순위 — 유리한 순서 · 계획서 `transfer-basic-deduction-same-day-tie.plan.md`)

> **표기 규약** — 이하 **§**는 「소득세법」을 가리킨다.

> **📌 요약**
>
> 일괄양도(한 계약으로 주 자산 + 함께 양도 자산)는 모든 자산의 양도일이 같다. 그래서 기본공제 순서는 #2220이 정한
> 「같은 날 양도 — 납세자에게 유리한 순서(재일46014-1685)」로 정해진다. 그런데 **어느 자산에 공제해도 세액이 같으면**
> 마지막 기준이 `propertyId` 사전순이다. 일괄양도의 id는 다음과 같아서 결과가 화면 순서와 어긋난다.
>
> - 주 자산 id는 `"primary"`, 함께 양도 자산 id는 `asset-<생성 시각>-<n>`(`lib/stores/calc-wizard-asset-factory.ts:86`)이다.
>   사전순으로 **`asset-…` < `primary`**라서 세액이 같으면 **주 자산이 공제를 받지 못한다**.
> - 함께 양도 자산끼리는 **생성 시각** 순이다. 자산을 지우고 다시 추가하면 화면의 자산 번호와 공제 순서가 달라진다.
>
> **사용자 결정(2026-10-16)**: 일괄양도에서 세액이 같으면 **한계세율이 높은 자산 → 자산 번호 순**으로 정한다.

## 1. 근거와 위치

### 1.1 법령·해석례

- §103②은 같은 날 양도한 자산 사이의 순서를 정하지 않는다. #2220이 그 자리를 재일46014-1685(「납세자에게 유리하다고
  판단되는 양도자산의 양도소득금액에서부터」)로 채웠다(계획서 §1.2).
- **세액이 같은 후보 사이**에는 유리·불리가 없다. 이 자리에는 법령·해석례 기준이 없고 계산기의 **결정적 표시 규약**만 필요하다.
  이번 변경은 그 규약을 바꾸는 것이다. 바꿔도 **총 부담(`totalTax`)·결정세액은 바뀌지 않는다.**
  유리 판정이 먼저 이 두 값을 최소로 고정하고, 그 안에서만 고르기 때문이다(§4 실측 7건 모두 같음).
- 바뀌는 것은 다음 **귀속 표시**다.
  - 자산별 배분 기본공제·과세표준 몫
  - 자산별 결정세액 몫
  - 세율군 카드(세율군이 갈리는 경우)
  - 별지84 자산별 기본공제

### 1.2 기존 결정과의 관계

| 결정 | 이번 계획 |
|---|---|
| #2220 Q-1 유리 판정 = 총 부담 → 결정세액 → `propertyId` | 앞의 두 단계는 그대로 둔다. **일괄양도만** 세 번째 단계를 「한계세율 ↓ → 자산 번호 ↑」로 바꾼다 |
| #2220 Q-3 「입력 순서와 무관하게」 | 다건 합산(`/api/calc/transfer/multi`)은 그대로 둔다(§5 Q-1). 일괄양도의 자산 번호는 사용자가 정한 화면 순서이고, 주 자산은 항상 자산 1이다 |
| PR #1645 「다건에 높은 세율 우선을 기본값으로 되살리지 않는다」 | 충돌하지 않는다. 양도일 순서·감면 외 우선·유리 판정은 그대로 두고, **세액이 같은 후보 사이**에서만 한계세율을 쓴다 |
| §133 감면 한도 vs 0893(2026-10-16 사용자 결정, 미구현) | 범위 밖(별건) |

## 3. 설계

### D-1. 세 번째 기준을 호출측이 고르게 한다

- `AggregateTransferInput`에 선택 필드를 신설한다.
  - `sameDayEqualTaxOrder?: "propertyId" | "marginalRateThenAssetNumber"`
  - 기본값은 `"propertyId"`다. 다건 합산과 기존 호출은 동작이 바뀌지 않는다.
- `pickFavorableTieRank`의 두 번째 인자를 `idOf`에서 **비교 함수** `order(a, b)`로 바꾼다. 후보 나열 순서가 곧 세액 동순위 순서다.
  - `"propertyId"`: 종전 `byId`(propertyId 사전순 → idx)
  - `"marginalRateThenAssetNumber"`: `appliedRate` 내림차순 → idx 오름차순
- 유리 판정(총 부담 → 결정세액, 엄격 비교)과 후보 상한 24·상한 초과 시 「첫째 자산만 바꾸기」는 그대로 둔다. 상한 초과 시 남는 순서를 채우는 기준도 이 `order`를 따른다.

### D-2. 일괄양도 경로만 켠다

- `app/api/calc/transfer/route.ts:481` `aggregateInput`에 `sameDayEqualTaxOrder: "marginalRateThenAssetNumber"`를 넣는다.
- 같은 입력을 펼쳐 쓰는 두 번째 호출(`aggregateWithSameDayRightWarning`의 `{ ...aggregateInput, properties: heldItems }`)도 자동으로 이어받는다.
- 집계 공개 진입점(이월과세 A/B 비교로 여러 번 도는 경로)이 입력을 그대로 넘기는지는 Do에서 route anchor로 확인한다.
- 서버가 조립하는 엔진 입력이라 폼·Zod·④⑬은 해당 없다. **14 동기화 지점 신설 없음.**

### D-3. 「한계세율」의 정의

- 자산 단독 계산의 **적용세율 `appliedRate`**를 쓴다. 종전에 `tieRank`가 없을 때 쓰던 기본 순서(`eligibleForBasic[].rate`)와 같은 필드다.
- 기본세율 자산은 단독 과세표준이 속한 구간의 세율이다. 실측: 20억 주택 0.38, 3억 토지 0.35.
- 다른 정의(합산 후 세율군의 한계세율)를 쓰면 같은 세율군 자산이 모두 같은 값이 되어 사실상 자산 번호 순이 된다(§5 Q-2).

### D-4. 표시

- 계산 과정 「기본공제」 문구(「같은 날 양도 — 납세자에게 유리한 순서(재일46014-1685)」)는 그대로 둔다(§5 Q-3).
- 자산별 배분·세율군 카드·신고서·PDF는 모두 `allocatedBasic`을 읽으므로 손대지 않는다.

### D-5. 손대지 않는 것

- 다건 합산의 동순위 기준(`propertyId`)
- 양도일 순서·감면 외 우선·0893 감면율 순
- 파트 축(`PARTS_HIGHEST_RATE`)
- §133 감면 한도 연동(별건)

## 5. 결정 필요

| # | 질문 | 권고 |
|---|---|---|
| Q-1 | 다건 합산(`multi`)에도 같은 규칙을 적용할지 | **적용하지 않는다.** 지시 범위가 일괄양도다. 다건은 저장된 건별 계산을 모은 목록이라 순번이 사용자의 「자산 번호」라는 보장이 약하다. #2220 Q-3(입력 순서와 무관)을 유지한다 |
