## 0. 결론 먼저

**구현 가능하다. 그리고 종전 진단보다 훨씬 싸다.**

종전 기록은 「일괄 분기가 §159 안분(STEP 0.48)을 타지 않으므로 **aggregate 경로에서 §159를
돌리는 재설계**가 필요하다」였다. 실측 결과 **그 재설계는 이미 되어 있다** —
`transfer-tax-aggregate.ts:174`가 카드를 **통째로 spread**해 단건 엔진을 부른다:

```ts
const perAsset = input.properties.map((item, assetIdx) => {
  const singleInput: TransferTaxInput = {
    ...(item as unknown as TransferTaxInput),   // ← burdenedGiftInfo·ownershipRatio도 함께 넘어간다
    annualBasicDeductionUsed: 0,
    skipBasicDeduction: true,
    ...
```

⇒ 카드에 `burdenedGiftInfo` + `ownershipRatio`가 실리기만 하면 **STEP 0.48이 카드마다 돈다**.
엔진은 한 줄도 고칠 필요가 없다.

**단, 축 A와 정반대의 채무 규약이 필요하고(§2), 함정이 둘 있다(§4).**

## 2. 규약 — 축 B에서는 **채무도 안분**한다 (축 A와 반대)

### 2.1 왜 축 A 규약을 쓰면 깨지는가

§159①1호는 `양도가액 = A × B/C`이고 **B/C(채무비율)는 물건 단위 하나**다.
`scaleBurdenedGiftInfo`는 A·C(평가액·기준시가)만 줄이고 **B(채무)는 그대로** 둔다 —
축 A에서는 그것이 옳다(§2.2). 그런데 축 B에서 그대로 쓰면:

| 카드 | A(평가액) | C = max(보충적, 담보) | B(채무) | B/C |
|---|---|---|---|---|
| 60% | 6억 | max(6억, **6억**) = 6억 | **6억** | **1.0** 🔴 (정답 0.6) |
| 40% | 4억 | max(4억, **6억**) = 6억 | **6억** | **1.5** 🔴 |

담보평가 항이 **절대금액**이라 지분에 따라 줄지 않아 C가 채무로 clamp되고, B/C가 1을 넘는다.
그 결과가 위 표의 187,374,000원이다.

⇒ **채무·보증금·임대료·저당설정액도 ×지분율**로 안분해야 B/C가 보존된다.

### 2.2 왜 축 A와 반대여도 모순이 아닌가

| | 축 A — 공유 소유 | 축 B — 지분 분할 취득 |
|---|---|---|
| 증여계약 | 공유자마다 **별개** | 갑 한 사람의 **하나** |
| tranche의 실체 | 실제 소유 지분(타인 지분 존재) | **세법상 계산 단위일 뿐**(전부 갑의 것) |
| 채무 인수액 | 계약마다 당사자가 정한다 ⇒ **사실** | 하나의 계약에 하나 ⇒ **산식이 안분을 요구** |
| 처리 | 사용자가 지분 인수분 입력 · 스케일 X | 물건 전체 입력 · **엔진/변환이 ×지분율** |

축 B의 안분은 **자동 안분 fallback이 아니다** — 「미입력을 시스템이 추정」하는 것이 아니라
「하나의 값을 §159 산식이 요구하는 계산 단위로 나누는 것」이다. `feedback_no_silent_apportion_fallback`이
막는 것은 전자다.

> 🔴 **같은 필드가 축에 따라 반대로 처리된다.** `feedback_rename_same_name_two_axes`의 사례이므로
> **전역 치환·공통 헬퍼 통합을 하지 말 것**. 축 판정을 인자로 받는 형태여야 한다.

### 2.3 안분을 **어디서** 하는가 — ④ 권장

④ API 변환에서 카드를 만들 때 채무 4필드에 `applyRatio`를 미리 적용하고, `ownershipRatio`는
그대로 실어 보낸다.

- 엔진 `scaleBurdenedGiftInfo`는 채무를 건드리지 않으므로 **이중 적용이 없다**.
- 엔진의 계약(「카드가 준 채무를 그대로 쓴다」)이 그대로 유지된다 — 축 파라미터를 엔진에
  들일 필요가 없다.
- 축 판정(`isFullFractionalBundle`)은 ④가 이미 알고 있다.

> ✅ 12억 고가주택 판정은 자동으로 맞는다 — `wholePropertySupplementary`는 **`rawInfo`**(스케일 전
> 기준시가)를 보는데, ④가 미리 곱하는 것은 **채무뿐**이라 기준시가는 물건 전체로 남는다.

## 4. 함정 2건 — 착수 전 반드시 설계할 것

### 4.1 🔴 증여세가 카드 수만큼 쪼개진다 — 19,400,000원 과소

`buildBurdenedGiftBreakdown`은 `giftDate`가 있으면 증여세까지 계산한다.
카드마다 돌면 **증여재산공제(§53)가 N번 차감되고 누진세율이 쪼개진다**:

| | 증여세 과표 | 증여세 결정 |
|---|---|---|
| 단건 100% (정답) | 350,000,001 | **58,200,000** |
| 카드 합계(60% + 40%) | 190,000,000 + 110,000,000 = 300,000,000 | **38,800,000** 🔴 |

⇒ 증여세는 **물건 단위 1회**여야 한다. 두 방향:

| 안 | 방법 | 평가 |
|---|---|---|
| **(가)** | 카드에는 `giftDate`를 **주지 않고**(증여세 미계산), route가 **물건 전체 info로 1회** `buildBurdenedGiftBreakdown`을 불러 증여세만 취한다 | 권장 — 엔진 무변경 유지, 값이 단건과 동일함이 자명 |
| (나) | 첫 카드에만 `giftDate` | ❌ 그 카드의 base도 지분분이라 여전히 틀린다 |

### 4.2 🔴 UI 채무 라벨이 축을 구별하지 못한다

`RedevelopmentBlock`·`BurdenedGiftBlock`이 쓰는 `isFractionalOwnership(asset)`는
**축 A·축 B 모두에서 참**이다. 그래서 축 B에서도 「(지분 인수분)」 라벨이 뜨는데,
축 B의 채무 입력은 **물건 전체(100%)** 다 ⇒ **정반대의 안내**가 된다.

⇒ 축 판정을 `isFullFractionalBundle(form.assets)`로 갈라야 한다. 그런데 그 술어는
**폼 전체**를 봐야 하므로 자산-수준 블록에 **폼 컨텍스트를 내려야** 한다(현재는 asset만 받는다).

> 이 라벨 결함은 **축 B를 열지 않으면 발생하지 않는다** — 지금은 Gate-B가 조합 자체를 막는다.
> 즉 §4.2는 이 작업이 **새로 만드는** 요구사항이지 기존 결함이 아니다.

## 8. 범위 밖 → ✅ **공익수용도 같은 날 열렸다 (2026-09-03)**

착수 시점에는 「공익수용 × 축 B는 다루지 않는다 — 양도가액이 **보상가액**이라 구조가 다르고
지분 안분 정합을 재지 않았다」로 남겼다. **재보니 그 전제가 틀렸다.**

### 8.1 [실측] 양도가액은 **총계약가를 그대로 쓴다**

`transfer-tax-api.ts`의 `transferPrice` 삼항에 **수용 분기가 없다** —
`receiveOnly → 청산금 / 부담부증여 → placeholder / fractional → 총계약가 × 지분율 / else → 총계약가`.
즉 공익수용도 지분 모드에서 **총계약가 × 지분율**로 정상 처리된다.

보상 관련 필드는 §164⑨1호 **환산 분모** 전용이다:

| 트랙 | 분모 |
|---|---|
| per-sqm (토지·건물·상가·일반건물) | `min(기준시가㎡당, 보상㎡당, 보상기준㎡당) × 면적` |
| 총액 (주택) | `min(양도시 기준시가총액, 보상총액, 보상기준총액)` |

환산취득가 = `양도가액 × (취득시 기준시가 ÷ denominator)`이므로 **분모는 비율 성분**이고
분자와 **약분**된다 ⇒ **지분 스케일이 애초에 불필요**하다.
(재개발의 권리가액·청산금이 「절대금액이 취득가액에 직접 더해져」 스케일이 필요했던 것과 **정반대 성질**.)

### 8.2 [실측] 6케이스 전부 단건 100%와 **차익·세액 완전 일치**

취득일을 같게 둔 60% + 40% 2카드:

| 토지 (per-sqm) | `[perSqm, perSqm]` | ✅ 차익 597,000,000 · 세액 159,495,600 |
| 건물 (per-sqm) | `[perSqm, perSqm]` | ✅ 〃 |

### 8.4 🟡 §77의3(개발제한)은 **판별력 없이** 확인됐다
