## 0. 결론

| 질문 | 결과 |
|---|---|
| 0.5%p가 필요한 폭인가 | **아니다.** 허용 이유는 코드 주석(`transfer-tax-validate.ts:472`)이 «33.33×3=99.99 등 2자리 반올림 흡수»뿐인데, 균등 분할을 2자리 백분율로 입력할 때 반올림 오차는 최대 **0.03%p**(7분할 14.29×7=100.03), 지분 11건(서버 상한)의 이론 최대도 **0.055%p**다(V-2). 0.5%p는 그 9배 이상이다. |
| 대역 안에서 무슨 일이 생기나 | 합이 100%에서 벗어나도 ⑧이 통과시키고 서버는 **양도가액 합을 총액 100%로 고정**한다(편차는 흡수 자산이 받는다). 그런데 **취득가액·필요경비는 지분율대로 줄거나 늘어** 양도차익이 `편차 × 그 지분의 100% 기준 취득가액`만큼 어긋난다. 총 10억·취득 3억 시료: 합 99.5% → 양도차익 +150만원·**세액 +554,400원**, 합 100.4% → **−443,520원**(V-3). |
| 방향 | 합 < 100%면 세액이 늘고(불리) 합 > 100%면 줄어든다(유리) — 사용자 의도와 무관하게 편차 부호로 정해진다(V-3). 편차가 **어느 지분에 실렸는가**에 따라서도 달라진다(혼합 취득: 같은 −0.5%p가 +554,400 ↔ +436,590)(V-4). |
| 좁히면 | 허용 0(엄격)으로 3곳을 바꾼 시험 적용에서 전체 vitest 3642 파일 중 **#2790이 만든 anchor의 대역 기대 7건만** 깨지고 기존 테스트·E2E는 0건이다(V-6). 즉 이 폭에 기대는 기존 입력이 저장소 안에는 없다. |
| 한계 | 엄격(허용 0)은 UX 함정이 있다 — ⑧ 문구가 `toFixed(2)`라 33.333333×3(=99.9999%)이 «현재 100.00%»로 보이며 차단된다(V-7, 코드 읽기 · 실행 확인은 하지 않았다). |
