## 2. 문제 정의와 범위

### 2.1 «상태»란 무엇인가 — 법 §104의3①4호 가·나·다목은 날마다 따진다

기타토지는 «가·나·다목을 **제외한** 토지»가 비사업용이고, 그 판정 대상이 «소유하는 기간 중 영 §168의6 기간»이다. 따라서 날마다 («재산세 비과세·면제» ∨ «별도합산·분리과세» ∨ «다목 사업 관련») 여부가 바뀔 수 있다. 바뀌는 요소를 영 §168의11 각 호·지방세법 §106 기준으로 분해하면:

| 시간에 따라 바뀌는 요소 | 근거 | 현행 입력 | v1 이력 대상 |
|---|---|---|---|
| **건축물 유무**(신축·멸실·철거) | 지방세법 §106①2호가목(건축물 부속토지)·다목(철거·멸실) · 법 §104의3①4호나목 · 규칙 §83의5①9호 | `nblOtherHasBuilding` 토글 | **포함**(핵심) |

### 2.2 이번 모델이 다룰 것 / 뺄 것

**다룬다(v1)**: 기타토지(`other_land` 그룹)의 «건축물 유무 + 재산세 구분» 변화로 생기는 **전량 사업용 ↔ 전량 비사업용** 구간. 시나리오 = 철거 후 나대지 · 신축 직후 · 철거 후 재신축(사건 3개 이상) · 축 B 지분별 소유기간 상이.

**뺀다(v1)**:
- 부분 면적 안분 경로(배율 초과·공장 초과·2% 바닥면적·호별·연접·복합용도)의 시간축 — Q-4. 이력 입력 시 «이력은 부분 면적 판정에 반영되지 않음 — 확인 필요»를 고지.

- 별장 — 별장은 이미 «사용기간» 입력 모델(`usage_periods`)이 있고 농어촌주택 3요건은 양도일 속성이다.

## 3. 엔진 입력 모델 — 안 3개 비교와 추천

### 3.1 공통 전제 (모든 안에 적용)

- 구간은 `[start, end)` 반열린. 사건일 = **새 상태의 첫날**. 철거일은 규칙 §83의5①9호의 기산일(«멸실·철거된 날부터»)과 같은 날이라 직전 구간 `end` = 철거일, 9호 유예 구간 `start` = 철거일로 **경계가 맞는다**(중복·공백 없음).
- 소유기간 밖 구간은 `meetsPeriodCriteria`의 창이 잘라낸다(`getOwnershipStart` = 취득일 다음날, 초일불산입). 의제 양도일이 있으면 `getPeriodJudgmentDate`가 끝을 정한다.
- 날짜는 `lib/tax-engine/utc-date`와 `toOptionalDate`(매퍼에 이미 주입된 `parseDate`)만 쓴다 — 신규 코드 `new Date(x)` 금지(CLAUDE.md).
- 마지막 구간(양도일 현재 상태)은 **새로 받지 않는다.** 현행 `otherLand` 입력이 그대로 그 구간의 상태다. 이전 상태만 추가로 받으므로 하위호환이 구조적으로 보장된다.

### 3.2 (A) 상태 구간 배열 — `otherLandStatePeriods[{startDate, endDate, hasBuilding, propertyTaxType}]`

- 엔진에 가장 자연스럽다: `meetsPeriodCriteria`가 이미 `DateInterval[]`을 받고, 유예(`GracePeriod[]`)가 같은 모양이다. 겹침은 합집합이 되지만 **상태 구간의 겹침은 «같은 날 두 상태»라는 모순**이라 합집합으로 접으면 입력 순서가 아닌 값에 따라 유·불리가 갈린다 → ⑧·⑫에서 차단.
- 단점: 취득일·양도일을 다시 입력(중복) · 빈틈·겹침·첫/끝 불일치 오류 ≈8종 · 취득일 수정 후 연쇄 오류 · 축 B 지분 카드마다 «첫 구간 시작 = 취득일»이 달라진다(UI 문서 §3.1과 같은 평가).

### 3.3 (B) 사건 목록 — `[{kind: building_built | building_removed, date}]` (UI 안)

- 입력 부담 최소(라디오 1 + 날짜 1). 첫 사건 종류가 취득 당시 상태를 정해 «취득 당시 유무» 질문이 필요 없다. 지분 취득일 이전 사건은 replay로 접힌다.
- 엔진 관점의 한계: **사건만으로는 각 구간의 사업용 여부를 알 수 없다**(§3.4). 사건 종류가 늘면 «상태 기계(초기 상태 + 전이)»가 되어 순서 모순(멸실 뒤 멸실)을 ⑧이 잡아야 한다.

### 3.4 중대 발견 — 건축물 유무만으로는 «사업용 구간»이 정해지지 않는다

UI 문서 §3 공통 전제는 «구간의 사업용 여부 = 구간별 건축물 유무 + **현행 입력 칸**(재산세 분류·근거·…)»이다. 철거 후 나대지 시료로 따라가 보면:

1. 양도일 현재 입력은 보통 `hasBuilding=false` · `propertyTaxType=comprehensive`(나대지는 종합합산 — 현행 `isBareLand`·V1-A 규칙).
2. 철거 전 «건축물 있음» 구간을 같은 `propertyTaxType=comprehensive`로 평가하면 → 종합합산 → **비사업용**. 이력을 넣어도 구간 전체가 비사업용이라 A1의 과대(+55,750,000)가 **그대로 남는다.**
3. 반대로 «건축물 있던 구간 = 별도합산으로 간주»하면 사용자가 선언하지 않은 혜택을 엔진이 만든 것이다(2026-10-04 「모름 = 혜택 불성립」 · 「법 근거 없는 유리 적용 금지」 위반).

⇒ **건축물이 있던 구간의 재산세 구분은 사용자가 말해야 하는 사실**이다(재산세 고지서로 확인 가능한 사실 — 근거 모델 V1-A와 같은 «근거» 철학). 최소 보정: 사건 `building_removed` 행에 선택 칸 `propertyTaxTypeBefore`(그 철거 직전 구간의 재산세 구분: 비과세·면제 / 분리과세 / 별도합산 / 종합합산 / **미선택=모름**). `building_built` 사건 앞 구간(나대지)은 종합합산으로 둔다 — 근거 없는 비종합합산 선언은 종합합산으로 접는 기존 규칙(V1-A)과 일치하고, 그 구간에서 공지상태 별도합산 등을 주장하려면 후속(E3)에서 칸을 연다(V-6).

- 참고: 양도일 현재 입력에서 «별도합산 + 근거 = 철거ㆍ멸실»을 고르면(D2 `property-tax-basis.ts` `demolished`) 마지막 구간 자체가 종전 바닥면적 × 영 §101② 배율 범위만 사업용(한시 지위 미판정)으로 core가 판정한다 — 이는 «철거 후 별도합산 지위»를 양도일 상태로 주장하는 별개 경로이고, 이 계획의 이전 구간(철거 **전** 건축물 구간)과 겹치지 않는다. 두 경로를 함께 쓰면 부분 면적이 생길 수 있어 Q-4 (가)에 따라 이력 미반영 + 고지다.
- 별도합산·비과세·분리과세로 선언된 «건축물 있음» 구간의 배율·2% 요건은 구간별로 재판정하지 않는다(건축물 바닥면적·시가표준액 이력이 없다) → «배율 이내를 전제로 함 — 확인 필요» 고지(V-5). 현행 V1-A 표의 «별도합산 + 건축물 유 → 근거를 묻지 않음»과 같은 취급이다.

## 4. 판정 산식

### 4.1 흐름 (우선순위)

```
judgeNonBusinessLand
 ├─ Step 2 무조건 사업용 의제(§168의14③)      → 성립하면 즉시 사업용 — 이력 무관(기존 순서 유지)
 └─ Step 3 judgeOtherLand
      ├─ core(judgeOtherLandCore)               → 양도일 현재 상태 판정(= 마지막 구간). 기존 fullPeriod 호출은 무변경
      │    └─ DM-01(judgeRevenueBusinessStart)  → landStateHistory.mode='changed'이면 건너뜀(이력이 정본 — Q-5)
      └─ 후처리 1개: applyStateHistory(result, input, rules)   ← 신규 leaf
           · 이력 없음/unchanged/unknown/부분 면적/양도일 의제 동시 → 아무것도 안 바꿈(+고지) → 기존 applyGraceToNonBusinessRemainder 경로
           · 전량 사업용 또는 전량 비사업용 → 아래 4.2
```

### 4.2 산식

입력: core 결과(전량 사업용 `B` / 전량 비사업용 `N`) · `intervals`(이전 구간들) · 마지막 구간 `tail = [마지막 사건일, 의제양도일)` · 유예.

1. `pastBusiness` = `intervals` 중 `business(구간)`인 것: `hasBuilding=true ∧ propertyTaxType ∈ {exempt, special_sum, separate}` → 가·나목 해당 → 사업용. `hasBuilding=false`(나대지) 또는 `propertyTaxType ∈ {comprehensive, unknown}` → 비사업용.
2. `tailBusiness` = (core 결과가 `B`이면 `tail`, 아니면 없음).
3. `businessIntervals = pastBusiness ∪ tailBusiness`.
4. `r = meetsPeriodCriteria(businessIntervals, 취득일, 의제양도일, "other_land", rules, 유예)` — 유예는 합집합이라 이중 계상 없음(`period-criteria.ts` 헤더).
5. `r.meets` → 사업용, 아니면 비사업용(전량). 부호가 core 결과와 같으면 변화 없음, 다르면 `reason`·`steps`(`other_state_history`)·`appliedLaws`에 근거를 남기고 `areaProportioning` 제거(전량).
6. 기간 수치 echo는 «전 기간 사업용으로 채운 표시값»이 아니라 `r`의 실제 값(`effectiveBusinessDays`·`gracePeriodDays`·`ratio`·`criteria`)을 쓴다 — `applyGraceToNonBusinessRemainder`의 선례와 같다. `periodEvaluation.basis = "state_history"`.

이 한 산식이 §1.3의 네 시료를 전부 설명한다: A1(`pastBusiness`=건물 구간, core=N) · B1(`pastBusiness`=∅, core=B → `tail`만) · C1(후속).

### 4.4 하위호환 (이력 미입력 = 현행 + 고지 유지)

- `landStateHistory`가 `undefined`·`mode ∈ {"", unchanged, unknown}`이면 `applyStateHistory`는 즉시 반환한다 → 판정·세액·고지 문구 **바이트 동일**. 소비표 열을 추가해도 `other_land` 외 지목에는 `false`.
- ⑫ Zod는 새 칸을 전부 optional로 받고 `mode ""`을 400으로 막지 않는다(⑧이 더 엄격한 것은 허용 — 반대(⑫가 더 엄격)면 UI 통과 ↔ API 400 모순). 따라서 UI 문서 UQ-1(질문 필수)은 ⑧에서만 구현한다.
- 구 이력 복원(IndexedDB·sessionStorage): `calc-wizard-asset-migrate-nbl.ts`에 `nblOtherStateHistoryMode = ""`·`nblOtherStateEvents = []` 기본값(현행 `nblGracePeriods` 처리와 같은 모양, `calc-wizard-asset-migrate.ts:225`).

### 4.5 부분 면적 안분 경로 (Q-4)

배율 초과·공장 초과·2% 바닥면적·호별 기준면적·연접·복합용도 경로는 «면적 × 시간» 이중축이다. 각 구간의 사업용 면적이 달라질 수 있고(일부 철거·합필), 영 §168의6이 부분 면적에 어떻게 적용되는지 직접 근거를 확인하지 못했다(V-3). v1은 **반영하지 않는다**: `result.areaProportioning`의 비사업용 비율이 0과 1 사이면 `applyStateHistory`는 아무것도 바꾸지 않고 «이력은 부분 면적 판정에 반영되지 않았습니다 — 확인 필요» 고지만 더한다. 세액은 이력 입력 전후 동일(부분 경로는 현행 유지)이므로 새 과소·과대 경로가 열리지 않는다.
