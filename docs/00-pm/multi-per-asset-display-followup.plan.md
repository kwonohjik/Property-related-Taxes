## 1. ① 건별 `determinedTax` · PDF [직접]

### 1.1 코드 읽기

- 건별 `determinedTax`는 `transfer-tax-aggregate-once.ts`가 `r.result.determinedTax`(단건 엔진을 `skipBasicDeduction=true`로 부른 결과)를 그대로 싣는다 — 같은 파일의 `:537` 주석이 이 값을 «양도소득금액 기준 부정확»이라 적은 그 값이다.
- 소비처(비테스트): ① `lib/pdf/ResultPdfTransferSections.tsx:564`(PDF «결정세액 기여분 (참고)») ② `MultiTransferTaxSummaryCard.tsx:57`의 `determinedTaxAll` — **어디서도 읽지 않는 죽은 합산**(`grep determinedTaxAll` 정의 2줄뿐) ③ `app/api/calc/transfer/multi/route.ts:257`의 `pre?.determinedTax ?? breakdown?.determinedTax ?? 0` — 가산세 base의 **대체값**. `pre`(`computePreliminaryFilingTaxes` 결과)는 카드 묶음(GB)의 첫 카드 인덱스에만 실리고 «가산세 입력도 그 카드 한 장에만 있다»고 `transfer-tax-preliminary-filing.ts`의 `PreliminaryCardUnit` 주석이 적는다 — 즉 `pre`가 없는 인덱스는 가산세 입력이 없는 카드다. 이 대체값이 실제로 쓰이는 입력은 **찾지 못했고 측정하지 않았다**.
- PDF의 `props`는 다건 route 응답의 `properties`(`r.properties`)다. 그 원소(`PerPropertyBreakdown`)에는 `calculatedTax`가 없다(`types/transfer-aggregate.types.ts` — `refCalculatedTax`만; `calculatedTax`는 최상위 `AggregateTransferResult`에 있다).

## 4. ③ 옛 저장 이력 — 이전 보고 정정 [직접: 호출처 grep]

#3162의 PR 본문·계획서 §7.6·메모리(`project_99_993_994_review_2026_11.md`)에 «옛 저장 이력은 저장된 혼합 기준 값이 그대로 표시된다»고 썼다. 코드를 읽어 보니 근거가 없는 서술이다.

- 다건 결과 화면(`MultiTransferTaxResultView`)은 `MultiTransferTaxCalculator.tsx:355`의 `setResult(res)`(방금 받은 API 응답)로만 채워진다. 스토어 `result`는 `partialize`에서 제외돼(`multi-transfer-tax-store.ts:293-296`) 세션 복원에도 없다.
- 이력 상세 드로어(`HistoryDetailDrawer.tsx`)는 `extractResultSummaryItems`로 최상위 «산출세액·결정세액·납부세액·합산 납부세액»만 읽는다. 건별 breakdown(`refDeterminedTax` 포함)을 다시 그리는 컴포넌트는 `components/calc/results/Multi*`뿐이고 모두 신선한 응답을 받는다.
- 이력에서 정정·합산으로 들어가는 길(`transfer-amendment-entry.ts`·`transfer-aggregate-entry.ts`·`transfer-multi-load-entry.ts`)은 `inputData`로 폼을 복원하거나 `resultData`의 최상위 세액만 읽는다(`transfer-multi-load-entry.ts:34-41` `result.determinedTax`·`localIncomeTax`).
- PDF는 결과 화면의 `generateResultPdf` 버튼이 부른다(이력에서 직접 생성하는 호출처는 찾지 못했다).

따라서 #3162에서 넣은 «옛 이력 대체 계산 2곳»(`getRefDeterminedTax`·아코디언)은 **현재 코드 기준으로는 도달 경로가 확인되지 않는 방어 코드**다(기존 계약 테스트 `multi-breakdown-adapter-contract`가 «필드 부재 시 NaN 방지·형제와 같은 값»을 요구해 정합을 유지한 것이다). 삭제 대상으로 보지 않는다 — 그 가드는 #104 코드리뷰가 IndexedDB 복원을 이유로 넣은 것이라 다른 경로가 있을 가능성을 배제하지 못한다(이력 → 결과뷰 경로 부재는 `grep`으로 확인했지만 라우트 전수 확인은 아니다).
