- 증여세 **97,000,000 과소**(주택 쌍). UI 는 ⑧ 이 막으므로 화면 경로는 안전하고, 계약 밖 직접 호출(API 소비자)이 영향을 받는다.
- 원인(코드): `bgBundleMixedWinner`(`transfer-tax-schema-gb-bg-refines.ts:105-120`)가 ① 주 자산은 `propertyType === "general_building"` 일 때만 집계에 넣고(`:108`) ② 모든 항목의 기준시가 **4칸**이 > 0 이어야 판정한다(`:112`). 주택 info 는 토지 칸이 0 이라 4칸 검사가 `0101` 로 실패 → 판정 보류 → 혼합 승자가 통과. 일반건물 주 자산 + 주택 컴패니언도 컴패니언 쪽 4칸이 비어 보류된다. 호출은 `transfer-tax-schema.ts:140` 이 자산 종류와 무관하게 한다.
- 승자 판정 leaf(`companionBurdenedGiftValuations`)는 ⑧ 과 같고 종류를 가리지 않는다 — 주택 info 에서도 ⑧ 이 올바른 승자를 구한다(위 표의 `승자=ms` 등).

### PB-2 컴패니언 매매사례가액 — 결함 아님

- 컴패니언 Zod 스키마(`transfer-tax-schema-sub.ts`)에 `acquisitionMethod`·`similarSalesValue` 가 없다. ⑧ 이 막는 입력은 ④ 가 payload 에 싣지 않으므로 ⑫ 가 받는 것은 `fixedAcquisitionPrice` 뿐이다.
  - 실가(`fixedAcquisitionPrice`) 있음: 플래그를 버리고 계산 → 플래그 없는 대조군과 양도차익 같음. 계약에 없는 필드를 무시하는 것이다.
  - 실가 없음: 400 (`companionAssets.0.fixedAcquisitionPrice`).
- 주 자산 매매사례는 지원 조합 — ⑧ 이 매매사례 차단을 걸지 않고 ⑫ 200.

### 묶음 B-1 (⑧ 과차단) — 근거 정리

- 일반건물: #2753 의 「⑧게이트·⑫200·균일」 38셀(2건 29 + 3건 9) 모두 ⑫ 가 맞게 계산(증여가액 = ΣA, ΣB = 폼 채무 합, 양도차익 = 단건 합).
- 주택: 균일 담보 승 쌍이 같은 불변식(PB-1 마지막 행).
- ⑧ 을 푸는 곳은 한 곳이다(`transfer-tax-validate.ts:352-366` — 비보충 승 자산마다 이슈). 단 화면(⑤ 카드·⑦ 결과)이 담보 승 묶음을 제대로 보여 주는지는 코드로만 확인했다(`bgCollateralForcesStdAcq` 는 지분 보유 자산을 제외 — `burdened-gift-collateral-win.ts`). 브라우저 미확인.

## 3. 한계 (확인 필요)

- 주택만 측정했다. 상가·토지·겸용주택·입주권 컴패니언은 미측정(같은 leaf 라 같은 모양일 가능성이 높으나 확인 필요).
- 일반건물+주택 혼합 종류의 오라클 증여세 수치는 측정하지 않았다(`wholeMax < ΣA` 관계만 고정).
- 화면(브라우저)은 보지 않았다.

## 4. 결정 대기

**Q-1 (PB-1 ⑫ 확장)**
- **a (권고)**: `bgBundleMixedWinner` 를 자산 종류와 무관하게 — 주 자산도 종류 제한 없이 집계에 넣고, 「판정 가능」 조건을 4칸 대신 **양도 쪽 입력**(시가 모드: `marketValueAtTransfer` > 0 / 기준시가 모드: 양도시 토지+건물 기준시가 합 > 0)으로 바꾼다. 일반건물은 취득시 칸이 비면 `requireStd` 가 이미 400 이라 출력은 같고 메시지만 늘 수 있다. 메시지 문구는 「일반건물」 한정을 걷어낸다.
- b: 두지 않는다 — ⑧ 의 UI 보호만 유지하고 직접 호출 한계로 기록. 「침묵 오산보다 명시 차단」 정책(`multi-transfer-tax-validate.ts:57-71`)과 어긋난다. 비권고.

- b: 지금 푼다(⑧ 을 「혼합 승자만」으로 좁힘) — 화면 확인 없이 UI 를 여는 것이라 비권고.
