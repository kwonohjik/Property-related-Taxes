## 1. #4 비사업용 중과 시료와 조건 정정

### 1.1 시료가 중과로 이어지지 않던 이유 (#3175 계획서의 V-5 해소)

#3175의 E·H·J 시료가 `isNonBusinessLand: true`인데도 `progressive`였던 것은 **mock 세율표 때문이 아니었다.** 두 가지 중과 배제가 겹쳤다 — ① 양도일 2024-06은 2022.5.10~2026.5.9 비사업용 토지 중과 배제 기간(확인 필요: 기간은 시료 거동으로 추정, 조문 본문은 이번에 조회하지 않았다) ② 취득일 2010-01-01은 위기취득(2009.3.16~2012.12.31 취득) 배제(`nblSurchargeExcludedBy: "crisis_acquisition"` — `nbl-rate-deferral-era.anchor.test.ts` 주석 근거). 양도일 2021-06-01 · 취득일 2000-01-01 · 폴백 세율표로 바꾸자 `non_business_land:0.5`가 나왔다.

## 2. #5 아코디언의 일반건물 파트 카드 [직접: 실제 응답 렌더]

토지 + 일반건물 다건 응답(`land#p2`·`building#p2`)을 `MultiTransferTaxResultView`로 렌더했다. 일반건물 그룹(`data-testid="multi-gb-group-p2"`)의 파트 카드 2장 모두 «산출세액 (참고)»·«결정세액 (참고)» 행을 낸다(코드: `MultiTransferPropertyBreakdown.tsx:395`·`:426` — 가드는 `!isExempt && taxBaseShare > 0`뿐, `isGbPartCard`를 부르지 않는다). `MultiGbAssetGroup.tsx`가 파트 카드를 `PropertyBreakdownAccordion`에 그대로 넘긴다.

| 표시 위치 | 일반건물 파트 카드의 산출/결정(참고) |

## 3. 나머지 항목 근거

### 3.1 #1 주식

`calculateStockTransferTaxAggregate([...], "aggregate")` 4시료(세율 구간이 갈리는 소득 4억/건):

| 시료 | Σ items.calculatedTax | totalCalculatedTax | 차 | `otherAssetComparativeTax` |
|---|---|---|---|---|
| 대주주 2종목 | 169,375,000 | 169,375,000 | 0 | 없음 |
| 대주주 1 + 기타자산 1 | 217,435,000 | 217,435,000 | 0 | 없음 |
| 기타자산 2 (각 4억) | 267,120,000 | 299,010,000 | **31,890,000** | `clause2` |
| 기타자산 2 (소액) | 90,000 | 90,000 | 0 | `clause2` |

- 주식 `items`는 대주주 군에서는 합계와 같다(자산 단독이 아니라 합산 결과의 몫으로 보인다 — 코드를 읽지는 않았다). 기타자산 2건은 비교과세와 같은 군 누진 합산이 한꺼번에 켜져 있어 어느 쪽이 차이를 만드는지 가를 수 없다. 소액 2건이 차 0인 것은 «누진 구간이 안 갈려서»로도 «비교과세가 같은 값을 골라서»로도 설명된다.
- 따라서 `stock-transfer-aggregate.ts:75` 서술(«기타자산 2건 이상이면 §104⑤ 비교과세가 합계에 적용 → Σ ≠ 합계»)은 **반증되지 않았다.** 건드리지 않는다.

### 3.2 #2 주택 분할

`hasSeperateLandAcquisitionDate=true` 주택 1건(토지 80,000,000·건물 120,000,000 취득, 양도 토지 400,000,000·건물 500,000,000)을 단건·다건 route에 보냈다. 건별 `splitDetail` 있음(분리 취득 경로 통과). §99의3은 소득금액 차감형이라 `reductionAmount = 0`이고 산출세액이 줄어든 값(136,393,333)이 단건과 같다. 겸용주택은 `MULTI_REJECT_RULES.mixedUse`(`transfer-tax-schema-multi-refines.ts:64`)가 거부한다 — 겸용주택의 건별 표시는 다건 범위가 아니다.

| 시료 | 합산 산출 | Σ건별 산출 | 차 | 합산 감면 = Σ배분 |

### 3.4 #6 가산세 대체값 (`multi/route.ts:257`) [직접: 코드 읽기]

`determinedTax = pre?.determinedTax ?? breakdown?.determinedTax ?? 0`의 대체값은 `if (p.filingPenaltyDetails)`·`if (p.delayedPaymentDetails)` 안에서만 쓰인다. `pre`가 없는 인덱스는 일반건물 카드 묶음의 **첫 카드가 아닌** 카드뿐이다(`transfer-tax-preliminary-filing.ts`: 묶음은 `indices[0]`만 계산·`set`; 이월과세 × 채무 단위는 `indices: [idx]` 1개라 항상 있다). 그런데 가산세 입력은 **첫 카드에만** 실린다(`multi-gb-expansion.ts:10·92`). 따라서 이 대체값이 가산세 base가 되는 입력은 코드상 없다. 실행으로 확인한 것은 아니다 — 기존 MG-6·7 anchor(가산세 단건 일치)가 이 경로를 지키고 있다.

### 3.5 #7 이력 → 결과뷰 [직접: grep 전수]

`resultData` 사용처(`app components lib`, 테스트 제외): 쓰기 = 6개 결과뷰(`TransferTaxResultView`·`MultiTransferTaxResultView`·`InheritanceTaxResultView`·`GiftTaxResultView`·`ComprehensiveTaxResultView`·`PropertyTaxResultView`)의 이력 저장 호출. 읽기 = `HistoryClient`·`HistoryDetailDrawer`의 요약(`extractTotalTax` 등), `transfer-amendment-entry`·`transfer-multi-load-entry`·`transfer-resume-entry`(최상위 `determinedTax`·`localIncomeTax`·`ruralSurtax`·형태 판별). 어느 곳도 저장된 건별 breakdown을 결과뷰에 다시 넘기지 않는다. 앱 라우트는 `app/calc/**` + `app/history`뿐이다(`ls app`).
