## 1. 사용자 결정 (2026-10-05)

- 「합가 전 구성을 모르는 경우」 4가지 중 **1(명부 없음)·2(합가 전 소유 미입력)를 먼저 「불성립 + 확인 필요」로 바꾼다.**
- **3(명부 행 수 ≠ 판정 주택 수)은 엔진 보완부터** — 어느 행이 주택 수에서 빠졌는지 엔진이 알게 한 뒤 판정한다.
- 방향: 「기본적으로 **세대 보유 주택은 모두 목록에 입력**해야 되고 **주택별로 세대원 소유인지 양도자 소유인지** 입력받으면 될 것」 — 계산기에도 합가 전 소유 입력을 연다.
- 4(주택 수 2·3 외)는 손댈 코드가 없다(§2-2).

### 2-4. 계산기에는 합가 전 소유 칸이 없다

- 편집 창의 소유 라디오(`components/calc/transfer/HouseEntryMergeOriginBlock.tsx`)는 `mergeContext` prop이 있을 때만 열린다.
- 이 prop을 넘기는 곳은 **판정 메뉴 한 곳**(`app/calc/one-house-exemption/steps/Step2.tsx:170`)뿐이다. 계산기의 두 렌더 지점(`app/calc/transfer-tax/steps/Step4.tsx:675` · `app/calc/transfer-tax/steps/step4-sections/SurchargeJudgmentSection.tsx`)은 넘기지 않는다.
- ④ 변환(`lib/calc/transfer-tax-api-houses.ts:286` — 주석 「계산기는 이 칸이 없어 늘 미전송」)·⑫ Zod·⑭ route·엔진은 **메뉴 공용**이라 이미 값을 받는다. ⇒ 계산기 사용자는 지금 2번에 **항상** 해당한다(사례 b2).
- 계산기 ⑧ validate에는 합가 관련 검증이 없다. 판정 메뉴 ⑧은 미입력을 **경고만** 한다(`lib/calc/one-house-exemption-validate.ts:109-125` — 「구 저장분이 전부 이 상태라 차단하면 기존 판정이 한꺼번에 막힌다」).

### 2-5. 명부 필수 여부

- 명부는 필수가 아니다. 세대 주택 수(숫자)와 명부 행 수가 어긋나도 안내만 한다(`lib/calc/house-count-divergence.ts` — 표시 전용).
- 다주택 중과는 명부가 있으면 명부 기준으로 센다(같은 파일 주석) — 「세대 주택은 모두 명부에」는 엔진 설계와 맞는 방향이다.

## 3. 설계

### 3-1. 엔진 — `unknown`을 사유별로 나눈다

```
MergeComposition
  | { status: "holds" }
  | { status: "fails"; reason: ...; confirmNotice?: string }   // 1·2번은 fails + confirmNotice
  | { status: "unknown"; reason: "count_mismatch" }             // 3번 — 2단계 전까지 종전 동작
```

- 1번(명부 없음 · 양도 주택 행 없음) → `fails` + `reason: "roster_missing"` + 확인 필요 문구 「세대 보유 주택을 모두 목록에 입력하면 판정한다」.
- 2번(합가 전 취득 행 소유 미입력) → `fails` + `reason: "origin_missing"` + 「합가 전 보유자(양도자 쪽 / 배우자·합친 가족 쪽)를 고르면 판정한다」.
- 1번에 **명부가 있지만 행이 모자라는 경우**(제외가 하나도 없는데 행 수 < 주택 수)도 포함한다 — 입력하지 않은 주택이 있다는 뜻이다. 제외가 있어서 어긋나는 경우만 3번(`count_mismatch`)이다.
- `matchMergeApartFromWindow`는 `fails`를 그대로 거른다(`:717` 변경 없음). `unknown`(3번)만 종전 동작.
- 「확인 필요」 채널: §155⑳ 선례처럼 **결론을 가를 때만**(합가 외 요건을 모두 충족해 합가 구성 하나로 비과세가 갈릴 때) 비과세 판정 단계에 보조 행을 싣는다. 다른 의제(§155① 등)로 비과세가 서면 고지하지 않는다.
- 요건 검토 카드(`requirement-review.ts`): 1·2번은 `unchecked`(미확인) → `unmet`(불성립) + 확인 필요 note.
- 판정 메뉴 사유 카드(`unmet-exceptions.ts`): `fails` 템플릿에 두 사유 문구를 더한다.

### 3-2. 화면 A — 계산기 명부 필수화(Q-3 · Q-2 · D-4 폐기)

- **세대 주택 수는 명부에서 도출**한다(판정 메뉴 `deriveJudgmentHouseCount`와 같은 방식 — 숫자 칸 「1 / 2 / 3+」 위젯을 없애거나 읽기 전용 표시로 바꾼다, Q-6). 숫자 칸 비교 게이트는 도출값을 보게 한다.
- **「다른 보유 주택 없음」 확정 입력**을 새로 둔다 — 명부 0행이면 이 확정이 있어야 다음 단계로 간다(⑧ 차단). 확정 후 행을 추가하면 확정은 풀린다(Q-5).
- ⑧: 대상 자산(Q-7)에서 「명부 ≥ 1행」 또는 「없음 확정」이 아니면 **차단**.
- 입주권·분양권·재개발 아파트·겸용주택은 ① 의미가 달라 도출식이 다르다(§2-8 자산 표) — Q-7.

### 3-3. 화면 B — 계산기에 합가 전 소유 입력을 연다

- 계산기 두 렌더 지점(`Step4.tsx:675` · `SurchargeJudgmentSection.tsx`)에 `mergeContext={mergeContextOf(form)}`를 넘긴다(합가일이 없으면 `undefined` — 칸이 안 열린다). 위젯·라벨(현행 그대로 — Q-1)·명부 표 배지·합가 후 취득 날짜 파생은 판정 메뉴 것을 그대로 쓴다.
- ⑧: 합가일이 있고 합가 전 취득 행의 소유가 비면 **차단**(Q-2). 판정 메뉴 ⑧(`one-house-exemption-validate.ts:109-125`)의 경고도 차단으로 올린다(같은 근거 — 옛 저장분 삭제).
- 14 동기화: ①타입 · ④ · ⑫ · ⑭ · 엔진은 이미 있다. 새로 필요한 것은 ⑤(계산기 두 지점) · ⑦(계산기 결과뷰에 불성립 사유가 보이는지 — V-C) · ⑧.

### 3-4. 3번 보완 — 제외 행을 빼고 합가 구성 판정(Q-4)

- `resolveExemptionHouseCountExclusions`가 이미 가진 제외 행(`excludedHouses[].houseId` · `houseCountExclusionDetails[].houseId` · `specialHouseExclusionDetail.entries[].houseId`)을 **제외 행 집합**으로 모아 `resolveMergeComposition`에 넘긴다. 명부에서 그 행을 **빼고** 남은 행으로 행 수 비교와 구성 판정을 다시 한다(사용자 결정 Q-4 — 상속주택·조특법 감면주택은 합가 당시 주택 수에서 뺀다).
- 행이 특정되지 않는 제외(API 직접 호출에서 `houseId` 없는 선언)는 어느 행인지 모른다 → 불성립 + 확인 필요. 계산기는 ⑧이 이미 막으므로 화면에서는 생기지 않는다(§2-6).
- V-A(해석례)는 근거 기록용으로 조사한다. 반대 취지가 나오면 보고하고 멈춘다.
