## §2. 기각 항목 R-1 — 양도차손 안분은 현행이 옳다 (실측)

`offsetLossesCore`를 직접 호출해 실측했다:

| 국외주식 차손 | 종목1 배분 | 종목2 배분 |
|---|---|---|
| −20,000,000 | 6,000,000 | 14,000,000 ← **현행 화면** |
| −21,000,000 | 6,300,000 | 14,700,000 ← 제보 기대치 |

- 안분 base = 통산 전 양도차익 **24,600,000 : 57,400,000 = 30 : 70** (영 §167의2①2호
  「각 세율별 양도소득금액의 합계액에서 당해 양도소득금액이 차지하는 비율」).
- 제보 기대치의 합은 **21,000,000**으로 차손 총액 20,000,000을 초과한다. 배분 합계가 pool을
  넘는 것은 **어떤 안분 기준으로도 불가능**하므로 안분 로직의 결함이 아니다.
- 국외주식 종목의 필요경비는 **0원 입력**임을 제보자가 확인했다 ⇒ 차손 20,000,000 확정.

> ❌ **이 축을 미결로 재기재하지 말 것.** `lib/tax-engine/loss-offset-core.ts`는 변경 대상이 아니다.
>
> 🔑 다만 **왜 「안 맞아 보였는지」는 실재하는 결함이다** — D-1이 안분 base를 화면에서 지워버려
> 검산이 불가능했다. D-1을 고치면 `24,600,000 − 6,000,000 = 18,600,000`으로 세 줄이 맞아떨어진다.

## §3. D-1 — 18행 「양도차익」이 통산 **후** 값을 표시한다

### 3.1 현상 (화면 수치로 검산)

| | 라벨이 약속한 산식 ⑦−⑪−⑭ | 화면 18행 | 차이 |
|---|---|---|---|
| 종목1 | 39,000,000 − 14,000,000 − 400,000 = **24,600,000** | 18,600,000 | −6,000,000 |
| 종목2 | 100,000,000 − 42,000,000 − 600,000 = **57,400,000** | 43,400,000 | −14,000,000 |

차이가 정확히 18-1행 통산액이다. 결과적으로 표가 자기모순이다:

```
18행 18,600,000 + 18-1행 (−6,000,000) = 12,600,000  ≠  19행 18,600,000
```

### 3.2 원인 (file:line)

`StockFilingFormTableHelpers.ts:225-232`(18행)과 `:268-273`(19행)이 **같은 값**을 쓴다:

```ts
values: val(result.transferIncome, (agg) => agg.totalTransferIncome, (item) => item.transferIncome)
```

그런데 `item.transferIncome`은 `stock-transfer-aggregate.ts:429-431`에서 **통산 후 값으로
갈아끼워진** 것이다(주석 그대로 — 「통산 후 값으로 갈아끼운다 — 그래야 `taxBase =
transferIncome − basicDeduction`」).

### 3.3 🔑 고칠 값은 이미 엔진이 내보내고 있다 — 다만 **아무도 읽지 않는다**

`stock-transfer-aggregate.ts:473-477`이 **조건 없이** 통산 전 값을 싣는다:

```ts
transferIncomeBeforeOffset: rawItems[i].transferIncome,
```

grep 결과 이 필드의 참조는 **선언(`stock-transfer.types.ts:1135`)과 세팅(위 1곳)뿐**이고
**소비처가 0건**이다. 정확히 이 18행을 위해 만들어진 echo가 미배선 상태다.

### 3.4 설계

18행만 소스를 바꾼다. 19행은 **그대로 둔다**(통산 후 = 양도소득금액이 맞다).

```ts
// 18. 양도차익 — 통산 «전». optional 이므로 단건·통산 미발생 경로는 현행값으로 떨어진다.
(item) => item.transferIncomeBeforeOffset ?? item.transferIncome
```

- **단건 경로**(`aggregate` 없음): 필드가 undefined ⇒ `result.transferIncome` 유지 ⇒ 거동 불변.
- **합계 열**: `agg.totalTransferIncome`은 통산 후 합계다. 이 케이스에서는 차손이 전액 흡수되어
  통산 전후 합계가 **우연히 같다**(24.6 + 57.4 − 20.0 = 18.6 + 43.4 + 0 = 62,000,000).
  ⇒ **V-1** 잔여 차손이 소멸하는 케이스(`unusedLoss > 0`)에서는 둘이 갈린다. 합계 열도
  통산 전 합계(= `Σ transferIncomeBeforeOffset`)로 바꿔야 18 + 18-1 = 19가 성립한다. **Do 전 실측 필요.**

## §4. D-2 — 16행 「매매수수료·기타 양도비용」 합계 열이 비어 있다

### 4.1 현상

14행 필요경비 합계는 1,000,000인데, 그 내역인 16행 **합계 열만 「–」**이고 종목 열에는
400,000 / 600,000이 찍힌다. 표가 1,000,000의 출처를 설명하지 못한다.

> 이 공백이 제보의 21,000,000 오해에 기여했을 가능성이 있다 — 국외주식 종목의 필요경비가
> 0인지 1,000,000인지 표에서 읽을 수 없었다. (**추정이며 제보자 확인 전이다.**)

### 4.2 원인

`StockFilingFormAssetCostRows.ts:329-335` — 합계 열 계산자가 `() => null`이다.
같은 파일 17행(개산공제)은 `:340-346`에서 `aggregate?.items.reduce(...)`로 **집계하고 있다**.
⇒ 16행만 빠진 비대칭이다.

### 4.3 설계

17행과 **같은 모양**으로 맞춘다:

```ts
() => aggregate?.items.reduce((s, r) => s + (otherExpenses(r) ?? 0), 0) ?? null
```

- `otherExpenses`는 `expenseMode !== "actual"`이면 null을 준다 ⇒ estimated 모드 종목이 섞이면
  그 종목은 0으로 집계된다. **V-2** 혼재 시 합계가 14행과 어긋나 보일 수 있다 — 실측 후
  「actual 종목만의 합」임을 라벨이 이미 말하고 있는지 확인한다(현행 라벨: 「(actual 모드)」).
- **Q-1** D-2를 이번 범위에 포함할지는 제보자 결정 사항이다(§10).

## §5. D-3 — 열폭: colgroup이 **무시되고 있다** (실측)

### 5.1 의도 vs 실제

`StockFilingFormTable.tsx:110-117`의 의도는 **항목 220px / 데이터 각 130px**(총 740px)이다.
실제 렌더를 Playwright로 실측했다(3종목 · viewport 1280):

| 열 | colgroup 지정 | **실측** | 배율 |
|---|---|---|---|
| 항목 | 220px | **88px** | ×0.40 |
| 합계 | 130px | **355px** | ×2.73 |
| 종목 1·2·3 | 각 130px | **각 242px** | ×1.86 |
| 표 전체 | 740px | **1170px** | ×1.58 |

`tableLayout`은 computed로 `fixed`인데도 **지정 폭이 하나도 지켜지지 않는다.**

### 5.2 원인 — 두 겹

**원인 ①: `table-layout: fixed` + `width: auto` 조합** (`StockFilingFormTable.tsx:106-109`)

```ts
style={{ width: "auto", tableLayout: "fixed" }}
```

테이블 폭이 `auto`면 브라우저는 fixed 알고리즘을 적용할 기준 폭이 없어 **내용 기반(shrink-to-fit)
으로 폴백**한다. 이때 `<col>` width는 강제값이 아니라 선호 힌트로만 쓰이고, 각 열의
min-content/max-content가 우선한다.

> 실측 대조: 동일 구조를 **컨테이너보다 좁게** 최소 재현하면 220px이 그대로 지켜진다
> (표 폭 827px < 컨테이너 1100px). 즉 표가 컨테이너를 넘어 늘어나는 순간 지정이 무너진다.

**원인 ②: 데이터 셀 전역 `whitespace-nowrap`** (`StockFilingFormTable.tsx:165`)

데이터 열은 nowrap이라 **min-content = 전체 텍스트 폭**이 되어 줄지 않고, 항목 열은 nowrap이
없어 **min-content(가장 긴 단어)까지 압축**된다. 이 비대칭이 제보의 「항목은 좁고 합계는 넓다」다.

각 열이 실제로 요구하는 내용 폭을 실측했다:

| 열 | max-content | 그 폭을 만든 셀 |
|---|---|---|
| 항목 | 418px | `23-1.   ③ 세율구분 그룹 (작성요령 4번 — 세율이 같은 자산을 합산)` |
| 합계 | **441px** | `예정신고: 반기 말일 + 2개월 / 확정신고: 다음연도 5월 31일` |
| 종목 | 291px | `20% 그룹 (국내 비대주주·국외주식 공통)` |

🔑 **합계 열을 밀어낸 것은 금액이 아니라 설명 문자열이다.** 금액 최장값
`149,000,000`은 font-mono 12px 기준 ~95px + padding 24px ≈ 119px에 불과하다.

### 5.3 설계

**(a) 테이블에 명시 폭을 준다** — fixed 알고리즘이 실제로 작동해 colgroup이 강제된다.

```ts
style={{ width: `${ITEM_COL_PX + DATA_COL_PX * columns.length}px`, tableLayout: "fixed" }}
```

**(b) 목표 폭** — 제보 배율을 **실측 현재값**에 적용한다(코드 지정값이 아니라 화면에 보이는 값이
제보의 기준이다):

| 열 | 실측 현재 | 제보 요구 | **목표** | 근거 |
|---|---|---|---|---|
| 항목 | 88px | ×2.5 | **220px** | 88 × 2.5 = 220 — 공교롭게 **기존 colgroup 지정값과 동일**하다 |
| 합계 | 355px | ×0.4 | **150px** | 355 × 0.4 = 142 → 금액 119px + 여유. 기존 지정 130px과 근접 |
| 종목 | 242px | 「조금씩」 | **190px** | ×0.79. 헤더 `종목 2 (비상장 대주주)` 실측 173px 수용 |

⇒ 3종목 총폭 = 220 + 150 + 190×3 = **940px**. 실측 스크롤 컨테이너 924px과 거의 일치해
가로 스크롤이 사실상 사라진다(현행 1170px → 246px 초과였다).

> 🔑 **제보 배율이 원래 의도(220/130)를 거의 그대로 가리킨다.** 이 작업의 본질은 새 디자인이
> 아니라 **「지정한 폭이 지켜지게 만드는 것」**이다.

**(c) 🔴 nowrap을 열 단위가 아니라 «값 종류» 단위로 건다** — (a)만 하면 441px짜리 문자열이
150px 셀 밖으로 삐져나온다.

```
숫자 값  → whitespace-nowrap 유지 (금액 줄바꿈 금지 — amount-column-align 정책)
문자열 값 → 줄바꿈 허용
```

`fmtCell`에 들어가는 `row.values[c.key]`의 타입으로 가른다. **V-3** `RowDef.values`의 실제
유니온 타입과 `fmtCell`의 분기를 확인해 판정식을 정한다(추정 금지).

**(d) 항목 열 줄바꿈은 «허용»한다.** 220px에 최장 라벨 418px은 들어가지 않는다. 제보는 「2행
이상에 걸친다」인데, 실측 88px에서는 **4~5행**이 된다. 220px면 최장 라벨도 2행에 든다.
⇒ 목표는 「줄바꿈 0」이 아니라 **「2행 이내」**다. **Q-2**로 확인한다.

### 🔴 이 작업에서 배운 함정 2건

**함정 1 — 범위 단언이 「고쳤다」고 오판하게 만든다.**
M-2를 처음 돌렸을 때 **통과했다**(= 뮤테이션을 못 잡았다). `(c)` 줄바꿈만으로 max-content가
줄어 범위 단언(`>= 200`, `<= 170`)을 우연히 만족했기 때문이다. 실제 폭을 재보니
**215/148/187** 로, colgroup 이 여전히 강제되지 않고 **컨테이너 폭에 맞춰 비례 압축**된
상태였다. 좁은 창(800px)에서는 항목 열이 **166px** 까지 찌그러졌다.
⇒ 지정값을 검증할 때는 **범위가 아니라 ±1px 동등성**으로 단언한다. 범위 단언은
「거의 맞는 값」과 「지정이 지켜진 값」을 구분하지 못한다.

**함정 2 — `emulateMedia({media:"print"})` 만으로는 인쇄 화면이 아니다.**
결과뷰는 섹션을 `PrintSection`으로 감싸고 **미선택 섹션에 `print:hidden`** 을 건다
(기본값 **전체 미선택**). 선택 없이 print 미디어만 켜면 표가 `display:none` 이라 폭이 **0** 으로
잡힌다 — 제품 정상 동작인데 **결함으로 오판**했다. 인쇄 경로 E2E 는 「전체 선택」을
먼저 눌러야 하고, **폭 0 가드**를 같이 둬야 이 오판이 재발하지 않는다.
