## 2. 법령 원문 — 「상증법」§4의2 (2025.10.01. 시행본 verbatim)

- **①** 「수증자는 다음 각 호의 구분에 따른 증여재산에 대하여 증여세를 납부할 의무가 있다.」
  1호 「수증자가 거주자(본점이나 주된 사무소의 소재지가 국내에 있는 **비영리법인을
  포함한다**…)인 경우」 / 2호 「수증자가 비거주자(… **비영리법인을 포함한다** …)인 경우」
  ⇒ **영리법인은 납세의무자 범위 자체에 없다.**
- **③** 「제1항의 증여재산에 대하여 **수증자에게** 「소득세법」에 따른 소득세 또는
  「법인세법」에 따른 법인세가 부과되는 경우에는 증여세를 부과하지 아니한다. 소득세 또는
  법인세가 … 비과세되거나 감면되는 경우에도 또한 같다.」
- **④** 「**영리법인이 증여받은 재산 또는 이익**에 대하여 「법인세법」에 따른 법인세가
  부과되는 경우(법인세가 … 비과세되거나 감면되는 경우를 포함한다) **해당 법인의 주주등**에
  대해서는 **제45조의3부터 제45조의5까지의 규정에 따른 경우를 제외하고는** 증여세를
  부과하지 아니한다.」

### 🔴 ③과 ④는 수범자가 다르다 — 한 축으로 뭉뚱그리면 틀린다

| 항 | 요건의 주체 | 증여세를 면하는 자 |
|---|---|---|
| ①(+2 9호) | — | **수증자 자신**이 영리법인인 경우 (납세의무자 아님) |
| ③ | **수증자**에게 소득세·법인세 부과 | **수증자 자신** |
| ④ | **영리법인**이 받은 재산·이익에 법인세 부과 | 그 **법인의 주주등** (≠ 수증자일 수 있음) |

①·③은 **이미 구현돼 있다**(§39 1-E — `doneeIsForProfitCorp`). 이 문서가 다루는 미구현 축은
**④ 하나**다. ⇒ 리뷰의 조건 ③(「①과 묶어 설계」)은 **§39 범위에서는 이미 충족**됐고,
남은 통합 대상은 「①·③·④를 같은 모듈이 같은 형태로 반환하게 만드는 것」이다.

## 4. 설계

### 4.1 위치 — `lib/tax-engine/gift-deemed/taxpayer-gate.ts` (신설)

순수 함수 모듈 하나가 **세 항의 판정과 사유 문자열을 단독 소유**한다.
엔진마다 손으로 적으면 §39에서 겪은 것과 같은 표현 드리프트가 재발한다.

```ts
export type TaxpayerExclusion =
  | { excluded: false }
  | { excluded: true; basis: "donee_for_profit_corp" | "donee_income_taxed" | "shareholder_of_taxed_corp";
      reason: string };

export function evaluateTaxpayerGate(args: {
  giftType: DeemedGiftType;          // §45의3~§45의5 단서 판정용
  doneeIsForProfitCorp?: boolean;    // §2 9호·§4의2①
  doneeIncomeOrCorporateTaxed?: boolean; // §4의2③
  issuerGainCorporateTaxed?: boolean;    // §4의2④ — 영리법인의 «수증이익»에 법인세
  doneeIsShareholderOfIssuer?: boolean;  // §4의2④ — 「해당 법인의 주주등」 요건
}): TaxpayerExclusion;
```

### 4.2 적용 지점 — 라우터 후처리가 아니라 **엔진 내부 선(先)판정**

`router.ts`에 후처리를 붙이는 안은 **채택하지 않는다**. 이유:

1. 결과 타입이 유형마다 다르다(`DeemedGiftResult` / cap-table의 `perBeneficiary` /
   `capitalDecreaseMulti` / `shareholders` 다건). 후처리로 0을 만들려면 라우터가 모든
   형태를 알아야 하고, 그것이 곧 `router.ts`를 **모든 유형의 결과 구조에 결합**시킨다.
2. cap-table·다건 경로는 **수증자별로** 판정이 갈린다(A는 주주, B는 비주주). 단일 결과에
   플래그 하나를 붙이는 후처리로는 표현할 수 없다.
3. `router.ts:76`이 「router 후처리는 **없다**」를 선언하고 있고 그 단순함 자체가 자산이다.

⇒ 각 엔진이 **계산 직후·반환 직전**에 `evaluateTaxpayerGate`를 부르고, §39가 7단계에서
확립한 `excludedResult()` 형태(금액은 보존, 라벨을 「제외 전 산출 이익」으로)로 반환한다.

### 4.3 🔴 리뷰의 수정 방향에 **없던** 제약 2건

리뷰는 「`issuerCorporateTaxOnGain?: boolean` true이면 전체 배제」를 제안했다.
그대로 구현하면 **두 군데서 틀린다**.

#### (a) §4의2④는 「해당 법인의 **주주등**」에만 미친다 — §39①1호 다목은 수증자가 비주주다

「상증법」§39① 각 호를 원문 대조한 결과:

| 호·목 | 이익을 얻는 자 (원문) | 주주 여부 |
|---|---|---|
| 1호 가 | 「그 실권주를 **배정받은 자**」 | 사안 의존 |
| 1호 나 | 「그 신주 인수를 포기한 자의 **특수관계인**」 | 사안 의존 |
| **1호 다** | 「해당 법인의 **주주등이 아닌 자**」 | **정의상 비주주** |
| 1호 라 | 「해당 법인의 **주주등**이 … 초과하여 직접 배정받음으로써」 | 주주 |
| 2호 가·나 | 「그의 특수관계인에 해당하는 **신주 인수 포기자**」 | 주주(신주인수권 보유) |
| 2호 다·라 | 「그의 특수관계인인 **주주등**이 얻은 이익」 | 주주 |
| 3호 가 | 「그 주식을 **교부받은 자**」 | 주주 |
| 3호 나 | 「그 주식을 교부받은 자의 **특수관계인**」 | 사안 의존 |

⇒ **1호 다목에서는 §4의2④가 성립할 수 없다.** 일괄 배제하면 그 목에 **과소과세**가 생긴다.
⇒ 그래서 게이트 입력에 `doneeIsShareholderOfIssuer`를 **별도 축**으로 둔다. 「사안 의존」
행(1호 가·나, 3호 나)은 **사용자 입력**으로 받고, 조문상 확정되는 행은 그 값을 **무시하고
조문이 정한 값**을 쓴다(입력 오류가 법문을 이기지 못하게).

#### (b) §45의3~§45의5는 배제의 **예외** — 그 세 유형에서는 게이트가 발동하면 안 된다

④ 단서 「**제45조의3부터 제45조의5까지의 규정에 따른 경우를 제외하고는**」.
이 저장소의 해당 유형은 `listing_gain`(§41의3 계열이 아님에 주의) 이 아니라
**§45의3 일감몰아주기 · §45의4 사업기회 · §45의5 특정법인 거래**다.
`specific_corp`(§45의5)는 엔진이 있으므로 **게이트가 그 유형을 만나면 절대 배제하지 않는다**
— 이 반대 방향이 anchor의 긍정 짝이 된다.

### 4.4 반환 형태 — 7단계에서 확립한 「금액 보존 + 라벨 전환」을 그대로 쓴다

§39 5단계에서 정한 규칙을 재사용한다. 「상증법」§31①이 「증여재산가액」을 **과세대상
가액**에 한정 정의하므로, 배제되면 그 이름이 성립하지 않는다:

- `applied: false` · `deemedGiftValue: 0`
- breakdown의 마지막 「증여재산가액」 행 **라벨만** 「제외 전 산출 이익」으로 바꾸고
  **금액은 보존**한다 — §4의2④ 사안에서 그 금액은 **법인세 익금의 근거**이지 허수가 아니다
- `thresholdEcho.gain`에 산출 이익을 남긴다

## 5. 리뷰 서술 정정 1건

리뷰 `H-ui.md:164` 검증란의 **정정 ④**는 이렇게 적혀 있다:

> 「사안의 호는 2호 **라목**이 아니라 **다목**일 가능성이 높으나(㈜C가 증자 전 주주가 아닌
> 채권자), 「상증령」§29②5호가 다·라목을 한 호로 묶고 엔진도 같은 분기로 떨어뜨리므로
> 출력은 동일하다」

**자문 원문의 「3.관련규정」란은 §39①2호 「라.」를 인용한다**(다목은 인용하지 않는다).
따라서 「다목일 가능성이 높다」는 **원문과 배치**된다. 다만 원문은 ㈜C의 ㈜A 지분 보유
여부를 적지 않으므로 「㈜C가 비주주였다」는 전제 자체가 원문에서 확인되지 않는다.
⇒ 확정되는 사실은 **「국세청이 인용한 목은 라목이다」**까지이고, 결론(출력 동일)은 불변이다.

## 8. 이 문서가 닫지 않는 것

- **§39 외 35개 엔진** — 게이트 모듈은 공통이지만 **입력 축(①②③④⑤⑧⑫⑬⑭)은 유형마다
  따로 배선해야 한다**. 이 문서는 §39 3경로(단건·cap-table·전환주식)만 범위로 한다.
  나머지는 모듈이 선 뒤 유형별로 잇는다 — 한 PR에 38개를 넣지 않는다.
- **§4의2③(수증자 본인 소득세·법인세)** — `doneeIncomeOrCorporateTaxed` 축은 게이트
  시그니처에 자리만 만들고 **배선하지 않는다**. 「수증자에게 소득세가 부과되었는가」는
  §39 화면이 알 수 없는 사실이고, 별도 입력 경로 설계가 선행한다.
- **영리법인 ≠ 발행법인인 경우** — 자문은 영리법인 = 신주발행법인인 사안이다. 제3의
  영리법인이 받은 수증이익으로 주주가 이익을 보는 국면은 원문 범위 밖이라 다루지 않는다.
