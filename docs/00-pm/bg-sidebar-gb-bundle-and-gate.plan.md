## 1. Q-1 사이드바(⑥) — 일반건물 묶음 계산 후 취득가액·필요경비 「-」

### 1.1 원인 (실측)

- 응답 모양(`__tests__/api/transfer.sidebar-gb-bg-bundle.anchor.test.ts` 작성 전 프로브): `apportionment.apportioned` 의 id 는 `primary` · `asset-…-2` 이고 `allocatedAcquisitionPrice` 는 0(§159 입력 전 값).
  `aggregated.properties` 의 id 는 `land#primary` · `building#primary` · `land#asset-…-2` · `building#asset-…-2` 다(일반건물 한 자산이 토지·건물 카드로 쪼개진다).
- `lib/stores/transfer-per-asset-summary.ts` 는 `propertyId === 자산id` 로만 찾아(`bundledProperty`) 카드를 못 잡았다. `bundledMatch`(안분 행)는 잡히므로 `acqPrice = 0`, `acqPending = false` 로 확정돼 계산 후에도 「-」였다.
- 단건 일반건물은 `apportionedCards`(`isSingle`), 축 B 지분은 `gbShareBgCards` 가 맡았고, **축 A 함께 양도 묶음**만 비어 있었다. 세액·양도가액은 영향 없음(표시 전용).

### 1.2 수정

`gbBundledBgCards` — 축 B 가 아니고 다건이며 안분 행이 잡히는 일반건물 × 부담부증여 자산에 한해, `cardSuffixOf(propertyId) === 자산id` 인 `aggregated.properties`(이월과세 꼬리 `land__purchased#id` 포함) 의 취득가액·필요경비 합을 쓴다.
공용 leaf(`general-building-share-id.ts` `cardSuffixOf`)를 재사용하고 새 해석 규칙은 만들지 않았다.

### 1.3 오라클·결과 (`transfer.sidebar-gb-bg-bundle.anchor.test.ts`)

행마다 (양도가액 − 취득가액 − 필요경비) 의 합 = 엔진 `aggregated.totalTransferGain` (±0), 7 시료:
일반건물 2건 · 자본적지출 2천만(채무비율 30% 안분 6백만) · 환산 취득(개산공제 1,800,000씩) · 3건 · 일반건물+주택 · 주택+일반건물 · 주택 2건(대조).
수정 제거 뮤테이션: SB-1 6건 red, 대조군 2건 green.

## 2. Q-2 ⑧ 균일 승자 과차단 해제

### 2.1 사실 (실측 — 수정 전)

| 쌍 | ⑧ | ⑫·엔진 |
|---|---|---|
| 주택 기준시가 담보 쌍 | 2건 차단 | 200 |
| 주택 기준시가 임대 쌍 | 2건 차단 | 200 |
| 담보 + 보충 혼합 | 1건 차단 | 400 |
| 일반건물 시가 모드 담보 쌍(담보 1.2B > 시가 1.0B) | 승자 게이트 + 「채무액 > 증여가액」 | 200(브라우저에서 두 규칙을 임시로 풀어 ⑦ 이 API 와 일치: 총 세액 693,795,300 · 양도차익 1,988,000,000) |

균일 승자 쌍은 합산 증여가액 = ΣAᵢ 이고 양도차익 = 단건 합(Aᵢ = Bᵢ 라 가산)이므로 맞다(#2750·#2753 격자 131셀). 틀리는 것은 승자가 섞일 때뿐(Σmax ≠ max(Σ성분)).

### 2.2 수정

1. **승자 게이트** (`transfer-tax-validate.ts`): 비보충 승자를 전부 막던 것을 ① 승자가 섞이면 1건 차단(`bgBundleWinnerModes` — 안내에 자산별 방식을 적는다) ② 지분·이월과세·조합원입주권·겸용주택 자산의 비보충 승자는 그대로 차단(`bgNonSupplementaryWinnerUnsupported`)으로 바꿨다.
   ⑧ 의 혼합 판정은 ⑫ 와 달리 「승자를 정할 입력이 찼는가」 조건을 두지 않는다 — ⑧ 이 ⑫ 의 상위 집합이어야 「⑧ 통과 ↔ ⑫ 차단」이 생기지 않는다(빈 입력은 자산별 필수 검증이 따로 막는다).
2. **채무 > 증여가액 분모** (`transfer-tax-validate-bg.ts`): 묶음 자산도 단건처럼 엔진 증여가액(담보 승이면 담보평가액)을 분모로 쓴다(`contractAssumedDebtTotal === undefined` 조건 제거).
3. **공용 leaf** `lib/calc/burdened-gift-bundle-winner.ts` — `bgBundleWinnerModes`(⑧)·`bgBundleWinnersMixed`+`bgWinnerDeterminable`(⑫). 두 층이 같은 승자 산출(`companionBurdenedGiftValuations`)을 쓴다.

### 2.2.1 기존 앵커 기대값 갱신 (모두 의도한 변경 — 불변식 「⑧ 통과 ∧ ⑫ 400 = 0」은 그대로)

| 시험 | 변경 |
|---|---|
| CB-1 | 균일 담보·기준시가 담보·임대 쌍의 ⑧ 게이트 2 → 0 |
| CB-2 | ⑧통과·200 8 → 11, ⑧게이트·200 12 → 9 (100/100 조합 3셀) · ⑧게이트·400 32 불변 |
| PB-1 | 주택 담보 쌍 ⑧ 게이트 → 통과 |
| FG-1 / FG-3 | ⑧통과·200·균일 6 → 9 / 7 → 10 (지분 있는 균일 비보충은 계속 ⑧ 게이트) |
| EC-3 | 통과 셀 504 → 792 · 담보 승 통과 36 → 108 (단건 36 + 묶음 2위치 × 36) · falseBlock 0 불변 |

이 PR 의 첫 구현은 혼합 안내에 기존 분류 문구(「함께 양도와 같이」)가 없어 CB-2 가 「⑧ 통과 ∧ ⑫ 400 = 14」로 보였다 — 실제 ⑧ 구멍이 아니라 시험의 분류 기준이었으나, 같은 문구를 안내에 넣어 분류를 보존했다.

### 2.3 풀지 않은 것 (이유)

- **지분 보유 자산의 비보충 승자**: 승자 판정(`bgWholeGiftValuation`)과 ⑤ 칸 노출(`bgCollateralForcesStdAcq`)이 단독 소유만 다룬다. 풀면 ⑤ 는 실지취득가액 칸을 계속 열고 엔진은 취득시 기준시가 × 채무비율을 강제하는 어긋남이 묶음까지 번진다.
- **이월과세 · 조합원입주권 · 겸용주택**: 단건 ⑧ 이 담보 승을 막는 범위(`transfer-tax-validate-bg.ts` 담보 승 차단 · MB-7)와 같다. 묶음에서도 그대로 막는다(임대 승 포함 — 묶음에서 이 조합의 취득가액 처리는 측정하지 않았다).

### 2.4 검증 (`transfer.route.bg-uniform-winner-gate.anchor.test.ts` UW-1~3, 9건)

- UW-1: 일반건물 시가 모드 담보 쌍 · 주택 담보 쌍 · 주택 임대 쌍 — ⑧ 이슈 0 ∧ ⑫ 200 ∧ 증여가액 = ΣA ∧ 양도차익 = 단건 합(±0).
- UW-2: 혼합 승자 ⑧ 1건 ∧ ⑫ 400 / 지분·이월과세·입주권·겸용 — 해당 자산(자산 2)만 차단·사유 문구.
- UW-3: 채무 1.2B ≤ 담보평가액 1.2B 통과 / 채무 1.5B > 1.2B 차단·분모 1,200,000,000원(시가 1.0B 아님).
- 뮤테이션 4종(게이트 원복 · 분모 원복 · 미지원 술어 무력화 · 혼합 차단 제거) 모두 해당 시험이 red, 복원 후 `diff -q` 확인. 회귀: `__tests__/calc`·`api`·`stores`·`tax-engine/transfer` 1,889 파일 통과.

## 3. 이번에 발견했으나 고치지 않은 것

- **기준시가 모드 묶음의 채무 초과**: 주택 기준시가 모드에서 한 자산의 채무가 자기 증여가액을 넘으면(예: 채무 15억 > 기준시가 10억) ⑧ 은 통과하고 엔진이 `EXCESS_BURDENED_GIFT` 로 500 을 낸다. ⑧ 주석 「기준시가 모드의 B/C > 1 검사는 엔진에서 fail-fast」 의 의도된 설계이나, 화면에서는 서버 오류로 보인다. 별건.
- **단건 지분 보유 담보 승**: ⑧ 이 승자를 판정하지 않아(`bgWholeGiftValuation` 100% 한정) ⑤ 가 실지취득가액 칸을 연 채 엔진이 취득시 기준시가를 강제할 수 있다. 이번 PR 이 묶음으로 넓히지 않았을 뿐 단건은 종전 그대로다.
