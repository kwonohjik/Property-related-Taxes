## 0. 한 줄 요약

증축이 있는 일반건물은 실가여도 항상 3-way 엔진(`general-building-extension.ts`)으로 간다. 그 경로에서 **실가 계열 파트(매매 실가·§163⑨ 상속·증여 평가액)의 자본적지출·양도비가 조합에 따라 통째로 사라진다**(⑧ 통과 · 과대과세 방향). 원인은 두 갈래 — 엔진이 파트 가격으로 대체한 파트의 필요경비를 개산공제(실가면 0)로 **덮어쓰고**, 파트 칸이 비면 swap이 실가 카드에 가산하지 않는 **자산총액 판정**으로 빠진다. 2-way 실가 경로(E-2)와 같은 규칙 — 자본적지출 + 양도비 몫을 **더한다**(§97②1호) — 을 swap 파트 축 **단일 경로**로 맞춘다.

## 3. 원인 (file:line — base `de608499a`)

### 3.1 파트 대체 시 필요경비 덮어쓰기
`lib/tax-engine/general-building-extension.ts:353-366` — `landPartApplied`/`buildingPartApplied`(파트 가격 대체)이면 `landExp = partAcq.estimatedDeduction.land`(실가 파트 = 0). 그 앞 `:233-269`(원건물 실가 조합 A/B)가 일괄 필요경비(`actualBundledExpenses`)로 계산한 몫을 **버린다**. 일괄 슬롯에 양도비가 대체값으로 들어온 경우(아래 3.3) 양도비가 함께 사라진다(C1 분리 OFF · 양도비).

### 3.2 swap 자산총액 판정은 실가 카드에 가산하지 않는다
`lib/tax-engine/general-building-entry.ts:259-279` — 파트 축(`resolvePerPart`)은 「두 파트 모드가 다르거나 파트 칸이 명시됐을 때」만. 원건물 두 파트가 **같은 실가 모드**이고 파트 칸이 비면 자산총액 판정(`general-building-swap.ts:152-176`)으로 가는데, 그 판정은 **환산 카드에만** 나목을 배분한다(`estimatedCards`). 실가 카드에는 `addition`(§97②1호 가산)이 없다 ⇒ `capitalExpenditure`·`transferExpense`가 사라진다(매매 분리 ON · 양도비 / C1 · 자본적지출 / 매매 분리 OFF · 자본적지출).

### 3.3 양도비가 두 경로로 갈라져 있다 (W-1a·W-1b 이력)
`lib/calc/transfer-tax-api-gb.ts:383-411` — 증축이면 `bundledExpenses = 일괄 취득 필요경비 || transferExpense || directExpenses`(대체값 사슬) + `bundledExpenseNature`. 같은 파일 `:477-484`(W-1b) — 양도비를 swap 나목에도 싣되 「일괄 슬롯이 소비하지 않을 때만」(환산·분리 ON·일괄 필요경비 입력). 즉 양도비는 **일괄 슬롯(카드에 직접) 또는 나목(swap)** 중 하나로 가는데, 3.1·3.2 때문에 **어느 쪽도 실가 카드에 닿지 않는 조합**이 생긴다:

| 조합 | 양도비가 가는 곳 | 결과 |
|---|---|---|
| 매매 분리 OFF · 일괄 필요경비 없음 | 일괄 슬롯 → 카드(토지·원건물만) | 반영(증축분 0 — Q-2) |
| 매매 분리 OFF · 일괄 필요경비 있음 | 나목 → 자산총액 판정 | 🔴 소실 |
| 매매·C1 분리 ON | 나목 → 자산총액 판정(파트 칸 비면) | 🔴 소실 |
| C1 분리 OFF | 일괄 슬롯 → 3.1에서 덮어쓰기 | 🔴 소실 |

⚠️ 이중계상 이력: 2026-08 W-1b 조사에서 「일괄 슬롯과 나목에 같은 양도비」가 실측 결정세액 131,082,800 → 16,954,949(과소)를 냈다(`transfer-tax-api-gb.ts:424-429` 주석). **설계의 1차 제약은 양도비·자본적지출이 정확히 한 경로로만 가는 것**이다.

## 4. 설계

### D-A (권장) — 실가 계열 파트의 자본적지출·양도비를 swap **파트 축 단일 경로**로

2-way 실가 경로의 `resolvePartExpenses`(E-2)와 같은 규칙을, 3-way에서는 이미 있는 `resolvePerPart` 갈래 3(`mode === "actual"` → `addition`)으로 낸다. 갈래 3은 「나목 = 파트 자본적지출 + 양도비(파트 양도가액 비례)」를 그 파트 카드들에 **가산**한다 — §97②1호 그대로다.

1. **⑭ 엔진 진입(`general-building-entry.ts`)** — 증축이 있고 원건물 두 파트가 실가 계열(`actual`)이면 **항상 파트 축**으로 판정한다.
   - 파트 자본적지출 = 파트 칸(`landDirectExpenses`·`buildingDirectExpenses`) 우선. 칸이 없는 파트는 자산 단위 `capitalExpenditure`를 **취득시 기준시가(토지 : 원건물)** 비율로 나눈 몫(2-way `apportionExpenses`와 같은 축 · §100② 본문 「취득 … 당시」).
   - 양도비 = 자산 단위 `transferExpense` 총액 그대로 넘긴다 — `resolvePerPart`가 파트 양도가액 비례로 나눈다(증축분 카드는 건물 그룹에 들어가 몫을 받는다 → Q-2).
   - ⚠️ 2026-08-13 주석(`general-building-entry.ts:248-254`)이 경고한 「같은 모드에서 파트 축으로 넓히면 자산 단위 자본적지출이 사라진다」는 **위 자산 단위 자본적지출 안분으로 해소**된다(그때는 `resolvePerPart`가 자산 단위 값을 읽지 않았다).
2. **④ API 변환(`transfer-tax-api-gb.ts`)** — 증축 `bundledExpenses` 대체 사슬에서 `transferExpense`를 **뺀다**(`일괄 취득 필요경비 || directExpenses`). 양도비는 항상 나목(`transferExpense`)으로만 보낸다 ⇒ 양도비 경로가 하나가 된다. W-1b 게이트(`:477-484`)는 「증축이면 항상 싣는다」로 단순해진다.
   - `bundledExpenseNature`의 `"transfer"` 값은 더 이상 생기지 않는다. 엔진 분기(`general-building-extension.ts:263`)는 옛 이력 재계산용으로 남겨 둔다(Q-3).
3. **엔진(`general-building-extension.ts`)** — 변경 없음. 3.1의 덮어쓰기는 그대로 둬도 된다: 실가 파트 카드의 `expenses`에는 **일괄 취득 필요경비(자본 성질)·legacy 몫만** 남고, 자본적지출·양도비는 swap `addition`이 단독으로 싣는다(2026-08-13 「같은 지출 두 번 차감」 교훈과 같은 축).
   - 단, 옛 형식 `directExpenses`(두 성질 섞인 덩어리)는 파트 대체 파트에서 3.1 덮어쓰기로 여전히 사라진다(V-2 실측) → Q-5.

### D-B (기각) — 엔진 3.1에서 덮어쓰지 않고 그 자리에서 자본적지출·양도비를 직접 더한다
2-way의 `resolvePartExpenses`를 3-way 엔진 안에 복제하게 된다. 파트 칸이 있으면 swap 갈래 3도 같은 값을 `addition`으로 싣기 때문에 **같은 지출이 두 번 차감**된다(2026-08-13 실측 9,450,000 과소의 재발). 두 경로를 서로 배제하려면 엔진과 swap이 같은 술어를 공유해야 해 D-A보다 복잡하다.
