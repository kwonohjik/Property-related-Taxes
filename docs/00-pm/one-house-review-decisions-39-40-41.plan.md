## 1. #39 — 판정 메뉴: 의뢰인이 바뀌면 남은 판정 결과를 쓰지 않는다 (B)

| 항목 | 내용 |
|---|---|
| 결함(재현) | 세무사 모드에서 결과 화면에 머문 채 헤더 「변경」으로 의뢰인을 바꾸면 `ProfessionalClientGate`가 계산기를 내렸다 올린다. 메모리 store의 옛 결과가 남아 재마운트한 자동저장 효과가 **새 의뢰인 이력**에 저장한다. `?new=1` 재진입도 같은 커밋에서 reset과 저장이 함께 돌아 옛 결과가 저장된다. |
| 처방 | store에 `resultClientId`(판정을 **요청한 시점**의 의뢰인, persist 제외). 지금 의뢰인과 다르면 표시·자동저장·세액 계산 전달에 쓰지 않는다. 의뢰인을 바꾸는 순간(professional store 변경 이벤트) 판정 store의 구독이 결과를 비우고 1단계로 보낸다(입력 유지, 결과가 있을 때만 — 입력 도중이면 단계 유지). `useEffect`로 store에 쓰지 않는다. 늦게 도착한 응답은 요청 시점 의뢰인과 지금 의뢰인이 같을 때만 쓴다. |
| 하위 2(가) | 「화면을 열기 전부터 있던 결과는 자동저장하지 않는다」 — 마운트 시점 결과 참조를 기억해 그것과 다른(이 화면에서 새로 판정한) 결과만 저장한다. 홈 카드 재진입·링크 재진입·의뢰인 전환을 한 장치가 막는다. |
| 하위 3(가) | 한 줄 안내를 두지 않는다. |
| 구현 | `lib/stores/one-house-judgment-store.ts`(구독 포함) · `app/calc/one-house-exemption/OneHouseJudgmentCalculator.tsx`(표시 단계 방어·마운트 시점 결과 미저장) · `lib/calc/history-resume-entry.ts`(필드 초기화) |
| anchor | `__tests__/calc/judgment-calculator-client-isolation-s13-3.anchor.test.tsx`(8건) |
| 범위 밖 | 이미 다른 의뢰인 이력에 잘못 들어간 기존 기록은 정리하지 않는다(별건). |

## 2. #40 — 같은 날 주택 2채 양도: 양도 순서 선택 (A, 하위 1 가 · 하위 2 나)

법문(KoreanLaw 원문 확인, 소득세법 시행령 MST 290841): **§154⑨** 「2개 이상의 주택을 같은 날에 양도하는 경우에는 당해 거주자가 선택하는 순서에 따라 주택을 양도한 것으로 본다.」 **§167의3⑥** 「…같은 날에 양도하는 경우 그 결정방법에 대하여는 제154조제9항의 규정을 준용한다.」

### 2-1. 재현 (master, 비조정·1세대·8억·취득 4억, A 2015 / B 2018 취득, 같은 날 2025-06-01 양도)

| 입력 | 결과 |
|---|---|
| 서로의 명부에 넣음 | 둘 다 과세 **266,079,000** |
| 둘 다 비우고 「없음」 | 둘 다 비과세 **0** |
| A 먼저(B 명부에서 A 제외) | A 과세·B 비과세 **111,166,000** |
| B 먼저 | **121,726,000** |

앞 둘은 어떤 순서로도 나오지 않는 값인데 경고가 없었다. 조건에 적힌 「칩이 효과를 내지 못한다(명부 행이 모두 빠지면 직전 자동 주택 수로 돌아감)」는 이미 `hasDatedHouseRow`(S12-1)로 해소돼 있었다 — 칩으로 유일한 행이 빠져도 stale 스칼라 `"2"`가 아니라 1로 계산됨을 anchor로 고정했다.

### 2-2. 설계 — 14개 동기화 지점

| 지점 | 내용 |
|---|---|
| ① 폼 상태 | `HouseEntry.soldSameDay?: boolean`(같은 날 양도함 표시) · `sameDayTransferOrder?: "first" \| "later"`. 둘 다 optional, 엔진은 모른다. |
| ② initial | 미설정(undefined) — `addHouse()` 팩토리·`createInitial*`는 건드리지 않는다. |
| ③ normalize | 구 저장분에 없는 optional → undefined로 동작 동일(세액 불변). 마이그레이션 불필요. |
| ④ API 변환 | **행을 아예 싣지 않는다** — `housesOwnedAtTransfer`(`lib/calc/household-house-count.ts`)가 `first` 행을 거른다. 같은 날 취득 행과 같은 경로라 주택 수·신규 주택 후보·엔진 명부·조특법 제외 선언·§155⑥1호·⑦·⑧ 행 사실이 함께 빠진다(주택 수 이중 차감 없음). 비과세·중과(§167의3⑥ 준용)가 같은 술어를 쓴다. |
| ⑤ UI | `HouseEntrySameDaySection`(emerald ToggleCard + 순서 RadioCardGroup) — `isOneHouseExemptionAsset` 양도(주택·재개발 신축주택)에서만 연다(입주권 §89①4호 제외). 명부 표 배지. 순서 미선택 + 세대 주택 2채 이상이면 고지(`sameDayOrderNotice`, 「확인 필요」). |
| ⑥ 사이드바 | 판정 메뉴 요약에 「같은 날 먼저 양도(§154⑨)로 제외 N채」. 계산기 사이드바는 금액 합계뿐이라 해당 없음. |
| ⑦ 결과 | `SameDayOrderLine` — 선택으로 뺀 주택을 근거 조문과 함께 표시(양도 단건·일괄·겸용·다건 건별·판정 결과). 선택 출력과 무관하게 인쇄되는 근거 고지로 `PrintSection` 밖. |
| ⑧ validate | 다건 ⑧(`validateMultiSettings`): 같은 날 주택 건 중 명부로 센 세대 주택 수가 1채인 건이 둘 이상이면 차단(서로 먼저를 골라 둘 다 1채가 되는 우회도 막는다). 같은 날 주택 건의 주택 수가 서로 같고 1채가 아니면 비차단 고지. 함께 양도에 같은 날 주택 2채 이상이 묶이면 차단(순서가 결론을 가를 수 있을 때 = 1세대 또는 조정대상지역). |
| ⑨⑩⑫⑬⑭ | 해당 없음 — ④가 행을 빼서 보내므로 Zod·body·route에 새 키가 없다. 다건 차단·함께 양도 차단은 **⑧(화면) 전용**이다 — 서버(⑫)는 같은 입력을 거부하지 않는다(다른 ⑧ 전용 차단과 같은 층위, API 직접 호출자는 종전 동작). |

차단 안내는 「같은 주택을 지분 등으로 나눠 입력했다면 한 건으로 합치세요」를 포함한다. 함께 양도 차단 안내는 다건이 받는 자산이면 「다건의 별도 양도 건」, 막는 자산(재개발 아파트·겸용주택 등)이 섞이면 「주택마다 단건 + 같은 날 다른 주택 행에 칩」으로 가른다. 증여세 부담부증여 화면은 명부가 없어 칩이 닿지 않으므로 「세대 보유 주택 수」 칸에 §154⑨ 안내를 둔다.

### 2-3. 미확인(확인 필요로 남김)

- **같은 날 증여**한 주택에는 이 칩을 쓰지 않는다 — 국세청 회신(2005.9.30.·2007.11.21.) 본문을 확인하지 못했다. 세액을 바꾸지 않는다.
- 비과세와 중과에 순서를 따로 고르는 것(회신 본문 미확인)은 지원하지 않는다 — 한 행의 선택이 두 판정에 같이 닿는다.

## 3. #41 — 다건 건별 명부 어긋남 고지 (A, 하위 1·2·3 가)

건별 명부(Q-9)는 그대로 둔다. 같은 신고의 다른 건과 **양도일 현재 기준**으로 어긋나면 알린다(`lib/calc/multi-roster-parity.ts`, 입력에서 매번 재계산·저장 없음).

| 종류 | 조건 | 처리 |
|---|---|---|
| 누락형 | 다른 주택 건 Q가 `Q 취득일 < P 양도일 < Q 양도일`인데 P 명부에 대응 행(취득일 일치, 소재지가 둘 다 있으면 소재지도 일치)이 없음 | 비차단 고지 |
| 누락형 + 빈 명부(하위 1 가) | P 명부 0행 + 「없음」 확인인데 위 Q가 있고 **소재지로 다른 주택임을 확인**할 수 있음 | **계산 차단**. 소재지를 알 수 없으면 비차단 고지로 맞춘다. |
| 잔존형 | Q가 P 양도일 전에 이미 양도됐는데 P 명부에 대응 행이 남음 | 비차단 고지 |
| 분양권(하위 2 가) | 분양권 양도 건이 P 양도일 현재 보유 중이었는데 P의 분양권·입주권 목록에 취득일이 같은 행이 없음 | 비차단 고지(빈 목록 「없음」은 기존 결정 그대로, 새 확인·차단 없음) |

- 소재지가 같은 건(같은 주택의 지분 분할 매각)은 대조에서 뺀다.
- 설정 단계와 결과 화면(하위 3 가) 모두 `MultiRosterNotices`를 쓴다.
- 재현: 누락형 **0** / 정답 **111,166,000** / 잔존형 **266,079,000**. 분양권 축은 재현 확인 — 목록에 넣으면 111,166,000, 빠뜨리면 0.
- 문구 정리: 명부 머리글 「(정밀 중과세 판정용, 선택)」을 두 메뉴 공통 「(양도일 현재 보유 기준)」으로, 입주권·주택 분기의 「없음」 확인 칸에 「양도일 현재」를 넣고, 없는 이름 「세대 보유 주택 목록」을 실제 머리글 「다른 보유 주택 목록」으로 통일했다(고지·결과 문구 포함).

### 추적 항목 (별건)

- **세대 단위 명부 공유**(Q-9가 미룬 별건) — 건과 명부 행을 명시적으로 연결하는 일까지 묶는다. 연결되면 취득일·소재지 휴리스틱 대응(`rowMatches`)과 상대 건 자동 대조가 불필요해진다. 일정 없음.
- **§104⑤ 크로스 재계산 경로**(`cross-104-5-recalc`)는 이번 대조 범위 밖이다 — `validateMultiSettings`를 타지 않는다.
- 서버(⑫) 쪽 같은 날 주택 차단은 두지 않았다 — 화면 ⑧ 전용.
