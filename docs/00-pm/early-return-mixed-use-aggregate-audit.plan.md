## 3. 발견

- **F-1 겸용주택: 결함 없음.** 정상 분기 전부와 컴패니언 집계가 단건과 같은 값을 낸다. 거부 분기는 설계상 전용 카드다. **세액·표시 모두 불변.**
- **F-2 다건 집계의 다필지 자산 행 필요경비 흡수(Q-1).** 원인: `resolveDisplayAcquisitionAndExpense`(`transfer-tax-aggregate-display-echo.ts`)는 취득가액을 `singleInput.acquisitionPrice`(다필지 요청은 자산 단위 칸이 0)에서 읽고 필요경비를 `양도가액 − 취득가액 − 양도차익`으로 **역산**한다 — 다필지 결과의 `parcelDetails`·`expenses`를 보는 분기가 없다. 그래서 취득가액 전부가 필요경비로 들어간다. 신고서 항등식은 역산이라 **성립해 오류를 가린다**(`feedback_early_return_branch_skips_pipeline_stages`와 같은 함정). **세액 불변.**
  - 닿는 경로: **화면은 막힌다** — ⑧ `multi-transfer-tax-validate.ts:172`가 「다필지 토지는 단건 계산기에서만 지원됩니다.」로 차단한다. 그러나 ⑫ `MULTI_REJECT_RULES`(`transfer-tax-schema-multi-refines.ts:40`)에는 `parcels` 규칙이 없고(같은 파일 grep 0건) 라우트 스키마는 `parcels`를 받으므로(`transfer-tax-schema-base-shape.ts:332`) **직접 API 호출은 200으로 계산된다**(R1). 다건 다필지를 보내는 기존 테스트는 0건이다 [직접: grep `__tests__`·`e2e`].
  - 세액이 단건과 같은지(기본공제 1회·세율군 분리 등 합산 맥락)는 재지 않았다 — 양도차익만 단건과 같다(394,000,000) [확인 필요].
- **F-3 (정상) 비과세·#3310 전파.** 단건 비과세 수정(`estimatedStdPrice*`·§164⑨ 상세 3종)이 집계에 그대로 실린다.

## 4. 수정안

- **Q-1 (다건 다필지 F-2)**
  - **a (권고)** ⑫ `MULTI_REJECT_RULES`에 `parcels` 거부 규칙 추가 — ⑧ 문구와 같은 사유(「다필지 토지는 단건 계산기에서만 지원됩니다.」). 직접 API가 400이 되어 ⑧≡⑫가 맞는다. 기존 선례 `transfer.route.multi-single-only-keys-f12.anchor.test.ts`(단건 전용 키를 ⑫가 거르는 패턴)와 같은 모양. 규모: `transfer-tax-schema-multi-refines.ts` 한 곳 + anchor(400 확인 + 단건 불변) + 계획서 결과 절. 약 1시간. 위험: 다건 다필지를 직접 API로 쓰는 외부 호출자가 있다면 400이 된다 — 저장소 안에는 호출 테스트·화면 경로가 없다 [직접].
  - b 집계 echo가 다필지 결과를 읽는다 — `resolveDisplayAcquisitionAndExpense`에 `parcelDetails` 분기(취득가액 = Σ 필지 취득가액, 필요경비 = 결과 `expenses`)를 추가. 약 1.5시간. 화면이 막힌 경로를 «지원하는 것처럼» 열어 두고, 합산 세액 정합(기본공제·세율군)은 미검증이라 그 위험은 남는다. 위 a와 같이 하면 중복이다.
  - c 현행 유지·한계 기록 — 화면 경로가 없고 세액은 정확하다. 직접 API 호출자에게만 신고서 표시가 틀린다.
