## 0. 측정 방법(이 계획서의 모든 수치)

**측정 절차**는 선행 계획서 §0과 같다.
- 측정 훅은 워크트리 복사본 `node_modules/@playwright/test/index.js`에만 임시로 넣었다. 끝날 때마다 원본으로 되돌리고 `cmp`로 확인했다.
- 전체 E2E 각 테스트의 **종료 화면**에서 글자를 직접 가진 요소마다 대비를 쟀다. 글자색과, 조상 배경을 투명도까지 겹쳐 계산한 바탕색 사이의 WCAG 대비다. 기준은 일반 글자 4.5다. 측정 동안 `transition`·`animation`을 껐다(중간값 함정).
- 수정안은 같은 종료 화면에서 inline style로 적용했다가 되돌리며 다시 쟀다(모사). 글자마다 전후를 짝지어 **나빠진 글자**(4.5 이상 → 미만)도 셌다. 측정 순간 테마가 라이트로 바뀌지 않은 화면은 건너뛰도록 했다(이번 실행에서 0화면).

**측정 실행**(모두 master `d37e685eb` 기준)

**한계**
- E2E가 도달하는 화면과 상태만 쟀다. 그 밖은 미측정이다.
- 「회」는 종료 화면 × 글자 요소의 연인원이다. 고유 위치 수가 아니다.

- 큰 글자(기준 3)는 따로 가르지 않았다.

## 3. ③ 다크 모드로 둔 채 인쇄 — 원인과 수정(실측 A·C)

### 3-1. 원인

- next-themes가 `<html>`에 `.dark`를 붙인다(`attribute="class"`). 인쇄할 때도 그대로 남는다.
- 다크 변형은 `@custom-variant dark (&:is(.dark *))`(`globals.css:5`)라서 매체를 가리지 않는다. 다크용 변수 블록 `.dark { … }`(`globals.css:86~118`)도 마찬가지다.
- 인쇄 규칙(`globals.css:199~`)에 색 처리가 없고, `body`에 `print-color-adjust: exact`(`:214~215`)가 있어 배경색까지 그대로 인쇄된다.

**실측 A**: 인쇄 UI가 있는 화면 1,142 중 **1,124화면이 인쇄+다크에서 배경 면적 90% 이상이 어둡다**(전체 97.7%, 인쇄+라이트는 0.6%). 실제 PDF로 뽑으면(크롬 기본값, 배경 그래픽 끔) 종이는 희고 글자는 다크용 밝은색이라 제목·라벨이 거의 보이지 않고, 배경을 가진 카드는 검은 덩어리로 나온다(PDF로 뽑아 이미지로 확인 — 저장소 밖 측정 산출물).

> `react-pdf`로 만드는 PDF 다운로드는 DOM·CSS와 무관해 영향이 없다.

### 3-2. 수정안

| 안 | 내용 | 규모 | 실측 |
|---|---|---|---|
| **P1** | 다크 변형과 다크 변수 블록을 `@media screen` 안으로 넣는다 → 인쇄할 때는 `.dark`가 있어도 라이트 스타일 | `globals.css` 2곳(+9 −1줄) | **C 전체 측정** |
| P2 | `beforeprint`/`afterprint`에서 `<html>`의 `.dark`를 잠깐 뗐다 붙인다 | JS 1곳 | 미측정. React 재렌더·next-themes 상태와 엇갈릴 수 있음(확인 필요) |
| P3 | 요소마다 `print:` 라이트 클래스를 붙인다 | 다크 짝 수천 곳 | 기각 — 지금 `print:` 사용 376곳으로도 덮지 못한다 |

**P1 변경**

```css
/* globals.css:5 */
@custom-variant dark {
  @media screen {
    &:is(.dark *) {
      @slot;
    }
  }
}

/* globals.css:86~118 */
@media screen {
.dark { /* 다크 변수 그대로 */ }
}
```

**P1 실측(C, 2,539화면 — A와 같은 화면끼리 짝지음)**

| 항목 | 수정 전(A) | P1(C) |
|---|---|---|
| 인쇄+다크 어두운 배경 면적 | 97.7% | **0.4%** |
| 인쇄+다크에서 90% 이상 어두운 화면 | 1,124 / 1,142 | **0** / 1,142 |
| 인쇄+다크 = 인쇄+라이트인 화면(4.5 미만 수·어두운 면적 모두 같음) | — | **1,140 / 1,140** |
| 화면 다크 4.5 미만 | 90 | 55 |
| 화면 라이트 | — | 같은 화면 2,534 중 차이 148(아래) |

- 화면 다크 90 → 55의 차이 35는 전부 두 화면(`transfer-validation-field-jump` 「unsold_98_3 5년 시점 기준시가」 9 → 0, 「보유 주택 최초 분양계약일」 26 → 0)이다. A에서 측정 순간 테마가 바뀌지 않았던 화면으로 이미 확인한 것이다(§4). 나머지 화면의 다크 값은 모두 같다.
- 화면 라이트 차이 148화면 중 136화면은 끝난 순간 글자 수 자체가 다르다(측정 순간 차이). 같은 제목 테스트가 여러 개라 짝이 불확실한 것이 3화면이다. 글자 수가 같은데 4.5 미만이 다른 것은 9화면이고, 1~3회씩 양방향(2→5, 4→1 등)이다. P1은 `.dark`가 있을 때만 걸리는 규칙이라 라이트 화면에는 닿지 않는다.
- PDF 확인: P1에서 다크 상태로 뽑은 PDF가 라이트와 같게 나왔다. 같은 화면의 화면 다크 캡처는 수정 전과 같았다(둘 다 저장소 밖 측정 산출물).
- `dark:print:`·`print:dark:` 조합 사용처는 0곳이다. `shadcn/tailwind.css`·`tw-animate-css`에는 다크 규칙이 없다. `.dark`를 JS로 읽는 곳은 `components/theme-toggle.tsx`(아이콘 전환)뿐이다.

**P1의 결과로 잃는 것**: 다크 화면 그대로 인쇄하는 선택지가 없어진다. 인쇄물은 늘 라이트다.

## 4. ② 다크 톤 카드 위 회색 글자 — 제외(재현 안 됨)

A에서 다크 4.5 미만은 90회였다.
- 비활성 컨트롤 34
- 다크에서도 흰 바탕을 유지하는 서식(`WHITE_FORM`) 안 21
- 두 화면(`transfer-validation-field-jump.spec.ts`)의 35 — 그 화면만 3회 다시 돌리니 다크 0이었다. 측정 순간 테마가 아직 라이트였던 것이다. C에서도 두 화면 모두 0이다.

톤 카드 위 회색 글자(4.2~4.49)는 위 두 화면에서만 나왔다. 실제 결함이 아니므로 이 계획에서 뺀다.

## 6. 검증 계획

- **전체 E2E 측정**(A와 같은 훅): 라이트 4.5 미만이 모사 B와 같은 수준(≈241, 비활성 36 포함)인지, **나빠진 글자 0**인지, **다크 화면이 변하지 않았는지**(A 다크 90 − 측정 순간 2화면 = 55 수준).
- **인쇄**: 인쇄+다크 = 인쇄+라이트를 다시 확인. 실제 PDF 1장(다크 상태)을 눈으로 확인.
- **회귀 E2E**
  - 라이트: `e2e/_helpers/dark-contrast.ts`를 테마 인자를 받게 넓히거나 라이트용 도우미를 둔다. 반올림 없이 잰다(4.497 함정). 대상: 섹션 「✓」(`emerald-600`), `ValidationIssuePanel` 문구(오류색), 옅은 톤 카드 위 회색 안내 글자, 신고서 표의 `text-slate-500` 글자.
  - 인쇄: 다크로 둔 채 `emulateMedia({ media: "print" })` → `body` 배경이 흰색이고 결과 화면 글자 대비가 4.5 이상인지.
- **뮤테이션**: 토큰을 원래 값으로, 치환한 클래스 하나를 원래 값으로, P1의 `@media screen`을 지운 상태로 각각 되돌려 위 회귀가 실패하는지 확인한다.
- **pre-push 게이트**: 워크트리에서는 husky가 돌지 않으므로 폰트·톤·다크 짝·워크플로 러너·typecheck·lint·`npm test`를 수동으로 돌린다.
