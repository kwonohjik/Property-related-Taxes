### 1.2 원인

- 축 B: `general-building-fractional.ts`가 결과 상세를 직접 조립하면서(`:267`) 단건 경로(`general-building-route-helper.ts:300`)가 싣는 `partDirectAddition`·`partBeforeExtensionCapex`를 싣지 않는다. 또 `remapGbSwap`(`general-building-part-cards.ts`)이 `allocation`·`addition`만 접미사로 다시 맵핑하고 `beforeExtensionAddition`은 맵핑하지 않는다.

### 1.3 설계

- **D-1 (축 B)**: 지분 루프에서 지분별 `swap.addition`·`swap.beforeExtensionAddition`(접미사 맵핑 후)을 모아 결과 상세에 `partDirectAddition`·`partBeforeExtensionCapex`로 싣는다. `remapGbSwap`에 `beforeExtensionAddition` 맵핑을 추가한다. 산식 빌더는 그대로(접미사 카드 id를 이미 인식한다 — S3에서 증축분 카드를 `building2#0`으로 알아봤다).
- **D-2 (함께 양도)**: Q-1.

## 2. L2 — 서버가 빈 「증축 전」을 거절하지 않는다

### 2.1 실측

| 시료 | ⑧(화면) | ⑫(서버 · 필수 규칙을 임시로 넣은 상태) |

- 관찰 O-1(별건 · 증축과 무관): 분리 OFF인데 숨은 건물 파트 칸(`buildingDirectExpenses`)에 값이 남아 있으면 ④가 싣고 엔진이 공제한다 — 증축 없음 시료 세액 251,130,000(잔존 2천만) vs 257,010,000(빈 칸) · ⑧ 통과. 분리 OFF 전환 patch(`transfer-tax-gb-toggle-patches.ts:67`)가 칸을 비우므로 화면 조작으로는 생기지 않는다 — 옛 저장 이력·다른 진입 경로로 생기는지는 확인 필요.

### 2.2 원인

⑫는 화면의 분리 ON/OFF·부담부증여 숨김을 모른다(payload에 분리 여부가 없다). ④는 자본적지출 금액을 칸이 숨었어도 싣는다. 그래서 ⑫가 「금액이 있으면 증축 전 칸 필수」를 걸면 ⑧이 칸을 요구하지 않는 자리(숨은 칸)에서 갈린다.

### 3.1 확정 (2026-10-23)

- **Q-1 b** — 이번엔 축 B(지분 분할)만. 함께 양도 일반건물 결과 산식 전체 공백은 별건 계획서로 둔다.
- **Q-2 a** — ④가 증축 자산의 자본적지출 금액을 칸이 쓰이는 자리에서만 싣고(`gbCapexBeforeExtensionSlots`), ⑫는 「증축 + 금액 있음 + 증축 전 키 없음 → 400」.
- **Q-3 a(권장 b 대신 · 사용자 결정)** — O-1도 이번 범위. 일반건물 화면은 파트 자본적지출 칸을 **분리 ON의 파트 카드에서만** 그린다(`GeneralBuildingAcquisitionCards`가 `CompanionAcqPurchaseBlock`에 `hasSeperateLandAcquisitionDate={false}`를 넘겨 그 블록의 분리 섹션은 일반건물에서 렌더되지 않는다 · `PartAcqModeField`는 `isSeparate`일 때만). ⇒ ④가 분리 OFF면 `landDirectExpenses`·`buildingDirectExpenses`를 싣지 않아도 화면과 어긋나지 않는다(숨은 칸 값만 계산에서 빠진다).
