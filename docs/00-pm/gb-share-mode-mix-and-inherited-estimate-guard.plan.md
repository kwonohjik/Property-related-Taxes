## S-1. 지분 분할 취득에서 지분마다 실가·환산이 섞이면 계산이 막힌다 (⑧ 통과 ↔ ⑫ 400)

### 1. 현상 — 실측 (2026-10-23 · 폼 → ⑧ `collectStepIssues` · ④ `callTransferTaxAPI` 본문 → route POST · mock 세율)

같은 일반건물을 50%씩 두 번 취득했다. 토지 205㎡ · 건물 300㎡ · 양도가 16억.

| 시료 | 지분 1 / 지분 2 | ⑧ 문제 | route | 오류 칸 |
|---|---|---|---|---|
| M1 | 실가 상속(1988) / 환산 매매(2010) | **0건** | **400** | `buildingArea` |
| M2 | 환산 매매 / 실가 상속 | 0건 | 400 | `buildingArea` |
| M3 | 실가 매매 / 환산 매매 | 0건 | 400 | `buildingArea` |
| M4 | M1 + 최초공시(§99-164-10) | 0건 | 400 | `buildingArea` + `hasFirstDisclosure`·`firstDisclosurePrice`·`firstDisclosureLandStdPrice`·`firstDisclosureBuildingStdPrice` |

- 오류 문구는 「지분 간 물건-수준 값이 다릅니다(buildingArea). 면적·양도시 기준시가·용도지역·물건 사건은 전 지분 동일해야 합니다.」다. 사용자는 두 지분에 같은 면적을 넣었고(지분 2는 지분 1의 물건 값을 복사한다 — `mergeGbPropertyLevel`), 고칠 칸이 화면에 없다 — **막다른 길**이다.
- **고친 뒤 모사** — 실가 지분 본문에 `buildingArea: 300`을 넣어 다시 POST했다.
  - M1~M3은 200이다.
  - 지분별 카드가 **같은 조건의 50% 단건과 원 단위까지 같다**:
    - M1 지분 1 = 「실가 상속 50%」 단건: 토지 취득가 150,000,000 · 차익 500,833,744 / 건물 75,000,000 · 74,166,256
    - M1 지분 2 = 「환산 매매 50%」 단건: 토지 118,032,960 · 529,725,784 / 건물 86,365,581 · 60,550,675
  - 결정세액: M1·M2 305,601,279 · M3 283,551,279.
  - ⇒ 엔진은 혼합을 이미 맞게 계산한다. **막는 것은 ⑫의 동일성 검사뿐**이다.
- M4는 `buildingArea`만 넣어서는 여전히 400이다(최초공시 4칸).

### 2. 원인

- ④ `buildGeneralBuildingValuation`(`lib/calc/transfer-tax-api-gb.ts`)은 지분마다 경로를 고른다.
  - 실가 경로 본문(`:553~`)은 `buildingArea`를 싣지 않는다. 환산 경로(`:349·362`)는 싣는다.
  - 최초공시 4칸은 `gbHasFirstDisclosure && anyEstimated`일 때만 싣는다(`:536`). 실가 경로에 실으면 엔진이 실가 취득가액을 환산주택가격으로 조용히 바꾸므로 일부러 막은 것이다(같은 곳 주석 · 2026-08-13).
- ⑫ `GB_SHARE_PROPERTY_LEVEL_PATHS`(`lib/api/transfer-tax-building-share-schemas.ts:26`)는 이 키들을 **모든 지분 쌍**에서 같아야 한다고 본다(`:127-137`). 한쪽이 「그 경로가 안 쓰는 값이라 안 실은 것」과 「값이 다르다」를 가르지 않는다.
- `buildingArea`는 엔진이 읽지 않는다 — 저장소 전체에서 타입 선언(`general-building.types.ts:79`)·Zod(`transfer-tax-building-schemas.ts:154`)·이 동일성 목록에만 나온다.

### 3. 설계 — Q-1에 따른다

- **a (권장) ⑫ 비교를 「그 값을 쓰는 지분끼리」로 좁힌다.**
  - 환산 경로만 쓰는 키(`buildingArea` · 최초공시 4칸)는 `actualPriceMode !== true`인 지분끼리만 비교한다.
  - 나머지 키는 종전대로 전 지분 쌍을 비교한다.
  - ④는 바꾸지 않는다 — 최초공시를 실가 지분에 싣지 않는 2026-08-13 결정을 그대로 지킨다.
- b ④가 실가 지분에도 `buildingArea`를 싣고, 최초공시는 ⑫에서만 경로별로 비교한다. 결과는 a와 같지만 고치는 층이 둘로 나뉜다.
- c ⑫를 「양쪽에 다 있을 때만 비교」로 바꾼다. 가장 짧지만 **값이 버그로 빠진 경우도 통과시켜** 검사가 약해진다.

### 4. 확인 필요

- 축 B에서 최초공시 입력은 **주 자산 폼**의 값을 전 지분이 복사한다(`mergeGbPropertyLevel` — `GB_PROPERTY_LEVEL_FORM_FIELDS`). 화면의 최초공시 칸은 주 자산의 산정방식으로 열린다(`isGbFirstDisclosureApplicable`).
- 그래서 주 자산이 실가이고 지분 2가 환산이면, 지분 2에 필요한 최초공시 칸이 화면에 안 보일 수 있다. 반대로 주 자산에 남은 옛 값이 지분 2에 실릴 수도 있다.
- 구현 때 화면으로 실측한다. 결함이면 이 PR에서 노출 조건을 「환산 지분이 하나라도 있으면」으로 맞춘다(3중 패턴 ⑤·④·⑧).

## S-2. 상속·증여 파트의 추계(환산·감정·매매사례) — ⑫가 받아 계산한다 (API 직접 호출 한정)

### 1. 현상 — 실측

상속(1988 · 토지·건물 모두 · 분리 OFF · 평가액 토지 3억 · 건물 1억 5천만)에 옛 추계 플래그(`useEstimatedAcquisition: true`)가 남은 폼.

| 층 | 동작 |
|---|---|
| ⑤ 화면 | 상속·증여 카드에는 산정 방식 라디오가 없다. 분리 ON 파트 라디오는 상속·증여 파트에 「실거래가」 하나만 준다(`gbPartAllowedModes`). 원인을 바꾸면 같은 배치에서 플래그를 비운다(`gbUnifiedSec1639ClearPatch` — G3) |
| ③ 복원 | `migrateAsset`이 같은 patch로 비운다(`calc-wizard-asset-migrate.ts:599`) |
| ⑧ 검증 | **막는다** — 「상속으로 취득한 토지는 취득가액을 환산취득가·감정가액·매매사례가액으로 산정할 수 없습니다 … (소득세법 §97①1호 단서·같은 법 시행령 §163⑨)」(`transfer-tax-validate-gb.ts:156`). 분리 ON·증여도 같다 |
| ④ 변환 | 그대로 `landAcqMode: "estimated"`를 싣는다 |
| ⑫·엔진 | **받아서 환산으로 계산한다** — 토지 취득가 236,065,921(평가액 300,000,000 대신) · 결정세액 **310,092,558**(정상 301,110,000 · +8,982,558). 분리 ON 토지만 추계면 318,098,519 |

- ⇒ **화면으로는 도달하지 않는다**(⑤·③·⑧ 세 겹). API를 직접 부르거나, 앞의 세 겹 중 하나가 회귀했을 때만 엔진이 법령과 다른 취득가액으로 계산한다. 「⑧은 막는데 ⑫는 받는」 비대칭이다(memory `feedback_fe8_vs_12_parity_grid`).
- 결과 카드 §163⑨ 블록의 「다만 1985.1.1. 전 상속 파트는 …」 문장이 1988 상속에 붙던 것(`gb-fractional-result-blocks.plan.md` §8)도 이 상태에서만 생긴다. 이 PR로 그 상태가 엔진에 닿지 않게 되면 함께 사라진다.
- ⚠️ 정정: 첫 실측에서 「분리 OFF 상속은 ⑧이 막지 않는다」고 기록했다. 그것은 probe 오류였다 — 검증 전에 부른 `migrateAsset`이 폼 객체를 **제자리에서** 고쳐 플래그를 지웠다. 다시 재 보니 ⑧은 막는다.

### 2. 설계 — Q-2에 따른다

- **a (권장) ⑫ superRefine 방어선.**
  - 일반건물 평가 객체에서 토지가 상속·증여인데(`acquisitionByInheritance` · 증여 표지) `landAcqMode`가 `actual`이 아니면 400을 낸다. 건물도 같다. 문구는 ⑧과 같다.
  - 의제취득일 전 상속은 ④가 파트 모드를 `actual`로 보내고 ①②③ 재선택을 별도 필드로 한다(실측 PRE 단건: `landAcqMode`·`buildingAcqMode` = `actual`, `actualPriceMode: true`). 그래서 이 규칙과 충돌하지 않는다 — anchor로 고정한다.
- b 기록만 하고 고치지 않는다(화면 도달 0).

### 3. 확인 필요

- 증여 표지의 ⑫ 키 이름·의제취득일 전 증여의 파트 모드는 구현 때 ④ 본문으로 실측해 정한다.
- 축 B 지분 본문(`generalBuildingShares[].valuation`)도 같은 평가 객체 스키마를 거치는지 확인한다(거치지 않으면 지분 스키마에도 같은 규칙).

## 8. 구현 기록 — S-1 (2026-10-23)

- **⑫** `GB_SHARE_ESTIMATED_PATH_ONLY`(`buildingArea`·최초공시 4칸)는 환산 지분끼리만 비교한다. 기준은 첫 **환산** 지분이다. 나머지 키는 종전대로 전 지분 쌍을 비교한다.
- **§4 실측 결과 — 결함이었다.**
  - 최초공시 토글은 주 자산 카드에만 있다(`!shareAcquisitionOnly`). 열리는 조건도 주 자산의 산정방식뿐이었다(`GeneralBuildingBlock.tsx` `fdApplicable`).
  - 그래서 주 자산이 실가이고 지분 2가 환산이면 칸이 없었다.
  - 고침: 순수 함수 `isGbFirstDisclosureApplicableForProperty`(`gb-first-disclosure.ts`)를 ⑤·⑧이 공유한다.
    - ⑤: `CompanionAssetsSection` → `CompanionAssetCard` → `AssetSectionAcquisition` → `GeneralBuildingBlock`이 주 자산 카드에만 전 지분을 전달한다.
    - ⑧: 지분 분할이면 주 자산은 물건 단위로, 둘째 이후 지분은 검증하지 않는다.
    - ⑧은 지분 카드에 주 자산의 물건 단위 값을 덮어쓰고 검사한다(`axisBEffectiveAsset`). 그래서 종전에는 주 자산 토글의 빈칸 오류가 **칸이 없는 지분 2 카드에도 중복으로** 떴다. 이제 자산 1에서 한 번만 뜬다.
  - ④는 바꾸지 않았다 — 최초공시를 실가 지분에 싣지 않는 2026-08-13 게이트를 유지한다.
  - ① 기본정보의 이정표 문구(`GeneralBuildingConversionSection.tsx:218`)는 아직 주 자산의 산정방식만 본다. 「③ 취득정보에 있습니다」라는 안내라 계산과 무관해 남겼다.
