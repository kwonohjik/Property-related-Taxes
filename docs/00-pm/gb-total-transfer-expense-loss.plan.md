## 2. 재현 (probe 실측)

### 2.1 픽스처
- **F1**: 일반건물 분리 ON · 양도 2026-02-16 · 양도가액 1,600,000,000 · 토지 205㎡ × 5,514,000(양도시 기준시가 1,130,370,000) · 건물 259,072,400 · 토지 취득 2005-05-01 실가 400,000,000 · 건물 취득 2010-05-01 200,000,000. 「혼합」= 토지 실가 + 건물 감정. 개산공제: 토지 6,150,000 · 건물 4,500,000(지분 60/40 은 3,690,000·2,460,000 / 2,700,000·1,800,000).
- **축 B**: 같은 일반건물 지분 60/40 두 카드(`assetSplitMode: "fractional"`).
- **함께 양도**: 일반건물(양도가액 1.6B) + 토지(0.4B), `bundledSaleMode: "actual"`, 계약 총액 2,000,000,000 → 일반건물 80% · 토지 20%.

- 오라클 = 두 카드 양도비 칸에 5,000,000(또는 1,500,000,000)을 각각 입력. 지분 비율로 줄어 카드1 3,000,000(= 5,000,000 × 0.6)·카드2 2,000,000 이 되고 토지 비율 0.8135 로 파트에 나뉜다 — **총 양도비 한 번 입력 ≡ 각 카드 100% 기준 입력** 이 곧 UI 약속(「자동 안분」)이다.
- 요청 본문 실측: 총 양도비 경로는 최상위 `transferExpense: 3,000,000` 만 싣고 `capitalExpenditure` 키가 없다. 카드 입력 경로는 `capitalExpenditure: 0` 과 `transferExpense: 3,000,000` 을 함께 싣는다. 두 경우 모두 `generalBuildingShares[].expenses` 는 0 이다.

## 3. 원인 · 데이터 흐름

1. **일반건물은 양도비를 자기 서브객체로 받는다.** 단건·지분·컴패니언 모두 ④-gb 가 `generalBuildingValuation.capitalExpenditure`·`transferExpense` 를 싣고(`transfer-tax-api-gb.ts:447-449,517-518`), 라우트가 그 payload 에서 읽는다(`general-building-route-actual.ts:75,94`). 최상위 `transferExpense` 는 토지·주택 등 일반 경로가 읽는다.
2. **A (축 B)**: 지분 빌더는 카드마다 `buildGeneralBuildingValuation(merged)` → `applyShareScale(valuation, ratio)` 로 만든다(`transfer-tax-api-gb-shares.ts:258-262`). `merged` 의 `transferExpense` 는 그 카드의 자산 칸이라 총 양도비가 들어갈 자리가 없다. 호출부 `transfer-tax-api-primary-context.ts:192` 는 `form.totalTransferExpense` 를 넘기지도 않는다. 총 양도비 유효값(`effectiveTransferExpenseFor` — `transfer-tax-api-asset-basics.ts:213-227`)은 최상위 필드로만 간다(`transfer-tax-api.ts:357-362`).
3. **B (함께 양도)**: 안분 엔진은 공통 몫을 자산별 `allocatedExpenses = direct + commonShare` 로 합쳐 낸다(`bundled-sale-apportionment.ts:210-226,246`). 일반건물 컴패니언 빌더는 이를 `engine.expenses` → `legacyExpenses` → `buildGbPartCards(…, actualExpenses)` 로 받는다(`general-building-part-cards.ts:322`).
   - 실가 분기(`actualPriceMode`): `effectiveExpenses = declaredExpenses > 0 ? declaredExpenses : actualExpenses`(`general-building-route-actual.ts:94-95`) — 선언 채널(자본적지출·양도비 칸)이 있으면 **legacy 가 통째로 후퇴**해 공통 몫이 사라진다(③).
   - 환산·혼합 분기: `buildEstimatedGeneralBuildingCards(estimatedPayloadOf(gbv))`(`:195`)는 `actualExpenses` 를 증축 주입(`extensionBundledInjection`)에서만 쓴다. 공통 몫이 payload 어디에도 실리지 않는다(①②).
4. 같은 구조의 선례: `gb-estimated-carryover-scenario-a-capex.plan.md` §2.6 은 이월과세 A 에서 같은 `allocatedExpenses` 가 버려지는 것을 보았고 Q-5 로 분리했다. 이 계획서는 그것이 **비-이월과세 혼합·환산·선언 채널에서도 재현**됨을 확인한 것이다.

## 4. 법령 근거 (해석 쟁점 없음)

- 「소득세법」 제100조 제2항 **후문**: 「이 경우 **공통되는 취득가액과 양도비용은 해당 자산의 가액에 비례하여 안분계산한다.**」 — 토지와 건물 등을 함께 양도하면 공통 양도비용은 자산 가액 비례로 나뉜다. 총 양도비는 정의상 「공통되는 양도비용」이다.
- 같은 법 제97조 제2항 제1호: 취득가액을 실지거래가액으로 하는 경우의 필요경비는 「… **제1항제2호 및 제3호의 금액을 더한 금액**」(자본적지출·양도비 가산) — 실가 파트 몫은 가산.
- 같은 항 제2호 본문·단서: 추계(감정가액·매매사례가액·환산취득가액)는 「… 금액에 자산별로 대통령령으로 정하는 금액을 더한 금액」(개산공제), 환산취득가액은 가목(환산취득가액 + 개산공제)이 나목(제1항제2호·제3호의 합)보다 적으면 나목 선택 — 감정·매매사례 파트 몫은 버려지고 환산 파트 몫은 비교.
- 따라서 법문이 정하는 결과는 §2 의 **오라클**이다(자산 칸으로 넣은 것과 같다). 법문이 명확하므로 질의·해석례 불요(메모리 `feedback_clear_statute_needs_no_ruling`). 이 계획서는 새 조문을 인용하지 않는다 — §100·§97 은 `verify:legal` 매니페스트에 이미 있다(`TRANSFER.COMMON_EXPENSE_APPORTION` 등 #2697).

## 5. 수정안

### 5.1 A — 축 B 지분 (④ 한 곳)
- `buildGeneralBuildingShares(assets, transferDate, declaredMode, totalTransferExpense?)` 에 **적용되는 총 양도비**(`appliedFormTotalTransferExpense(form)` — 칸이 화면에 있는 경우만, `transfer-expense-in-scope.ts:27-29`)를 받는다. 호출부 `transfer-tax-api-primary-context.ts:192` 에서 넘긴다.
- 카드의 자산 칸 `transferExpense` 가 0·빈 값이고 총 양도비 > 0 이면 `merged = { ...merged, transferExpense: String(총 양도비) }`(100% 기준)로 만든 뒤 기존 `applyShareScale` 이 × 지분율을 한다 → `effectiveTransferExpenseFor` 의 「폼 총액 × ratio」(`asset-basics:223-225`)와 같은 값. 자산 칸이 있으면 그것이 우선(`:219-222`) — 폼 규칙이 총 양도비가 있으면 자산 칸을 비우므로(`withInScopeTransferExpenses`) 실제로는 겹치지 않는다.
- 계약 총액 ≠ 지분 합 등 다른 입력은 건드리지 않는다. 14 지점: ④ 한 곳만(⑫ Zod 의 `generalBuildingShares[].valuation.transferExpense` 는 카드 입력이 이미 쓰므로 변경 없음 · ⑧ 변경 없음 · ⑭ 변경 없음).

### 5.2 B — 함께 양도 (안분 출력 확장 + 컴패니언 빌더, 서버)
- `apportionBundledSale` 출력에 **공통 몫만** 담은 필드(`allocatedCommonExpense`)를 추가한다(`bundled-sale-apportionment.ts:210-226` 에 `commonShare` 가 이미 있다). `allocatedExpenses` 의미(= 직접 + 공통)는 그대로 둔다 — 소비처 다수.
- `buildGbCompanionItems`(와 주 자산이 일반건물인 `bundled-route.ts:262` 호출)가 이 공통 몫을 받아 **`gbv.transferExpense` 에 합산**하고 legacy `engine.expenses` 에서는 같은 몫을 뺀다(이중계상 방지). 이로써 실가·환산·혼합 모두가 자산 칸 양도비와 **같은 경로**로 파트에 나뉜다(§2.3 오라클이 곧 기대값).
- **legacy 직접분 보호**: 분리 OFF 일반건물 실가 일괄의 이전 형식 `directExpenses` 는 그대로 legacy 로 남아 선언 채널이 비어 있으면 쓰인다(`general-building-route-actual.ts:95`). 공통 몫을 선언 채널에 넣으면 선언 채널이 생겨 이 직접분이 후퇴한다 — 공통 몫 합산 시 **직접분도 같은 채널로 옮기는지(양도비 전액 취급 — 이월과세 카드의 legacy 덩어리 규칙과 같음)** 를 Pre-Do 격자로 정한다(V-4).
