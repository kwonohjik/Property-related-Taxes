## 3. 원인 추적 (file:line)

### 3.1 소실 지점
1. `lib/tax-engine/transfer-tax-carryover.ts:226` `const effectiveCapex = (rawInput.capitalExpenditure ?? 0) + effectiveDonorCapex;` — **항상 숫자**(증여자 자본적지출이 0이어도 0).
2. `:298` `capitalExpenditure: effectiveCapex` — A 입력(`inputABase`)이 **본인이 선언하지 않았어도** `capitalExpenditure !== undefined`가 된다.
3. `lib/tax-engine/transfer-tax-helpers.ts:261-263` `swapEligible = input.capitalExpenditure !== undefined || input.transferExpense !== undefined` → `:267` 실가 모드 `expensesApplied: swapEligible ? directSide : input.expenses` · `:281`/`:296` 환산 모드는 `expenses` 무시. 즉 **스칼라 `expenses`는 선언 채널이 비어 있을 때만 쓰인다.**
4. A 최종 입력 조립 `:362-426`: 실가 갈래(`:417-426`)는 `transferExpense: (rawInput.transferExpense ?? 0) + giftTaxAddedToExpense`와 `expenses: rawInput.expenses`를 싣지만 3번 때문에 `expenses`는 읽히지 않는다. 환산 갈래(`:398-415` — 이 갈래는 `capitalExpenditure`/`transferExpense`를 undefined로 되돌리고 `expenses`만 싣는다)는 `necessaryExpenseBeforeGift`(= 양도가 − 증여자 환산취득가 − 증여세 가산 전 양도차익 · `:385-388`)에서 파생하는데 그 양도차익이 이미 본인 지출을 뺀 값이라 같은 소실을 물려받는다.
5. B는 `lib/tax-engine/transfer-tax-carryover-inputs.ts:67` `capitalExpenditure: rawInput.capitalExpenditure`(미선언이면 undefined) → `swapEligible` false → `expenses` 사용. **A만 `:226`에서 선언 상태로 바뀐다.**

### 3.2 카드가 `expenses`로만 싣는 이유
- 일반건물 환산: `app/api/calc/transfer/general-building-route-cards.ts:193` `expenses: isSwapCard ? swapNabok : card.expenses + directAddition`. 카드의 `capitalExpenditure`/`transferExpense`는 어디서도 세워지지 않는다. `card.expenses`는 환산 파트에서 **본인 환산의 개산공제**(`general-building-swap.ts` 가목)이고, swap 발동 시 `swapNabok`(본인 나목을 (취득가액+개산공제) 비례로 환산 카드에 배분한 몫), 실가 파트는 `directAddition`(§97②1호 가산).
- 일반건물 실가: `app/api/calc/transfer/general-building-route-actual.ts:435`(`expenses: landExp`), `:426`, `:459`(`expenses: buildingExp`). 자본적지출은 취득시 기준시가, 양도비는 양도가액 비례(`apportionExpenses`)로 이미 합산된 몫이다.
- 함께양도: `app/api/calc/transfer/bundled-split-helpers.ts:285` `expenses: a.allocatedExpenses`(= 자산별 `directExpenses` + 공통 양도비 가액 비례 몫 · `lib/tax-engine/bundled-sale-apportionment.ts:226`), `:286-287`은 사용자가 선언한 `capitalExpenditure`/`transferExpense`만 싣는다. 주 자산도 `engine-input.ts:56` `expenses: data.expenses`.
- 단건 UI는 `lib/calc/transfer-tax-api.ts:339-352`에서 `capitalExpenditure`/`transferExpense`를 **선언**하고 `expenses`(= `directExpenses`)는 deprecated 0이다(`transfer-tax-validate-split.ts:667-672`). 그래서 단건은 정상이다.

### 3.3 이 규칙은 의도였나
- `:225` 주석 「4b: 필요경비 합산 (swap 통합 — directSide에 증여자 capex 포함)」, `:371-376` 주석(「자본적지출이 누락되지 않는다 — 과거 버그: 개산공제만 써서 capex 전액 누락」)이 보여 주듯 **의도는 본인 자본적지출을 A 나목에 넣는 것**이다. 이 의도는 `carryover-estimated-gift-capex-swap.test.ts`(단건)가 고정한다. 일반건물 카드는 채널이 달라 그 의도가 닿지 않았다.
- `buildProperties`(`general-building-route-cards.ts:158` 부근)와 환산 경로 주석은 이월과세 카드에서 `expenses`가 A에 들어간다는 전제를 한 곳에서도 쓰지 않는다 — 전제 위반이 아니라 **침묵 소실**이다.

### 3.4 B 쪽 부수 현상 (B-2, A 수정과 별개로 결정 필요 — Q-3)
환산 경로에서 이월과세가 **적용 배제**(예: 기간초과)되면 `buildInputB`가 취득가액 = 증여 당시 평가액(실지거래가액으로 봄 — 「소득세법 시행령」 제163조 제9항)을 쓰면서 필요경비는 카드 스칼라(**본인 환산의 개산공제**)를 그대로 쓴다. 측정: 증여 2010-03-17(기간초과), 토지 카드 취득가액 200,000,000 + 필요경비 **2,394,000**(자본적지출 0) — 실가 경로·단건은 0 / 자본적지출 3M이면 2,473,212. 법문상 개산공제는 제97조제2항제2호(환산 등) 몫이라 실지거래가액 B에는 근거가 없다.

**판정(법문이 명확 — 해석례·질의 불요)**
1. 이월과세 A의 필요경비는 제97조제2항 체계다. 제97조의2제1항 제2호는 증여자의 지출을 **더하는** 문언이지 양도자 본인의 지출을 **대체**하는 문언이 아니다(「포함한다」). 따라서 A에서도 본인의 자본적지출·양도비는 제97조제1항제2호·제3호 금액으로 들어간다.
2. 증여자가 실지거래가액이면 제97조제2항제1호 — 취득가액에 제1항제2호·제3호를 **전부 더한다**(비교 없음). 증여자가 환산취득가액이면 제2호 — 가목(증여자 환산취득가액+개산공제) 대 나목(자본적지출+양도비, 증여자 자본적지출 포함)을 비교한다. 현행 엔진의 환산 갈래 비교식(`transfer-tax-helpers.ts:281`)과 일치.
3. 제163조의2제2항 후단 한도는 「양도가액 − 제97조제1항·제2항의 금액」이라 **본인 지출이 한도 계산에도 들어간다**. 수정하면 `giftTaxLimitCap`(`transfer-tax-carryover.ts:366`)이 지금보다 작아질 수 있다(본인 지출이 매우 크면 한도 발동 가능 — Pre-Do 확인).
4. 따라서 A에서 본인 지출을 빼는 현행 일반건물·함께양도 거동은 **결함**이다. 「의도된 규칙」으로 읽을 문언 근거가 없다. (제97조제2항제2호 단서의 「할 수 있다」는 납세자 선택 문언이며 엔진은 큰 쪽을 자동 선택한다 — 이 문서의 대상이 아니고 현행 유지.)
5. B(비교과세)는 제97조의2 제1항을 적용하지 않는 계산이라 증여 당시 평가액 취득가액(실지거래가액 의제, 령 §163⑨)에 제97조제2항제1호를 쓴다 → 개산공제 혼입(§3.4)은 법문 근거가 없다(별건 Q-3).

일반건물 카드의 `expenses`는 경로마다 뜻이 달라 **접을 수 없다**(§6.1 가드 실측). 카드별 본인 직접귀속 나목을 따로 내려 명시한다.

| 카드 종류 | `expenses`의 뜻 | A에 줄 본인 나목 |
|---|---|---|
| 환산 파트(환산 경로) | swap 불발: 본인 환산의 **개산공제** / 발동: `swapNabok` | 신규 — swap 결정이 계산 (아래 1) |

| 실가 경로 카드 | 본인 자본적지출+양도비 몫 그대로(`general-building-route-actual.ts:426/435/459`) | `card.expenses` |

1. `lib/tax-engine/general-building-swap.ts` `GeneralBuildingSwapDecision`에 `ownDirect: Map<propertyId, number>`. 자산총액 판정 분기: `directSide`를 환산 카드 전부에 `(acquisitionPrice+expenses)` 비례(`allocateWithinGroup` 재사용 — 잔액 흡수), swap 발동 여부와 무관. 파트 축(`resolvePerPart`): 파트 직접귀속 + 파트 안분 양도비를 그 파트 카드에 같은 basis로. 갈래 4는 `continue` 전에 같은 계산.
2. `app/api/calc/transfer/general-building-route-cards.ts:193` 부근 `buildProperties`: `card.carryoverTaxation`이 있는 카드에만 `capitalExpenditure`(= 위 몫, 없으면 **0 명시**). 비이월과세 카드는 변경 없음. 실가 경로 호출(`buildProperties(cards, nonBusinessRatio, undefined, …)` — `general-building-route-actual.ts:634`)은 `swap`이 없으므로 `card.acquisitionMode === "actual"`이면 `card.expenses`를 싣는다.
3. 이월과세 카드 `expenses` 스칼라는 그대로 둔다(비이월과세 공용). B는 `capitalExpenditure`를 명시 값으로 받으면 `swapEligible`이 켜져 B도 실가 의미(자본적지출+양도비, 개산공제 없음)가 된다.
4. `buildApportionment`(같은 파일 하단)의 사이드바 표시는 세액과 무관 — 이월과세 카드 표시가 스칼라 그대로인지 Do에서 확인(V-5).
5. 증축 카드(building1)·지분(%) 카드는 같은 `buildProperties`를 쓰지만 몫 계산이 증축 전/후 배분과 얽힌다 → Do 전 probe(V-1). 막혀 있다면 침묵 소실을 남기지 않도록 해당 조합을 validate로 차단할지 Q-6.

3. **V-4 표시: `capitalExpenditureForDisplay`를 `min(자본적지출, 필요경비)`로 상한 (§6.2·§6.3)** — 카드가 `capitalExpenditure`를 싣기 시작하자 `capExInAcquisitionColumn`(이월과세 A 에서 자본적지출을 취득가액 칸으로 옮김)이 양수가 되었다. 증여자 **환산** + 단서 불발(본문 = 개산공제) 또는 단서 발동 시 표시(취득가액 = 환산취득가, 필요경비 = 역산 나머지)에서는 그 값이 필요경비보다 커져 `양도가액 − (취득가액칸 + 필요경비칸) ≠ 양도차익`이 되었다(8개 조합 × 2카드 = 16개 중 3건 False 실측). `transfer-tax-aggregate-once.ts` 에서 상한을 두어 전부 True. 세액 불변.
4. **Q-6: 차단이 아니라 포함으로 닫음** — 증축(3-way)·지분(%) 카드는 같은 `buildProperties`·`resolveGeneralBuildingSwap`을 거치므로 `ownDirect`(단서를 강제 발동한 2차 실행의 `allocation ∪ addition`)가 그대로 선다. 실측: 지분 B 토지 A 필요경비 12,000,000 → 17,000,000(몫 5,000,000), 증축 원건물 환산 토지 몫 10,649,350(= 20M × 235,610,102 / 442,487,265)·원건물 실가 11,549,295(= 20M × 205/355), 증축분 환산·실가 모두 확인. 차단하지 않으므로 ⑧ validate·⑫ 서버 거울이 필요 없다. 증축 분기 4곳은 단위 테스트(O-6~O-10)로 뮤테이션을 죽인다.
5. **Q-4 합산의 부작용(별건 후보)** — 본인 자본적지출·양도비를 `capitalExpenditure` 한 칸에 합산하면, 신고서가 이월과세 A 에서 `capitalExpenditureForDisplay`를 취득가액 칸에 얹는 관행 때문에 **양도비 몫도 취득가액 칸에 표시**된다(E2E 실측: 토지 취득가액 165,000,000 = 증여자 150M + 본인 몫 15M — 양도비 5M 포함, 필요경비 칸 12,000,000 은 증여세). 세액과 항등식은 정확하다. 라벨까지 정확히 하려면 자본적지출/양도비를 나눠 싣는 별건(Q-4 b안)이 필요하다 — **이번 범위 밖**. 증여자 환산 + 단서 불발 + 증여세 0 구간은 상한 때문에 개산공제가 「자본적지출」 문구로 표시될 수 있다(합계는 맞음).
