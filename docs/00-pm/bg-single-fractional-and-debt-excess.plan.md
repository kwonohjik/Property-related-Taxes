# 부담부증여 — 단건 지분 담보 승 차단 사유 + 기준시가 모드 채무 초과(B/C > 1) ⑧↔엔진 정합

> 선행: #2762(사이드바 일반건물 묶음 + ⑧ 균일 승자 과차단 해제). 그 PR 본문의 「고치지 않은 것」 두 건을 이어서 처리한다.
> 사용자 지시: 「단건 지분 담보 승, 기준시가 모드 채무 초과 500, 안내 문구 정리 순서로 진행해」 — 이 PR 은 앞의 두 건(둘 다 ⑧ 의 `validate-bg` 채무 초과 검사)이다. 셋째(안내 문구)는 UI 라 별도 PR.

## 1. 단건 지분 담보 승

### 1.1 실측 (수정 전)

공유 소유 50%(나머지 타인 소유 선언 = 축 A, Gate-A 통과) 주택, 시가 모드, 시가 10억·본인 인수 채무 7억(설정액 7억):

| | 결과 |
|---|---|
| 증여가액 C | 담보평가 7억(보충 5억을 이김) |
| 엔진 | 200 · 취득가액 = 취득시 기준시가 5억 × 지분 50% × 채무비율 1 = 250,000,000 · 양도차익 442,500,000 |
| ⑧ | 「채무액(700,000,000원)이 증여가액(500,000,000원) (지분 50% 해당분 …)을 초과합니다」 로 차단 |
| 취득시 기준시가 비움 | 엔진 400 「취득시 기준시가를 입력하세요」(담보 승이 취득가액 기준을 기준시가로 강제) |

### 1.2 원인

- ⑧ 의 분모는 시가 × 지분율이다. 담보가 이기려면 보증금 + min(설정액, 차입금) > 보충적평가(시가분) 이어야 하므로 **채무 합계가 항상 시가분보다 커서 이 검사에 항상 걸린다** — 사유가 틀리다(채무가 증여가액을 넘은 것이 아니라 담보평가액이 이긴 것).
- #2762 PR 본문의 「⑤ 가 실지취득가액 칸을 연 채 엔진이 취득시 기준시가를 강제」는 이 차단에 가려 **화면에서 도달하지 못한다**(정정).
- 완전 지원은 승자 판정(`bgWholeGiftValuation`·`bgCollateralForcesStdAcq`)이 자산 하나만 보는 함수라 축(공유 소유 / 지분 분할 취득)을 form 맥락으로 8개 호출처(⑤ 2곳 · lib 6 파일)에 전달해야 한다. 축 B 자산에 축 A 해석을 적용하면 승자를 잘못 판정해 ⑤ 칸을 잘못 숨긴다(실제 축 B 회귀 위험). 사용자 결정(Q-1 a): **정확한 차단 문구로 교체**한다.

### 1.3 수정

`bgFractionalCollateralWin(asset)` (`burdened-gift-collateral-win.ts`) — 지분 < 100% 이고 시가 모드 담보 승이면 true. ⑧ 이 채무 초과 검사 **앞에서** 이 경우를 「지분 자산의 담보 승은 취득가액 처리를 확인하지 못해 계산하지 않는다」로 막는다(축 B 는 제외). 계산 가능 범위는 그대로이고 사유만 정확해진다.
진짜 채무 초과(담보가 못 이기는 경우 — 설정액이 작음)는 종전 「초과」 문구를 유지한다.

앵커 `transfer.route.bg-single-fractional-collateral.anchor.test.ts` SF-1~3(4건) · 뮤테이션(⑧ 원복) 시 SF-1 red.

## 2. 기준시가 모드 채무 초과 500

### 2.1 실측 (수정 전)

기준시가 모드 주택 묶음·단건에서 자산의 채무가 자기 증여가액을 넘으면 ⑧ 은 통과하고 엔진이 `[EXCESS_BURDENED_GIFT]` 를 **일반 `Error` 로 던져 route 가 500 `INTERNAL_ERROR`(개발 환경은 스택 노출)** 로 응답했다. 같은 계열의 다른 부담부증여 입력 오류는 `TaxCalculationError(INVALID_INPUT)` 라 400 이다(저장소 규약 2026-09-30 — `lib/api/tax-error-response.ts`).

엔진은 **자산마다 자기 채무와 자기 증여가액을 비교한다**(주 자산 · 컴패니언 모두 실측 — 합계는 이내인데 주 자산 하나가 자기 증여가액을 넘어도 EXCESS). 따라서 ⑧ 의 자산별 검사가 같은 기준이다.

### 2.2 수정

1. 엔진(`burdened-gift-eligibility.ts`): 같은 메시지를 `TaxCalculationError(INVALID_INPUT)` 로 던진다 → 400. 메시지·`[EXCESS_BURDENED_GIFT]` 접두는 그대로(기존 엔진 시험 `toThrow(/EXCESS_BURDENED_GIFT/)` 무변경).
2. ⑧(`transfer-tax-validate-bg.ts`): 기준시가 모드에도 같은 검사를 한다. 증여가액은 엔진과 같은 경로(`companionBurdenedGiftValuations` — 지분 축소 → Max). 축 B 는 물건 전체 입력이라 지분을 줄이지 않는다(시가 모드와 같다). 메시지는 시가 모드와 한 헬퍼(`debtExceedsGiftValueMessage`)를 쓴다.

### 2.3 검증 (`transfer.route.bg-std-debt-excess.anchor.test.ts` 13건)

- SD-1 격자 12셀(단건 100% · 단건 50% 축 A · 함께 양도 묶음 × 채무 위치·수준 · 담보 승 포함): ⑧ 「채무액(」 차단 ⇔ 엔진 EXCESS(400), ⑧ 통과 셀은 엔진 200. 담보 승 셀(C 가 담보평가액)은 거짓 차단이 없다.
- SD-2: 엔진 직접 호출 초과 = 400 INVALID_INPUT (500 아님).
- 뮤테이션 2종: 엔진 원복 → 7건 red, ⑧ 검사 제거 → 6건 red. 복원 `diff -q` 확인.

## 3. 이번에 발견했으나 고치지 않은 것

- **함께 부담부증여 주 자산(첫 자산)에 채무가 없으면 ⑧ 통과 · ⑫ 400** (실측, 정상 금액에서도): 주 자산 채무 0 · 컴패니언 2억 → ⑧ 이슈 0 인데 요청이 `transferPrice: Too small: expected number to be >0` 로 400. 반대(주 자산 2억 · 컴패니언 0)는 200(양도차익 97,000,000). ⑧ 의 묶음 문구는 「채무가 설정된 물건에만 입력하면 됩니다」 라 화면 안내와 어긋난다 — 주 자산의 §159 양도가액 A×B/C 가 0 이 되어 `transferPrice` 양수 검사에 걸리는 것으로 보이나 원인 코드는 미확인. 이번 격자의 주 자산 채무 0 셀은 이 400 이 EXCESS 를 가려 제외했다. 별건(사용자 결정 필요: 주 자산에 채무가 없는 묶음을 계산하게 할지, ⑧ 이 정확히 막을지).
