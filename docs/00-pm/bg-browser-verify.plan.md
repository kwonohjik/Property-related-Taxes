## 2. 결함 — 일반건물 부담부증여 함께 양도 묶음의 사이드바 취득가액·필요경비 「-」

- 재현(브라우저): 일반건물 부담부증여 2건 함께 양도(보충 승 — ⑧ 통과, 지원 조합) → 계산 → 입력 단계로 돌아와 사이드바를 보면 양도가액은 300,000,000씩 맞지만 **취득가액·필요경비는 「-」**. 같은 응답의 카드 값은 취득가액 150,000,000씩(실지 5억 × 채무비율 30%). 결과 화면은 맞다.
- 같은 사실을 vitest 로 대조(`computeTransferPerAssetSummary` 에 `runCalc` 응답을 먹임): 균일 담보 승 묶음도 같다(사이드바 취득가액 0 vs 카드 200,000,000, 개산공제 6,000,000). 단건 일반건물은 카드 합이 맞게 나온다(`transfer.sidebar-burdened-gift-acquisition` SA-3).
- 원인(코드 읽기 기준 — **경로는 확인 필요**): `lib/stores/transfer-per-asset-summary.ts` 의 일반건물 카드 합 귀속이 **단건 전용**이다(`apportionedCards` = `isSingle && bundledResult && !bundledMatch` `:208-209`, 위 `:202-205` 주석 「멀티 자산에서는 카드↔자산 대응이 성립하지 않으므로 적용하지 않는다」). 축 B 지분은 `gbShareBgCards`(`:226-`)가 따로 잡는다. **함께 양도(다른 물건) 묶음**은 이 둘을 비껴간다. 다만 실측값이 `acq = 0 · acqPending = false`(「계산 후 표시」가 아니라 「-」)라 부담부증여 else 분기(`acqPrice = 0` + pending)는 아니다 — 어느 분기가 0 을 만드는지는 실측하지 않았다. 표시만의 문제로 세액에는 영향이 없다.
- 영향 범위: ⑧ 이 지금도 통과시키는 조합(일반건물 부담부증여 보충 승 묶음)이다. ⑧ 을 풀면(Q-2) 균일 담보·임대 승 묶음으로 넓어진다 → **Q-2 보다 먼저 고쳐야** 한다.

## 3. 결정 대기

- **Q-1 사이드바 결함**: a(권고) 일반건물 부담부증여 함께 양도 묶음의 카드 합 귀속을 `transfer-per-asset-summary.ts` 에 추가(먼저 실측: 어느 분기가 0 을 만드는지, 일반건물 카드의 `assetId`/라벨이 폼 자산과 어떻게 대응하는지) / b 지금은 기록만.
- **Q-2 ⑧ 과차단 해제**: 근거 정리 — 계산 정확성(#2753·#2755) · ⑤ 안내(C-5c) · ⑦ 결과(C-5b)는 충족. 남은 조건: ① ⑧ 두 곳 수정(승자 게이트 + 묶음의 `wholeValuation`) ② 위 Q-1 사이드바. 권고: **Q-1 을 먼저, 그 뒤 ⑧ 해제**(이월과세·입주권·겸용의 담보 승 차단 조건은 건드리지 않는다).
- **Q-3 안내 문구(C-1)**: 지분 컴패니언 카드에서 두 번째 문구를 지분 카드에는 숨기거나 「이 물건(지분 인수분)」으로 맞춘다 — 표시 변경이라 가벼운 별건. 비권고도 아님.

## 4. 한계 (확인 필요)

- 결과 화면(C-5b)은 ⑧ 을 임시로 푼 로컬 dev 서버에서 본 것이라 커밋된 코드에는 없다.
- 인쇄 · 다크 모드 · 좁은 폭은 보지 않았다. 지분 컴패니언 결과 화면의 카드별 표시는 합산 평가 명세만 확인했다.
- 사이드바 원인은 코드 읽기 기준이고 카드 ID ↔ 자산 대응은 실측하지 않았다.
- dev 서버 첫 컴파일이 오래 걸려(300~400초) 일부 Playwright 호출이 백그라운드로 넘어갔다 — 결과에는 영향 없음.
