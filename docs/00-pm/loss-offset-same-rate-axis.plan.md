## 0. 한 줄 요약

시행령 §167의2①은 차손을 「**같은 세율**을 적용받는 자산」에 먼저 공제하라고 정하는데, 엔진은 `classifyRateGroup`이 만든 **「호」 기반 `RateGroup`**을 그 축으로 쓴다. 두 축은 **직교**해서 양방향으로 틀린다 — 같은 70%를 갈라놓고(제보), 40·50·60·70%를 한 그룹에 몰아넣는다.

**세액이 바뀐다**: 실측 두 시나리오에서 각각 **5,197,222원 과대**·**5,197,222원 과소**.

> 🔴 **결함이 셋 겹쳐 있다.** ① 통산 축이 「호」다(이 계획서 본문) · ② 합산에 편입된 자산이 **원본과 끊긴 동결 스냅샷**이라 미등기가 반영되지 않았다(§10 — 별건) · ③ 차손 자산은 세율이 표시되지 않아 ②를 **눈으로 확인할 수 없다**(§6(나)가 함께 해소).

## 1. 제보

차손이 **미등기 양도자산**에서 발생했고, 같은 신고에 **주택 1년 미만** 양도차익 19,000,000이 있다.

> 미등기 양도는 세율이 70%라 주택 1년 미만 양도세율 70%로 **같은 세율**이라 주택양도차익 19,000,000원을 **먼저 공제**하고 나머지 1,000,000원을 안분해서 공제해야 함

**이 지적이 정확하다.** 조문과 실측이 모두 뒷받침한다(§2·§3).

## 2. 법령 — 축은 「세율」이다 (본문 확인 완료, KoreanLaw MCP)

**소득세법 시행령 §167의2①** (시행 2026-07-01):

> 법 제102조제2항의 규정에 의한 양도차손은 다음 각호의 자산의 양도소득금액에서 **순차로** 공제한다.
> 1. 양도차손이 발생한 자산과 **같은 세율을 적용받는 자산**의 양도소득금액
> 2. 양도차손이 발생한 자산과 **다른 세율**을 적용받는 자산의 양도소득금액. 이 경우 … **각 세율별 양도소득금액의 합계액에서 당해 양도소득금액이 차지하는 비율로 안분**하여 공제한다.

**소득세법 §104①** — 제보 두 자산의 세율:

| 자산 | 호 | 세율 |
|---|---|---|
| 미등기양도자산 | **10호** | 「양도소득 과세표준의 100분의 70」 |
| 주택 1년 미만 | **3호** | 「100분의 50(**주택**, 조합원입주권 및 분양권의 경우에는 **100분의 70**)」 |

⇒ **호는 다르고 세율은 같다.** §167의2①1호는 「세율」을 말하므로 **1호 대상**이다.

## 3. 근본 원인 — 하나의 `RateGroup`이 **서로 다른 두 법령 축**을 겸용한다

| 축 | 조문 | 기준 | 근거 |
|---|---|---|---|
| 비교과세 합산 단위 | **§104⑤2호** | **호** | 기획재정부 재산세제과-536(2018.6.19.) · 국세청 기준-2018-법령해석재산-0098 — 「제104조 **각 호별**로 합산한 자산」 |
| 차손 통산 범위 | **영 §167의2①1호** | **세율** | 위 §2 본문 |

`classifyRateGroup`(`transfer-tax-aggregate-helpers.ts:60`)은 §104⑤용으로 설계됐고 그 목적으로는 옳다(주석에 「§104⑤ 오합산 방어선」이라고 명시돼 있다). 문제는 `offsetLosses`가 **같은 값을 §102② 축으로 재사용**한다는 것이다:

```ts
// transfer-tax-aggregate-helpers.ts — offsetLosses
records.map((r) => ({ income: r.income, rateKey: r.rateGroup, exempt: r.result.isExempt }))
//                                       ^^^^^^^^^^^^^ §104⑤ 축을 §102②에 쓴다
```

### 🔑 코어는 무죄다 — 축을 넣는 쪽이 틀렸다

`loss-offset-core.ts`의 배분 순서(1호 → 2호, pro-rata, floor + 잔액 흡수)는 **정확하다**. 직접 호출 probe로 확인했다:

```
같은 rateKey 4자산            → fromSame = [5,479,452 · 0 · 1,735,159 · 12,785,389]   (이익 비례 ✓)
차손만 단독 rateKey           → fromOther = 동일 비율                                  (2호 안분 ✓)
```

⇒ **고칠 곳은 `rateKey`를 만드는 한 줄이다.** 코어·배분 로직은 건드리지 않는다.

> 🔑 코어의 doc 주석은 **이 함정을 이미 알고 있었다** — 주식에 대해 「「호」 축을 쓰면 §104①11호 하나에 10%·20%·20∼25%·30%가 다 들어 있어 서식과 어긋난다」며 **적용 세율 값**을 축으로 쓰게 했다. **같은 논증이 부동산에는 적용되지 않았다.**

## 4. 실측 — 세율 ↔ 그룹 불일치 전수

`classifyRateGroup`과 실제 `appliedRate`를 자산별로 찍었다:

| 자산 | 실제 세율 | `rateGroup` | 호 |
|---|---|---|---|
| 미등기 | **70%** | `unregistered` | 104-1-10 |
| 주택 1년미만 | **70%** | `short_term` | 104-1-3 |
| 토지 1년미만 | 50% | `short_term` | 104-1-3 |
| 토지 1~2년 | 40% | `short_term` | 104-1-2 |
| 주택 1~2년 | 60% | `short_term` | 104-1-2 |
| 분양권 2년이상 | 60% | `short_term` | 104-1-1 |

**두 방향 모두 틀린다:**

- 🔴 **거짓 분리** — 70%(미등기) vs 70%(주택 1년미만)가 **다른 그룹**. 1호여야 할 것이 2호로 간다. ← 제보
- 🔴 **거짓 병합** — 40·50·60·70%가 **한 그룹**(`short_term`). 2호여야 할 것이 1호로 간다.

### 추가 충돌 (같은 병, 아직 제보되지 않음)

| 그룹 | 실제로 섞이는 세율 | 조문 |
|---|---|---|
| `multi_house_surcharge` | §55①**+20%p**(2주택) · **+30%p**(3주택↑) | §104⑦1·2호 vs 3·4호 |
| `non_business_land` | §104①8호 표 · §104④ **+10%p**(지정지역) | 서로 다른 표 |

> ⚠️ 이 둘은 **실측으로 확인하지 않았다** — 표는 조문 대조로만 도출했다. 착수 시 §4와 같은 방식으로 찍어 확인할 것.

## 5. 세액 영향 — **실측** (두 시나리오, 동일 크기 반대 부호)

### A. 거짓 분리 (제보 유형)

자산: 토지 60,000,000 · **미등기 차손 −20,000,000** · **주택 1년미만 19,000,000** · 토지 140,000,000

| | 통산 배분 | 총 납부세액 |
|---|---|---|
| 현행 | 2호 안분 5,479,452 / 1,735,159 / 12,785,389 | **65,400,222** |
| 수정안 | **1호 19,000,000** + 2호 300,000 / 700,000 | **60,203,000** |
| | | **5,197,222 과대** |

수정안의 배분이 **제보자가 말한 그대로**다 — 19,000,000 우선 공제, 잔액 1,000,000을 60:140으로 안분.

### B. 거짓 병합

자산: **토지 1~2년 차손 −20,000,000(40%)** · **주택 1년미만 19,000,000(70%)** · 토지 60,000,000 · 토지 140,000,000

| | 통산 배분 | 총 납부세액 |
|---|---|---|
| 현행 | **1호로 70% 자산에 19,000,000 전액** | **60,203,000** |
| 수정안 | 2호 안분 1,735,159 / 5,479,452 / 12,785,389 | **65,400,222** |
| | | **5,197,222 과소** |

> 🔑 **과세표준 합계는 두 경우 모두 동일하다**(A에서 196,500,000). 바뀌는 것은 **어느 자산이 차손을 흡수하는가**뿐인데, 그것이 §104⑤ 그룹별 과세표준을 바꿔 세액을 움직인다. 「합계가 같으니 무영향」이라는 직관은 틀린다.

## 6. 구현 제약 — 🔴 **차손 자산은 세율 정보를 갖지 않는다**

실측:

```
미등기(차손)   group=unregistered   appliedRate=0   rateClause=-
```

`buildLossTransferTaxResult`가 `appliedRate: 0` · `progressiveDeduction: 0`을 싣고 `rateClause`를 **아예 넣지 않는다**(차익 ≤ 0이라 세율 단계에 도달하지 않는다).

⇒ **새 키를 `result.appliedRate`로 만들면 모든 차손 자산이 `rate:0`이라는 자기만의 그룹에 갇혀 1호가 영구 공전한다.** 현행 `classifyRateGroup`이 **입력 기반**인 것은 이 이유였을 가능성이 크다(추정 — 착수 시 커밋 이력으로 확인할 것. memory `feedback_deliberate_design_looks_like_the_defect`).

**해소 방향 두 가지 — 착수 시 실측으로 택일:**

- **(가) 입력 기반 유도** — `propertyType` + §104② 기산일 보유기간 + `isUnregistered`로 세율을 직접 계산. 이미 probe 패치로 동작을 확인했다(§5 수정안 수치가 그것). 단순하지만 **`transfer-tax-rate-calc.ts`의 세율 판정을 한 벌 더 쓰는 dual truth**가 된다.
- **(나) 차손 자산도 세율을 산출** — 조기반환 전에 `calcTax(0, …)`를 태워 `rateClause`·`appliedRate`를 결과에 echo. 단일 소스가 유지되나 조기반환 경로를 건드린다.

> **권고: (나)**. 이 저장소는 「같은 판정을 두 곳에서 손으로 다시 적는 것」으로 반복해 실패했다(memory `feedback_ui_engine_dual_truth_avoidance` · `feedback_leaf_unification_leaves_one_handwritten_predicate`). 다만 (나)는 §1642에서 막 손댄 차손 조기반환 경로를 다시 건드리므로 **세액 불변을 anchor로 고정한 뒤** 진행한다.

## 10. 🔴 **결함이 더 있다** — 미등기가 엔진에 도달하지 않았다

이미지 19의 4자산을 **정확한 수치로** 재현했다. 결정적 결과:

| 실행 | 결과 |
|---|---|
| `isUnregistered: true` | 안분 `54,520,548 / 0 / 17,264,841 / 127,214,611` · scope 전건 `other_group` |
| **`isUnregistered: false`** | **`40,000,000 / 0 / 19,000,000 / 140,000,000`** · `same_group` 1건 20,000,000 |
| **이미지 19 화면** | **`40,000,000 / 0 / 19,000,000 / 140,000,000`** |

⇒ **화면은 `false` 실행과 원 단위로 일치한다.** 사용자는 미등기 토글을 켰는데(이미지 18) **엔진은 양도 2번을 `progressive`로 분류**했다. 그래서 차손이 일반누진 자산(양도 1번, 24%)과 「같은 그룹」이 되어 1호로 전액 흡수됐다.

### 배선 층별 실측 — **전 구간이 플래그를 보존한다**

사용자 확인: **4건 모두 단건으로 계산한 뒤 이력에서 「합산」**(PR #1637 경로). 그 경로를 end-to-end로 태웠다.

| 단계 | 위치 | 실측 |
|---|---|---|
| 단건 이력 저장 | `TransferTaxCalculator.tsx:115` — `inputData: formData` | ✅ formData 전체 저장(form-global `isUnregistered` 포함) |
| dedup 갱신 | `calculation-repository.ts:226` | ✅ `inputData: input.inputData`로 **덮어쓴다**(stale 아님) |
| 이력→property | `transfer-multi-load-entry.ts:44` | ✅ probe → `property.form.isUnregistered = true` |
| ④ API 변환 | `multi-transfer-tax-api.ts:255` | ✅ probe → `payload.isUnregistered = true` |
| ⑫ Zod | `propertyItemSchema.safeParse` | ✅ **실제 파싱** → `true` 생존 |
| ⑭ Route | `multi/route.ts:146` | ✅ 무조건 매핑 |
| ⑤ UI 게이트 | `Step4.tsx:339` | ✅ `"land"`는 제외 목록에 없음 |

⇒ **코드 경로에는 유실 지점이 없다.** 즉 양도 2번 record가 **`isUnregistered: false`로 저장돼 있다**.

### 🔴 **세 번째 결함** — 합산에 편입된 자산은 원본 record와 **연결이 끊긴 동결 사본**이다

사용자 확인: **해당 record의 미등기 토글은 켜져 있다**(첫 실행 OFF → 이후 ON으로 바꿔 재실행). 그런데 위 7개 층은 전부 플래그를 보존한다. 남는 설명은 **합산이 읽은 form이 record의 «현재» 값이 아니다**라는 것뿐이다.

코드로 확인했다:

| 지점 | 사실 |
|---|---|
| `transfer-multi-load-entry.ts:44` | `form = record.inputData` — 편입 시점의 **사본**을 property에 싣는다 |
| `transfer-multi-load-entry.ts:53` | `sourceCalculationId: record.id` — 원본 id는 **들고 있다** |
| `multi-transfer-tax-store.ts:246` | `createJSONStorage(() => sessionStorage)` — `properties`가 **세션에 persist**된다 |
| — | **원본 record 변경을 감지하는 장치가 없다** |

⇒ 합산 화면에 한 번 편입한 뒤 단건으로 돌아가 입력을 고치고 재계산해도, 합산 화면은 **옛 스냅샷으로 계속 계산한다**. 그 사실이 사용자에게 **어디에도 표시되지 않는다**.

`sourceCalculationId`가 이미 있으므로 감지는 가능하다 — `backfillPriorPaid`(`:80`)가 같은 id로 원본을 되살리는 선례가 있다.

**수정 방향(별건 계획서로 분리):** 편입 시 원본의 `inputHash`(이미 record에 있다)를 함께 저장하고, 합산 계산 직전에 대조해 **불일치 시 「원본이 변경됨 — 다시 불러오기」 배너**를 띄운다. 자동 갱신은 사용자가 합산 화면에서 직접 고친 값을 덮을 수 있으므로 **금지**하고 명시적 재편입만 제공한다.

### 🔴 왜 알아챌 수 없었나 — 차손 자산에는 미등기가 **아무 흔적을 남기지 않는다**

미등기의 효과 넷이 **차손 + 실거래가 자산에서는 전부 관측 불가**다:

| 효과 | 차손 자산에서 |
|---|---|
| 70% 단일세율 (§104①10호) | 세액 0 — 세율 미표시(`-`) |
| 장기보유특별공제 배제 (§95②) | 차손이라 어차피 0 |
| 기본공제 배제 (§103①) | 합산 단계에서만 작동 |
| 개산공제 0.3% (§163⑥4) | **환산취득가 모드 전용** — 실거래가면 무효 |

이미지 19의 양도 2번 열도 **세율구분 코드 `-` · 세율 `-`**다. ⇒ 스냅샷이 낡았다는 사실이 화면 어디에도 드러나지 않는다.

> 🔑 **§6(나) 권고안이 이 가시성 문제를 함께 해소한다.** 차손 자산도 `calcTax(0, …)`로 세율·호를 산출해 echo하면 신고서 양도 2번 열에 **세율구분 코드와 70%가 표시**되어 미등기 적용 여부를 눈으로 확인할 수 있다. 통산 축 수정과 **같은 변경**으로 얻어진다.

### ✅ 판별 테스트 (사용자 1분)

**이력 화면에서 「합산」을 다시 눌러 새로 편입**한 뒤 재계산한다. 기존 합산 화면에서 「계산」만 다시 누르면 안 된다 — 그게 스냅샷을 쓰는 경로다.

| 결과 | 판정 |
|---|---|
| 양도 1번이 **54,520,548**(양도3번 17,264,841 · 양도4번 127,214,611) | **스냅샷 결함 확정**. 미등기는 반영됨 — 남은 오차는 §7 축 결함 |
| 여전히 **40,000,000** | 스냅샷이 아닌 **다른 유실 지점** — 7개 층 밖을 다시 판다 |

> ⚠️ 두 결과 모두 **법정 정답이 아니다**. 정답은 §5 A의 수정안 — 양도 3번에 19,000,000 우선 공제 후 잔액 1,000,000 안분(양도1번 300,000 · 양도4번 700,000). 축 수정이 있어야 나온다.

### ⚠️ 축 결함과 **독립**이다 — 둘 다 고쳐야 한다

미등기가 제대로 실렸어도 현행 축으로는 **여전히 틀렸다**: `unregistered` vs `short_term`으로 갈려 2호 안분(5,479,452 / 1,735,159 / 12,785,389)이 나왔을 뿐, 법정 정답(19,000,000 우선 + 1,000,000 안분)이 아니다.

⇒ **§7의 축 수정은 이 건과 무관하게 필요하다.** 다만 이 재현으로 **제보 화면 자체는 두 결함의 합작**임이 확정됐다.

### 착수 전 확인 요청

**양도 2번을 어떻게 만드셨는지** 알려주시면 위 후보 1~3을 가를 수 있다 — (a) 다건 화면에서 「자산 추가」 후 편집, (b) 이력에서 불러오기/합산, (c) 단건 계산 후 자동 백업. 재현되면 별도 계획서로 분리한다(축 수정과 커밋을 섞지 않는다).

### 🟡 §103 기본공제 배분의 축 (별건)

`allocateBasicDeduction`도 `rateGroup`을 받는다. §103②의 축이 「호」인지 「세율」인지는 **이 작업에서 판정하지 않았다**. 범위 밖으로 두되, §102②과 같은 병일 수 있으므로 별도 항목으로 남긴다.

### 🟡 §104④·§104⑦ 충돌 (§4 하단 표)

조문 대조로만 도출했고 실측하지 않았다. A-7·A-8이 그 실측을 겸한다.
