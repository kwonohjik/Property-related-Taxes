## 0. 실측

`/calc/comprehensive-tax` 2단계 → 주택 행 → 카드 모달 → 소재지 선택 → 동·호 고르기 → **모달 닫았다 다시 열기**(카드가 다시 마운트된다, `PropertyListInput.tsx:157` `key={selectedProperty.id}`).

다시 열면 동·호 목록이 사라지고 상세주소 칸이 보인다. 칸 값은 저장된 동·호를 이어 붙인 것이다(「101동 501」, 단동은 「1203」). 그 칸을 고친 뒤 「공시가격 조회」:

| | 고친 방식 | 저장되는 동 / 호 | 조회 |
|---|---|---|---|
| a | 「101동 502」 | 101동 / 502 | 502호 가격(정상) |
| b | 「101동 501호」 | 101동 / 501호 | 501호 가격(정상, API가 「호」를 뗀다) |
| h | 단동 「1204호」 | "" / 1204호 | 1204호 가격(정상) |
| j | 별도 「호수」 칸에서 1204 | "" / 1204 | 1204호 가격(정상) |
| c | 「101동501호」(띄어쓰기 없음) | 101동501호 / 101동501호 | 「해당 세대 없음」 |
| f | 다동, 끝 글자 하나 지움 | 101동 / 50 | 「해당 세대 없음」 |
| e | 칸을 비우고 「102동 501」을 한 글자씩 | 동 / 501 — 「동」을 치기 전 숫자가 모두 사라진다 | 「해당 세대 없음」 |
| **d** | 칸 비움 | "" / "" | **임의 세대 가격으로 「조회 성공」**(7억 — 고른 세대 9억) |
| **g** | 단동, 숫자만 「1204」 | "" / "" | **임의 세대(1203호 6억)로 「조회 성공」** — 원한 값은 1204호 5억 |
| **i** | 단동, 끝 글자 하나 지움 | "" / "" | **임의 세대 가격으로 「조회 성공」** |

- 다른 세대 가격이 채워지는 것은 동·호가 **모두** 빈 값이 될 때다. 단동 단지에서는 숫자만 고쳐도 그렇게 된다.
- 동·호가 엉뚱한 값이 되는 경우(c·e·f)는 조회가 실패해 드러난다.
- 별도 「동」·「호수」 칸은 지번이 있으면 늘 보인다(`PropertyCardEditor.tsx:150~177`). 동·호가 지워진 것은 그 칸에서 보인다.
- 종부세 이력 키는 동·호를 쓰지 않는다(`lib/storage/business-key.ts:106` content 폴백). 영향은 공시가격 조회값에 한정된다.

## 1. 원인

- 카드는 `AddressSearch`에 동·호를 넘기지 않는다. 상세주소만 저장된 동·호로 합성해 넘긴다(`PropertyCardEditor.tsx:101~108`).
- 목록이 없으면 상세주소 칸이 보이고, 입력은 `onChange({ ...value, detail })`(`components/ui/address-search.tsx:295~296`)로 올라온다. 여기에 동·호가 없으니 호출부는 상세주소를 띄어쓰기로 파싱한다(`PropertyCardEditor.tsx:139~144`).
  - 두 단어면 앞=동, 나머지=호
  - 한 단어면 「동」이 들어 있으면 동, 「호」가 들어 있으면 호, 아니면 **빈 값** → 단동의 「1204」는 동·호 모두 빈 값(g)
- 칸 값이 저장된 동·호의 합성이라, 한 글자를 칠 때마다 파싱 → 저장 → 다시 합성이 돈다. 빈 값으로 파싱되는 중간 상태에서 칸이 비워진다(e·i).
- 공시가격 API는 동·호가 없으면 실패하지 않고 그 지번의 「최신 연도 첫 세대」를 돌려준다(`app/api/address/standard-price/route.ts:257` `if (dong || ho)`가 거짓이면 필터 없음).
- #2339의 R2(동·호가 있으면 다시 마운트될 때 목록을 다시 불러옴)는 `value.dong`·`value.ho`를 본다(`address-search.tsx:126~127`). 이 카드는 그것을 넘기지 않아 R2도 동작하지 않는다.

## 2. 수정안 — R1(다른 6곳과 같음)

- `addressValue`(`PropertyCardEditor.tsx:101~108`)에 `dong: property.dong || undefined`, `ho: property.ho || undefined`를 더한다.
- 그러면 두 가지가 함께 일어난다(임시 적용 실측, 원복함).
  - **다시 열면 목록이 고른 세대와 함께 돌아온다**(R2가 동작). 상세주소 칸이 나타나지 않아 위 표의 경로 자체가 사라진다.
  - **목록을 다시 불러오지 못하면** 상세주소 칸이 나타난다. 입력은 `{ ...value, detail }`에 저장된 동·호가 실려 파싱되지 않으므로 동·호가 지워지지 않는다. 대신 칸 값은 저장된 동·호의 합성이라 **입력이 원래 값으로 되돌아간다**(a·b·e·g 모두 「변화 없음」으로 실측). 동·호는 별도 「동」·「호수」 칸으로 고친다(j는 R1 뒤에도 정상).
- 파싱 코드(`:139~144`)는 남긴다. 저장된 동·호가 없을 때(세대를 고르지 않았거나 단독주택) 상세주소로 동·호를 적는 경로는 그대로다.

## 3. 영향·위험

| 항목 | 내용 |
|---|---|
| 세대를 고른 주택 | 다시 열면 목록 재조회 1회 이상(외부 API). 고른 세대가 드롭다운에 보인다 |

| 목록 재조회 실패 | 상세주소 입력이 되돌아간다(Q-1). 동·호는 지워지지 않는다 |
| 계산 결과 | 이 카드의 동·호는 공시가격 조회에만 쓰인다. 저장된 공시가격·세액은 바뀌지 않는다 |
| 다른 계산기 | `PropertyCardEditor`만 바꾼다 |

## 5. 검증 계획

- **회귀 E2E**(종부세 2단계 카드 모달, 주소 검색·공시가격 `page.route` 고정 — 실측 probe와 같은 mock)
  - K-1: 다동 101동 501 선택 → 모달 닫았다 열기 → 드롭다운에 501이 보이고 상세주소 칸이 없다 → 조회 요청 `dong=101동 ho=501`
  - K-2: 단동 1203 선택 → 같은 조작 → 드롭다운에 1203 → 조회 `ho=1203`
  - K-3: 목록 재조회 실패 → 상세주소 칸에 「1204」(단동)·빈 칸(다동)을 넣어도 별도 동·호 칸 값이 그대로이고 조회가 고른 세대로 간다
  - K-4: 목록 재조회 실패 → 별도 「호수」 칸에서 고치면 반영된다(j)
  - **반례** K-5: 세대를 고르지 않은 주소는 다시 열어도 세대 조회를 다시 부르지 않고, 상세주소 「101동 501」 입력이 종전처럼 파싱된다
- **뮤테이션**: `addressValue`의 동·호 제거 → K-1·K-2(목록 안 돌아옴)·K-3(동·호 지워짐) 실패
- **기존 E2E**: `comprehensive-*` 전 spec
- **pre-push 게이트**: 워크트리라 husky가 돌지 않는다. 폰트·톤·다크 짝·러너, typecheck, lint, 범위 선택 테스트를 수동으로 돌린다
