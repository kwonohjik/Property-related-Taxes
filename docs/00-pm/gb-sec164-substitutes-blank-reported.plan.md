# ④ 가 상속·증여 파트의 평가액이 비었는데 §164 가액만으로 취득가액을 채운다 — 「주 자산 I1」의 결론

- 상태: 구현 완료 (Q-1 a · Q-2 a — 사용자 「권고안으로 진행해」)
- 앵커: `__tests__/api/transfer.route.gb-sec164-substitutes-blank-reported.anchor.test.ts` (7건 — 수정 후 기대)
- 선행: `gb-companion-required-refines-parity.plan.md` §10 · V-1 「주 자산 I1(두 파트 상속·평가액 비움)도 200」

## 1. 요약

**⑫ I1 은 고장나지 않았다.** 우회는 ④ 에서 생긴다.

1. `inheritedLandValue` 는 ④ 가 §163⑨ **단서 비교(평가액과 §164 가액 중 많은 금액)까지 마친 최종값**이다. API 가 받는 계약도 그 값이다 — 직접 보내면서 빼면 ⑫ I1 이 400 으로 막는다 (앵커 SU-4, 단건·주 자산·컴패니언 3위치).
2. 그런데 ④ 는 단서 구간(토지 1990.8.30. 전 · 건물 취득연도 2000/2001 전)이면 `Math.max(평가액, §164 가액)` 을 계산하고(`lib/calc/transfer-tax-api-gb-sec163-9.ts:95-101`), **평가액이 0 이어도 §164 가액이 양수라 비교가 성립하지 않는 입력을 한쪽 값으로 메운다.** 증여 파트의 `giftMax`(같은 파일 `:146-148`)도 같다.
3. 그 값이 양수라 ⑫ I1 · I3 이 「입력이 있다」고 본다. ⑧ 은 이 입력을 막는다(`validate-gb.ts:226-229` V3·V4, 증여는 파트 가액 칸) — 화면에서는 도달하지 않는다. **API 직접 호출이 아니라 ⑧ 을 우회하는 ④ 입력**에서만 생기는 잠재 결합이다.

## 2. 측정

### 2.1 상속 — 두 파트 상속 · 평가액 비움 (72셀: 상속일 4 × 분리 OFF·ON × 비움 3 × 위치 3)

| 상속일 | 구간 | 토지 비움 | 건물 비움 | 둘 다 비움 |
|---|---|---|---|---|
| 1980-05-01 | 의제취득일 전 · 토지·건물 단서 | **200 ≠** | 200 (=) | **200 ≠** |
| 1988-05-01 | 토지·건물 단서 | **200 ≠** | 200 (=) | **200 ≠** |
| 1995-05-01 | 건물만 단서 | 400 | 200 (=) | 400 |
| 2005-05-01 | 고시 후 | 400 | 400 | 400 |

(≠ = 평가액을 입력한 대조 세액과 다름, = = 같음). **⑧ 은 72셀 전부 막고**, ⑫ 는 200 이 42셀 · 400 이 30셀이다. 200 인 42셀 중 24셀이 세액이 다르다. (=)는 이 시료의 건물 평가액(1억)이 §164 가액(1.5억)보다 작아 대조에서도 §164 가액이 채택되기 때문이며 보호가 작동한 것은 아니다.

| 입력 | 평가액 비움 | 평가액 입력 |
|---|---|---|
| 1988 토지 비움 · 컴패니언·주 자산 | 422,310,000 | 392,385,000 |
| 1988 토지 비움 · 단건 | 329,040,000 | 301,110,000 |
| 1980 토지 비움 · 컴패니언·주 자산 | 402,009,169 | 383,824,038 |
| 1980 토지 비움 · 단건 | 310,092,558 | 293,104,038 |

토지 평가액(3억)이 §164 가액보다 크므로 비우면 취득가액이 줄어 세액이 **과대**하다. 반대 방향(평가액 < §164 가액)에서는 세액이 같다 — 평가액이 의미를 잃는다.

### 2.2 증여 — 두 파트 증여 · 파트 가액 비움 (36셀: 증여일 4 × 비움 3 × 위치 3, 분리 ON)

⑧ 은 36셀 전부 막고 ⑫ 는 200 21셀 · 400 15셀이며 **200 인 21셀이 전부 세액이 다르다.** 1980·1988 은 비운 것 전부 200(18셀), 1995 는 건물가액만 비운 셀 200(3셀)·나머지 400, 2005 는 전부 400. 1988 토지가액 비움: 컴패니언·주 자산 406,560,000 (입력 347,730,000), 단건 314,340,000 (입력 257,010,000).

### 2.3 한쪽만 상속 (토지 상속 + 건물 매매 · 분리 ON · 토지 평가액 비움)

1988: 200 · 컴패니언·주 자산 406,560,000 (입력 377,130,000), 단건 314,340,000 (입력 286,410,000). 2005: 400. (건물 상속 + 토지 매매 변형은 대조 자체가 ⑧ 차단이어서 판정에 쓰지 않았다.)

### 2.4 앞선 주장의 정정

`gb-companion-required-refines-parity.plan.md` §10·V-1 은 「주 자산 I1 보호가 이 입력에서 작동하지 않는다」로 적었다. 틀린 해석이다 — 보호는 작동하며(SU-4) 입력 경로가 우회된다. 앞선 측정 셀(1988-05-01 상속)이 하필 단서 구간이어서 ④ 의 대체에 걸렸다.

## 3. 법령

새 해석 없음. 소득세법 시행령 §163⑨ 본문(상속·증여 평가액 = 취득당시 실지거래가액)과 단서 1호·2호(평가액과 §164④·⑤ 가액 중 **많은 금액**)는 ⑧ 의 기존 문구가 그대로 인용한다. 단서는 **두 값의 비교**이며 한쪽이 없는 상태는 단서가 다루지 않는다 — 입력이 비면 비교가 아니라 필수 입력 누락이다 (`gb-without-valuation-subobject` 와 같은 「미입력은 검증 오류」 규율).

## 4. 설계안

④ 가 단서 비교를 **평가액이 양수일 때만** 한다. 비면 비교하지 않고 비운 채 보낸다 — 그러면 ⑫ I1·I3 이 그대로 400 으로 막는다.

```ts
// transfer-tax-api-gb-sec163-9.ts
const inheritedLandValue = (reportedLandValue > 0 && landSec164Applies ? Math.max(...) : reportedLandValue) || undefined;
// 건물 · giftMax 도 같다: (reported > 0 && applies ? Math.max(...) : reported) || undefined
```

- ⑧ 을 통과한 폼은 상속·증여 파트의 평가액이 양수이므로 **⑧ 통과 입력의 값은 바뀌지 않는다.**
- ⑫ 에 새 규칙을 더하지 않는다 — 기존 I1·I3 이 이미 맞는 계약을 지킨다.

### 영향 (임시 적용으로 실측 — 파일은 되돌렸다)

- 상속 격자 72셀: 바뀐 셀 42, **전부 「⑧ 차단 · 200 → 400」**, 200 인데 세액이 다른 셀 24 → 0.
- 증여 격자 36셀: 바뀐 셀 21, 전부 ⑧ 차단 · 200 → 400, 세액이 다른 200 21 → 0.
- 한쪽만 상속 1988: 200 → 400.
- 양도세 회귀 1,558파일 중 실패 **3건 — 전부 이 계열을 현행으로 고정해 둔 기존 앵커**:
  - `gb-companion-required-refines-parity.anchor` RP-3 「I1 두 파트 상속 · 평가액 비움 — 두 위치 모두 200」 (위 §2.4 의 오해를 고정한 것 — 400 으로 뒤집는다)
  - `gb-inherited-estimate-guard.anchor` S-2 「증여(실가) → 200 · 329,040,000」 · 「토지 매매 환산 + 건물 증여 → 200」 — 이름은 「정상 경로는 그대로」이지만 두 입력 모두 **⑧ 이 막는 입력**이다(「증여일이 기준시가 고시 전이라 토지·건물의 증여 신고가액을 파트별로 나누어 입력하세요」 · 「건물 증여 신고가액을 입력하세요」). 고정된 값이 곧 §164 대체값이다. **구현 후 확인: 둘의 거동이 다르다** — §8 참조(앞선 판에는 둘 다 400 으로 뒤집힌다고 적었으나 틀렸다).
  - 나머지 1,555파일은 그대로 통과한다.

## 6. 미검증 (V)

- **V-1** ✅ ⑧ 통과 입력의 값이 바뀌지 않음을 live 대조로 확인했다 — 격자 1,968셀(1,280셀 격자 × 단건 + 상속·증여 × 날짜 4 × 분리 × 위치 3)에서 ⑧ 통과 **436셀의 (상태, 세액)이 수정 전후 모두 동일**(전부 200, 변화 0).
- **V-2** 의제취득일 전(1980) 파트의 `landPreDeemedClauseA {reported, sec164}`(`gb-pre-deemed.ts` · `preDeemedFields`)는 ①②를 따로 싣는다 — 이번 변경이 그 echo·③ 환산 분자와 충돌하는지는 Do 에서 PRE 앵커로 확인 필요(회귀 1,555파일은 통과).
- **V-3** 건물 상속 + 토지 매매(분리 ON) 변형은 대조 셀이 ⑧ 차단이어서 측정하지 못했다 — 대칭일 가능성이 높으나 확인 필요.
- **V-4** 결과 echo `landSec1639Basis`(`adopted: "sec164"`)는 평가액 0 · §164 가액 양수일 때도 `sec164` 로 찍힌다 — 변경 후 값이 없는 파트는 echo 가 `undefined` 가 되어 표시가 바뀌는지 확인 필요.

- **V-5** 🆕 **분리 OFF 증여 × 고시 전(단서 구간)은 이번 수정으로 닫히지 않는다** — §8.

## 8. 구현 결과 (Do)

- `compareSec164(reported, applies, sec164)` (`transfer-tax-api-gb-sec163-9.ts`) — 평가액이 양수일 때만 §164 와 겨룬다. 토지·건물 상속(`inheritedLandValue`·`inheritedBuildingValue`)과 증여 파트(`landPartPrice`·`buildingPartPrice`)가 같은 헬퍼를 쓴다. 종전 `giftMax` 는 이 헬퍼로 대체해 삭제했다.
- 앵커 7건을 수정 후 기대로 뒤집었다(비운 셀 전부 400 · 대조 셀 ⑧ 통과 · 200 · 세액 불변). 변경안 적용 시 6건 적색이었던 것이 수정 후 7건 통과.
- 기존 앵커 정정: `gb-companion-required-refines-parity` RP-3 I1 (200 → 400) · `gb-inherited-estimate-guard` S-2 — ⑧ 이 막는 증여 입력 둘을 「정상 경로」 목록에서 분리.
- 격자: 상속 72셀 · 증여 36셀 전부 400, 한쪽만 상속 1988 400. **⑧ 통과 436셀 (상태, 세액) 변화 0.**
- 양도세 회귀 1,559파일 / 19,845테스트 통과.

### 구현 중 새로 드러난 것 (V-5) — 분리 OFF 증여 × 고시 전

S-2 의 두 입력 중 「토지 매매 환산 + 건물 증여(건물 증여 가액 비움)」는 예상대로 400 이 됐지만 **「증여(실가) · 분리 OFF · 고시 전」은 400 이 아니라 200 이다.**

| | 파트 슬롯 | 최상위 `acquisitionPrice` | 결과 |
|---|---|---|---|
| 수정 전 | 토지 205,000,000 · 건물 150,000,000 (= §164 가액으로 채움) | 400,000,000 (**무시됨**) | 200 · 329,040,000 |
| 수정 후 | 비움 | 400,000,000 (일괄 신고가액 — §166⑥ 안분) | 200 · 315,810,000 |

- ⑧ 은 이 입력을 막는다(증여일이 기준시가 고시 전이면 파트별 신고가액이 필요 — `validate-gb.ts` 증여 갈래) — 화면 도달 불가. ⑫ 는 수정 전후 모두 통과시킨다.
- 이 수정은 파트 슬롯이 빈 입력을 400 으로 막는 것이 아니라 **빈 슬롯을 §164 로 메우지 않는 것**이다. 분리 OFF 일괄 신고가액은 파트 슬롯이 아니라 최상위 값이므로 ⑫ I3 이 만족한다(`bundled > 0`). 결과는 사용자가 입력한 신고가액을 쓰게 바뀌었지만(수정 전에는 무시), **단서 비교(파트별 ①②)는 여전히 하지 못한다.**
- 별건 후보: ⑫ 가 ⑧ 과 같은 조건(증여 · 토지 1990.8.30. 전 또는 건물 고시 전 · 분리 OFF)에서 400 — 주 자산·컴패니언·단건 모두. 새 ⑫ 규칙이므로 계획서·Q 가 필요하다. 앵커 S-2 가 현행(200 · 315,810,000)을 고정한다.
